# UPS Software

This **optional chapter** is only for readers who have a compatible [uninterruptible power supply (UPS)](https://en.wikipedia.org/wiki/Uninterruptible_power_supply). A UPS can keep the homelab running through short power outages, report battery charge, load, estimated runtime, and power events, send useful alerts, and provide enough time for an orderly shutdown during a longer outage instead of letting the server lose power abruptly.

This guide cover two UPS management softwares: Network UPS Tools (NUT) and PowerMaster+. The correct choice depends on the exact UPS model, its USB, serial, SNMP, or network connection, and the quality of the available driver or vendor support; verify those details before installing either option. In most cases NUT supports wide range of UPS hardware while PowerMaster+ is more hardware dependent.

## About UPS Software

UPS hardware supplies temporary battery power, but management software turns the UPS state into useful system behavior. It reads utility-power and battery conditions, records events, exposes health and runtime information, sends alerts, and coordinates shutdown when configured thresholds are reached. In a multi-server design, it can also distribute the UPS state so secondary systems shut down before the machine controlling the UPS switches off the protected load.

[NUT](https://networkupstools.org/documentation) is free and open-source UPS management software with broad device and platform support. A hardware-specific driver communicates with the UPS, the `upsd` data server exposes its state, and clients such as `upsmon` monitor that state and can shut down the local or a remote system when power becomes critical. It is configuration-driven and fits the Debian base used by Proxmox VE.

[PowerMaster+](https://www.powermonitor.software/) provides an integrated browser interface and a vendor-oriented workflow. The computer connected to the UPS through USB or serial runs the **Local** component, while other UPS-powered computers can run **Remote** and receive state and shutdown instructions over the protected network. A compatible PMCARD can provide the UPS connection instead. PowerMaster+ can display battery condition, load, estimated runtime, and event history, but its Linux package must also support the host operating system.

Neither option is universally better. Choose the implementation that supports the exact UPS and communication method, provides the integrations you require, and matches the management experience you are prepared to maintain.

## Before You Begin

Complete these checks before changing the host:

- Find the UPS manufacturer, exact model, and communication method. A family name or similar-looking USB identifier is not enough.
- Confirm the model in the [NUT hardware compatibility list](https://networkupstools.org/stable-hcl.html) or the vendor's current PowerMaster+ compatibility information.
- Connect the UPS data cable directly to the machine that will manage it. Also identify every server, storage device, switch, and router that must remain powered long enough for coordinated shutdown.
- Verify that current backups exist and that local console access is available. Do not begin shutdown testing during a backup, replication, scrub, resilver, migration, upgrade, or other storage-intensive operation.
- Record the normal UPS load and estimated runtime. The shutdown reserve must come from measured behavior under the real load, not from an arbitrary percentage copied from another installation.

This guide follows current Proxmox VE 9.x, which is based on Debian 13. The current PowerMaster+ `1.2.3` 64-bit Linux support list stops at Debian `12.6`, so this guide does **not** treat direct PowerMaster+ installation on a Proxmox VE 9 host as supported. Use NUT on that host, or use the later PowerMaster+ path only on a platform listed by the vendor or after a dedicated real-system compatibility test.

## NUT (Network UPS Tools)

This is the primary path for a UPS connected by USB to the Proxmox VE node. It starts as a local-only configuration so no NUT control or monitoring interface is exposed to the LAN before normal communication and shutdown behavior have been verified.

### Install NUT and Detect the UPS

First confirm that Linux can see the hardware, then let NUT propose a driver. Do not guess a driver or continue when detection fails.

On the Proxmox VE node (**Node → Shell**), install the NUT metapackage and the USB inspection utility:

```sh
apt update
apt install -y nut usbutils
```

The Debian `nut` metapackage already installs `nut-server` and `nut-client`; listing all three packages is redundant.

Still on the Proxmox VE node (**Node → Shell**), inspect the USB device and request scanner output in `ups.conf` format:

```sh
lsusb
nut-scanner -U -N
```

`-U` limits discovery to USB and `-N` formats the result as a candidate `ups.conf` section. Scanner capabilities depend on the libraries included by the Debian package. Compare the proposed driver with its exact [NUT driver documentation](https://networkupstools.org/docs/man/index.html) and the hardware compatibility entry before using it.

Preserve a reported vendor ID, product ID, serial number, or bus identifier when it is needed to distinguish this UPS from another device. Do not blindly reduce every scanner result to only `driver` and `port = auto`. If `lsusb` does not show the expected hardware, or the scanner returns no suitable section, stop and resolve the cable, USB, permissions, model-support, or driver issue before continuing.

### Configure Standalone Mode

`MODE=standalone` starts all three local layers: the hardware driver, the loopback-only `upsd` data server, and the local `upsmon` shutdown controller. The following example uses the stable UPS name `ups`; use that identifier consistently in every file and command.

Before editing live power-management configuration, preserve a root-only copy. On the Proxmox VE node (**Node → Shell**), run:

```sh
nut_backup_dir="/root/nut-config-backup-$(date +%Y%m%d-%H%M%S)"
install -d -m 0700 "$nut_backup_dir"
cp -a /etc/nut/nut.conf /etc/nut/ups.conf /etc/nut/upsd.conf \
  /etc/nut/upsd.users /etc/nut/upsmon.conf "$nut_backup_dir"/
printf 'NUT backup: %s\n' "$nut_backup_dir"
unset nut_backup_dir
```

Edit `/etc/nut/nut.conf` and set the mode exactly as follows:

```ini
MODE=standalone
```

Edit `/etc/nut/ups.conf`. Replace `<UPS-DRIVER>` and any additional placeholder fields with the values verified from `nut-scanner` and the exact driver documentation:

```ini
[ups]
    driver = <UPS-DRIVER>
    port = auto
    desc = "Proxmox VE UPS"
```

Edit `/etc/nut/upsd.conf` so the standalone data server listens only on loopback:

```ini
LISTEN 127.0.0.1 3493
LISTEN ::1 3493
```

Create a strong, unique `<NUT-MONITOR-PASSWORD>` in a password manager. Enter it only in the two root-managed configuration files below; do not put it in a command argument, URL, screenshot, or ordinary setup notes.

Edit `/etc/nut/upsd.users`:

```ini
[upsmon]
    password = <NUT-MONITOR-PASSWORD>
    upsmon primary
```

Edit `/etc/nut/upsmon.conf` and use the same password:

```ini
MONITOR ups@localhost 1 upsmon <NUT-MONITOR-PASSWORD> primary
MINSUPPLIES 1
SHUTDOWNCMD "/sbin/shutdown -h +0"
POWERDOWNFLAG /etc/killpower
```

The `primary` role is appropriate because this `upsmon` instance runs on the host physically connected to the UPS. `MINSUPPLIES 1` describes the normal single-power-feed server. The `POWERDOWNFLAG` is consumed during late shutdown so a compatible driver can switch off the UPS load after the operating system is safely down.

Restrict the credential-bearing files. On the Proxmox VE node (**Node → Shell**), run:

```sh
chown root:nut /etc/nut/upsd.users /etc/nut/upsmon.conf
chmod 0640 /etc/nut/upsd.users /etc/nut/upsmon.conf
stat -c '%U:%G %a %n' /etc/nut/upsd.users /etc/nut/upsmon.conf
runuser -u nut -- test -r /etc/nut/upsd.users
runuser -u nut -- test ! -w /etc/nut/upsd.users
runuser -u nut -- test -r /etc/nut/upsmon.conf
runuser -u nut -- test ! -w /etc/nut/upsmon.conf
```

The expected ownership and mode are `root:nut 640`. The final four commands confirm that the NUT service account can read, but cannot modify, the two files.

### Start and Verify NUT

Activate the completed configuration once, then verify each layer before enabling any shutdown test.

On the Proxmox VE node (**Node → Shell**), run:

```sh
systemctl enable --now nut-server.service nut-monitor.service
systemctl is-enabled nut-server.service nut-monitor.service
systemctl is-active nut-server.service nut-monitor.service
upsdrvsvcctl list
upsc ups@localhost
ss -ltnp | grep -E '127\.0\.0\.1:3493|\[::1\]:3493'
```

Debian's NUT packaging manages each detected driver as a systemd service instance. `upsdrvsvcctl list` shows the device-to-service mapping. Replace `<NUT-DRIVER-UNIT>` below with the exact returned unit name, then verify that it is active and boot-enabled. On the Proxmox VE node (**Node → Shell**), run:

```sh
systemctl is-enabled "<NUT-DRIVER-UNIT>"
systemctl is-active "<NUT-DRIVER-UNIT>"
systemctl --no-pager --full status "<NUT-DRIVER-UNIT>"
journalctl -u "<NUT-DRIVER-UNIT>" --since '-10 minutes' --no-pager
```

In the `upsc` output, check at least:

- the detected manufacturer and model;
- `battery.charge`, `battery.runtime`, and load values where the UPS exposes them;
- a current, changing update rather than stale data; and
- `ups.status`, where `OL` normally means utility power is present and `OB` means the UPS is running on battery.

On the Proxmox VE node (**Node → Shell**), inspect focused status and recent logs:

```sh
systemctl --no-pager --full status nut-server.service nut-monitor.service
journalctl -u nut-server.service -u nut-monitor.service --since '-10 minutes' --no-pager
```

Also inspect the driver unit reported by `upsdrvsvcctl list`. Missing data, a stale driver, permission errors, an unexpected status, a service that is not boot-enabled, or a listener outside loopback is a blocker. Restore the saved configuration if the change cannot be corrected safely.

Before a NUT package upgrade, preserve `/etc/nut`, read the Debian and NUT release notes, and make sure current backups and console access exist. Afterward, repeat the service, listener, `upsc`, and journal checks before relying on automatic shutdown again.

### Configure Notifications (Optional)

NUT can call an external `NOTIFYCMD` only for events whose `NOTIFYFLAG` includes `EXEC`. Shutdown does not depend on that command, so an unavailable notification service must never prevent the host from powering off safely.

Without an independently reviewed notification helper, keep alerts local through the journal and logged-in terminal sessions. Add these lines to `/etc/nut/upsmon.conf`:

```ini
NOTIFYFLAG ONLINE SYSLOG+WALL
NOTIFYFLAG ONBATT SYSLOG+WALL
NOTIFYFLAG LOWBATT SYSLOG+WALL
NOTIFYFLAG COMMBAD SYSLOG+WALL
NOTIFYFLAG COMMOK SYSLOG+WALL
NOTIFYFLAG REPLBATT SYSLOG+WALL
```

`ONLINE` and `COMMOK` are recovery events; `ONBATT`, `LOWBATT`, `COMMBAD`, and `REPLBATT` report conditions that need attention. Reload only the monitor after saving the file. On the Proxmox VE node (**Node → Shell**), run:

```sh
upsmon -c reload
journalctl -u nut-monitor.service --since '-5 minutes' --no-pager
```

Do not embed a Gotify application token in `upsmon.conf`, a command line, a URL, or a log. A future Gotify integration must use a reviewed external helper, store its token in a root-owned file with restrictive permissions, use Gotify's supported authentication header, handle `NOTIFYTYPE` and `UPSNAME`, and pass a harmless test notification before `EXEC` is enabled. Until that exact helper is available and audited, this guide intentionally does not claim Gotify notification support for NUT.

### Test Automatic Shutdown Safely

Begin with read-only evidence. On the Proxmox VE node (**Node → Shell**), run:

```sh
upsc ups@localhost
grep -E '^(MONITOR|MINSUPPLIES|SHUTDOWNCMD|POWERDOWNFLAG)' /etc/nut/upsmon.conf
systemctl is-active nut-server.service nut-monitor.service
upsdrvsvcctl list
```

> [!CAUTION]
> `upsmon -c fsd` sets the forced-shutdown state and initiates the configured shutdown sequence. Never run it casually on an active Proxmox VE node and never describe it as a harmless status check. Even when a dummy `SHUTDOWNCMD` is deliberately used in a controlled test, the FSD state can remain latched until `upsd` is restarted and the configured `POWERDOWNFLAG` is safely cleared.

Only perform a shutdown test during a planned maintenance window with:

- a current verified backup;
- local console access and a documented recovery plan;
- no active backup, replication, scrub, resilver, migration, upgrade, or storage repair;
- enough measured battery reserve for the complete shutdown sequence; and
- the network switch and router needed by any protected secondary system connected to UPS power.

Before relying on host shutdown, review each VM and LXC container under its **Options → Start/Shutdown order** settings. Proxmox VE shuts guests down in reverse startup order and respects their shutdown timeouts. Use the normal host poweroff path; do not start snapshots, `vzdump` backups, replication, or other heavy I/O after a critical-battery event.

After the low-risk checks succeed, perform one controlled on-battery test using the UPS manufacturer's safe procedure. Verify the complete chain:

1. NUT changes from `OL` to `OB` and reports the event.
2. Configured local notifications occur without delaying shutdown.
3. When the tested critical threshold is reached, secondary systems shut down before the primary where applicable.
4. Proxmox VE stops its VMs and LXC containers cleanly in the configured reverse startup order.
5. The host powers off with battery reserve remaining.
6. The driver performs late UPS power-off only when the exact model supports and has been configured for it.
7. After utility power returns, the UPS and homelab recover according to the documented startup policy and the NUT services resume normal `OL` monitoring.

Do not treat successful `upsc` output, a dashboard, or a synthetic notification as proof that automatic shutdown works.

### Protect Additional Servers (Optional)

Standalone mode protects only the USB-connected Proxmox VE host. If a separate UPS-powered PBS system or another physical server must also shut down, convert the USB-connected machine to a restricted `netserver` and keep it as the NUT primary. Additional protected machines use `netclient` mode and secondary `upsmon` identities.

Keep this extension narrow:

- listen on the primary's named private address and allow TCP `3493` only from the exact secondary systems;
- create a dedicated least-privilege secondary monitoring identity rather than reusing the primary credential;
- keep the required switch and router powered for the whole shutdown window;
- configure enough `HOSTSYNC` time for every secondary to finish before the primary powers off the UPS; and
- perform an end-to-end shutdown-order test before relying on the topology.

Use the current NUT [`upsmon`](https://networkupstools.org/docs/man/upsmon.html), [`upsd.conf`](https://networkupstools.org/docs/man/upsd.conf.html), and [`upsd.users`](https://networkupstools.org/docs/man/upsd.users.html) documentation for the exact network configuration. Do not expose port `3493` broadly or grant remote control actions to an ordinary monitoring account.

If NUT is later replaced, first establish and test another power-protection path. Then disable its services, remove any TCP `3493` firewall rule, revoke monitoring credentials, and preserve a protected configuration copy until the replacement has passed a controlled outage test. Do not purge `/etc/nut` merely to troubleshoot a driver or permission error.

## PowerMaster+ (Conditional Alternative)

Use this path only when the exact UPS and host operating system appear on the current vendor support list. It is not the recommended installation for a Proxmox VE 9 node because that host runs Debian 13, which PowerMaster+ `1.2.3` does not officially list.

### Install PowerMaster+

Start with a hard compatibility gate. On the proposed PowerMaster+ Linux host (**Supported Linux host → Shell**), run:

```sh
cat /etc/os-release
uname -m
lsusb
```

Confirm all of the following before downloading anything:

- the UPS model supports PowerMaster+ through the intended USB, serial, or network method;
- the host is 64-bit and its exact distribution release appears in the [current PowerMaster+ download table](https://www.powermonitor.software/);
- the UPS appears through the intended local connection; and
- the selected **Local**, **Remote**, or PMCARD architecture matches the physical wiring.

Stop here when any condition fails. In particular, do not install the vendor binary directly on a Debian 13/PVE 9 host merely because an older Linux release worked.

PowerMaster+ currently publishes a `1.2.3` 64-bit Local/Remote archive at the official site, but the publisher does not provide a checksum or signature beside that download. Recheck the release, archive URL, supported operating systems, and the PowerMaster+ `1.2.3` Local/Remote manual at implementation time. Because the installer runs as `root` and includes its own runtime, download it only over the vendor's official HTTPS site.

On a vendor-supported PowerMaster+ Linux host (**Supported Linux host → Shell**), install the required utilities, download the current archive, and inspect it before execution:

```sh
apt update
apt install -y usbutils unzip
wget https://www.powermonitor.software/pmp/pmp123_linux64.zip
unzip -l pmp123_linux64.zip
unzip pmp123_linux64.zip
find . -maxdepth 1 -type f -name 'pmasterp*-linux-x86*.sh' -print
```

The expected `1.2.3` installer is `pmasterp123-linux-x86_x64.sh`. If the extracted name differs, return to the official download page and manual instead of changing a command until the new release has been reviewed.

Choose the component before launching the installer:

- **Local:** Only on the UPS-powered machine physically connected to the UPS by USB or serial.
- **Remote:** On another UPS-powered server that receives state and shutdown instructions over the protected network.
- **PMCARD design:** The card communicates with the UPS; protected computers normally use Remote.

On the supported PowerMaster+ Linux host (**Supported Linux host → Shell**), launch the documented text-mode installer:

```sh
chmod u+x ./pmasterp123-linux-x86_x64.sh
./pmasterp123-linux-x86_x64.sh -c
```

Use the installer prompts to select English or the preferred language, accept installation only after reviewing the destination, keep `/opt/PMasterP` unless a documented requirement justifies another path, select only the intended Local or Remote component, and finish the installation. Do not copy a historical transcript as an exact expected result; prompt wording can change between releases.

After installation, discover and verify the installed service rather than assuming an old unit name. On the supported PowerMaster+ Linux host (**Supported Linux host → Shell**), run:

```sh
systemctl list-unit-files --type=service | grep -i pmaster
systemctl --no-pager --full status pmasterpd.service
systemctl is-enabled pmasterpd.service
ss -lntup | grep -E ':(3052|53568)\b'
```

The `1.2.3` manual identifies `pmasterpd`; if the installed release exposes a different service, use the discovered unit consistently and revalidate its vendor documentation. From a browser on the trusted LAN, confirm the component's direct interface before continuing:

- Local: `http://<POWERMASTER-LOCAL-IP>:3052/local`
- Remote: `http://<POWERMASTER-REMOTE-IP>:3052/remote`

Do not continue if the service is inactive, not boot-enabled, listening on an unexpected interface, or showing the wrong component. Keep the archive and installer until this verification succeeds. Then remove only those two known installer files from the verified download directory; use the current vendor manual for uninstall or rollback rather than deleting `/opt/PMasterP` manually.

### Setup PowerMaster+

Secure the direct installation before enabling cross-system discovery, then connect the components, map the physical load, configure alerts and shutdown, perform a controlled test, and protect the validated configuration.

#### Secure the Management Interface

The first login temporarily uses plain HTTP from the trusted local management network. Never expose port `3052` to the public internet.

1. Open the direct Local or Remote URL from a trusted LAN client.
2. Sign in with the documented temporary username and password, `admin` / `admin`.
3. PowerMaster+ opens a password-change dialog, but that initial dialog does not expose **Login Connection Expiration**, so close the dialog.
4. Go to the **Change Password** area at the bottom of the page.
5. Replace the default password with a strong unique value stored in a password manager and set **Login Connection Expiration** to `1 day`, the shortest value provided by the reviewed interface.
6. Sign out and back in to verify both settings. Do not leave the default credential active or postpone this change.

Restrict direct management to the trusted LAN or approved VPN. Enable the application's HTTPS interface and verify `https://<POWERMASTER-HOST-IP>:53568/<COMPONENT>`, where `<COMPONENT>` is `local` or `remote`, before removing the known-working HTTP recovery path. The built-in self-signed certificate causes an expected browser warning; verify the destination before accepting it.

Importing a replacement certificate can interrupt communication because Local and Remote maintain certificate trust. Update that trust in a controlled sequence, retain console and direct LAN access, and verify Local/Remote communication after every certificate change.

#### Connect the Local and Remote Instances

PowerMaster+ uses a shared **Secret Phrase** to establish trusted application-to-application communication. Replace the vendor default with one strong unique phrase on every participating Local, Remote, and applicable PMCARD endpoint, store it in a password manager, and apply matching values in a controlled sequence. A mismatch prevents communication.

Allow only the traffic required by the selected design:

| Port | Protocol | Use |
| --- | --- | --- |
| `3052` | TCP and UDP | PowerMaster+ application communication and direct HTTP management documented for Local/Remote |
| `53568` | TCP | PowerMaster+ HTTPS management |
| `161` | UDP | SNMP polling only when a PMCARD/SNMP design requires it |
| `162` | UDP | SNMP traps only when that workflow is configured |
| `53566` | UDP | Vendor discovery only when the selected PMCARD or discovery workflow requires it |

Create source- and destination-specific rules between the named hosts. Do not open every vendor-listed port to the whole LAN. Keep the switch or router carrying Local-to-Remote traffic on protected UPS power.

Configure the narrowest **Auto-Discover Range** or an explicit address supported by the current interface. Wait for discovery, then verify each instance's role, address, identity, communication state, and UPS association before continuing.

#### Map and Verify Protected Equipment

Build the equipment inventory only after Local/Remote communication is stable:

1. Give each protected server an unambiguous role-based name.
2. Record its **Device Location** and responsible **Contact**.
3. Add it under **Connected Equipment** and record the physical UPS outlet or outlet group that actually powers it.
4. Confirm communication state, utility/battery state, load, charge, and estimated runtime where the model exposes them.
5. Trace the cable or switchable outlet physically before saving the mapping.

Outlet availability and control vary by UPS model. Do not tell every reader to choose outlet `2` or `3`. Assigning a Remote server to the wrong switchable or non-critical-load outlet can remove power before its shutdown finishes.

#### Configure Notifications and Reporting

Create a dedicated Gotify application only after the notification transport has a safe credential path. Gotify recommends authenticating message requests with the `X-Gotify-Key` header. The reviewed PowerMaster+ HTTP POST/SMS-provider form documents URL and POST-body fields but no protected custom-header field, so placing an application token in its URL or body risks exposing it through the interface, logs, exports, or screenshots.

Do not put a Gotify token into the native PowerMaster+ form. Use a local notification helper only after that exact helper has passed an independent secret-handling, syntax, dry-run, and event-mapping audit. Until then, configure only a vendor-supported notification method whose credentials can be protected and tested safely.

Select actionable events such as utility-power loss and restoration, critical battery, communication loss and recovery, and shutdown initiation. Treat occurrence and recovery as separate events, and send a harmless test before relying on any channel. Scheduled reports are optional; enable them only after the same delivery method has been proven and only when the report provides operational value.

#### Configure Shutdown Actions

Define the shutdown policy from measured behavior: trigger condition, delay, remaining-runtime or battery threshold, expected action duration, and reserve remaining when the host is off. A copied percentage is not a safety margin.

Prefer PowerMaster+'s normal operating-system shutdown action on the PVE host. Before enabling it, review every VM and LXC container under **Options → Start/Shutdown order** and its shutdown timeout. Proxmox VE then shuts guests down in reverse startup order as part of a normal host poweroff.

For a separate PBS system, configure Remote so that it shuts down while Local and the protected network path are still available. Do not test during an active PBS task. A bounded wait for active backup tasks requires a separately reviewed implementation; do not claim that a generic command hook provides it.

Do not start broad snapshots, `vzdump` jobs, replication, or other storage-heavy work after a critical-battery event. These operations consume the remaining shutdown window and belong in the regular backup strategy. Enable a custom event command only after the exact script is idempotent, fails closed on unknown or recovery events, uses bounded timeouts, keeps secrets out of arguments and logs, and has a no-write dry run that has passed independent review.

#### Test the Power-Failure Workflow

Begin with diagnostics that do not request shutdown. Run only the tests supported by the exact UPS:

- verify normal battery state, load, runtime, and connected-equipment mapping;
- send a harmless notification through the selected tested channel;
- confirm Local and every Remote remain connected;
- review event names and occurrence/recovery handling; and
- syntax-check and dry-run every custom script before enabling its event action.

Battery or runtime calibration can discharge the UPS. Do not start calibration during unstable utility power or important storage activity.

Then schedule one controlled outage test with current backups, local console access, no active backup, replication, scrub, resilver, or migration, enough battery reserve, and an explicit recovery plan. Verify that:

1. the power event is detected;
2. the tested notification channel reports both outage and recovery;
3. Remote systems shut down before they lose Local or network communication;
4. Proxmox VE stops guests cleanly in reverse startup order;
5. any separate PBS completes only its proven bounded handling;
6. Local powers off with battery reserve remaining; and
7. the environment returns according to the documented startup policy after utility power is restored.

Do not claim that the workflow works based only on the dashboard, one diagnostic, or a synthetic notification.

#### Export and Protect the Configuration

Export the PowerMaster+ configuration only after the selected workflow has passed validation. Use the current interface's documented export function, label the artifact with the component role and date, and store it outside the PVE/PBS host in a protected recovery location.

Treat the export as sensitive unless inspection of the current format proves that it excludes passwords, shared phrases, tokens, and other credentials. Record the tested shutdown timing, outlet mapping, component roles, event triggers, and recovery behavior beside it without copying secrets into plain-text notes.

Confirm that the exported artifact is readable. Test restoration only on a spare or isolated supported instance, or follow the current official recovery procedure; the existence of an export does not prove it can restore the configuration. Before a PowerMaster+ update, preserve the validated export, review vendor release notes and supported operating systems, update one component at a time, and repeat direct access, Local/Remote, notification, and shutdown checks. Remove firewall rules and revoke shared credentials when decommissioning a component.

### Configure HTTPS Access with Traefik

PowerMaster+ must work through its direct HTTPS interface before Traefik is added. This is an ordering exception: the first local login and internal HTTPS transition happen first so Traefik can use a known-working secured backend.

The private browser route does not replace Local/Remote communication and must not expose the UPS manager publicly. PowerMaster+ has its own login, and ForwardAuth compatibility has not been proven, so use the `secured` middleware rather than `secured-auth`.

Before changing a live route, preserve a known-good copy outside Traefik's watched directory. In the reverse proxy LXC (**LXC → Console**), run:

```sh
install -d -m 0700 /root/traefik-route-backup
test ! -e /TRAEFIK/config/dynamic/ups.yaml || \
  cp -a /TRAEFIK/config/dynamic/ups.yaml /root/traefik-route-backup/ups.yaml.before-change
```

From a trusted repository workstation (**PowerShell**), transfer the reviewed Local template to a staging path that Traefik does not watch:

```powershell
$source = "Application Library/Reverse Proxies/Traefik/Config files/Traefik/dynamic/ups.yaml"
scp $source root@192.168.0.102:/root/ups.yaml.pending
```

In the reverse proxy LXC (**LXC → Console**), edit `/root/ups.yaml.pending`. Replace `<MY-DOMAIN>` and `<POWERMASTER-LOCAL-IP>`, then install the reviewed file only when no placeholder remains:

```sh
nano /root/ups.yaml.pending
if grep -n '<[A-Z][A-Z-]*>' /root/ups.yaml.pending; then
  echo 'Replace every reported placeholder before installing this route.'
else
  install -m 0660 -o 1000 -g 1000 \
    /root/ups.yaml.pending /TRAEFIK/config/dynamic/ups.yaml
fi
```

The template creates `https://ups.<MY-DOMAIN>.com` and sends it to `https://<POWERMASTER-LOCAL-IP>:53568`. It uses the narrowly scoped `skipverify@file` transport for the application's self-signed backend certificate. Prefer a trusted backend certificate when one can be deployed without breaking Local/Remote trust.

If and only if a separate Remote host exists, create `/root/ups-remote.yaml.pending` outside Traefik's watched directory with the following complete configuration, replacing both placeholders:

```yaml
http:
  routers:
    ups-remote:
      entryPoints:
        - websecure
      rule: Host(`upsremote.<MY-DOMAIN>.com`)
      middlewares:
        - secured@file
      service: ups-remote

  services:
    ups-remote:
      loadBalancer:
        passHostHeader: true
        serversTransport: skipverify@file
        servers:
          - url: https://<POWERMASTER-REMOTE-IP>:53568
```

In the reverse proxy LXC (**LXC → Console**), check and install the optional route using the same fail-safe pattern:

```sh
if grep -n '<[A-Z][A-Z-]*>' /root/ups-remote.yaml.pending; then
  echo 'Replace every reported placeholder before installing this route.'
else
  install -m 0660 -o 1000 -g 1000 \
    /root/ups-remote.yaml.pending /TRAEFIK/config/dynamic/ups-remote.yaml
fi
```

After saving the route, Traefik's file provider hot-reloads it. In the reverse proxy LXC (**LXC → Console**), verify the direct backend and inspect focused logs:

```sh
curl -ksS -o /dev/null -w '%{http_code}\n' \
  "https://<POWERMASTER-LOCAL-IP>:53568/local"
docker logs --since 5m traefik 2>&1 | grep -Ei 'ups|error|middleware|router|service'
```

From a trusted LAN client, open `https://ups.<MY-DOMAIN>.com` and verify the correct PowerMaster+ login and component. If Remote was configured, test its hostname separately. Confirm that no router port forwarding or public DNS record exposes either route, and restore the known-good route if parsing or backend verification fails.
