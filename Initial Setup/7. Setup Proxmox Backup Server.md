# Proxmox Backup Server

Proxmox Backup Server adds deduplicated, integrity-checked backups to this homelab. This chapter installs PBS on separate hardware or, for learning and constrained environments, in an LXC container; it then connects PBS to Proxmox VE and proves the recovery workflow with a backup and an isolated restore.

## About Proxmox Backup Server

[Proxmox Backup Server](https://www.proxmox.com/en/products/proxmox-backup-server/overview) (PBS) is a free and open-source client-server backup platform optimized for Proxmox VE. It sends changed data incrementally, deduplicates and compresses stored chunks, verifies data integrity, and can encrypt backup content on the client before it reaches the server.

PBS protects virtual machines and LXC containers in this homelab. A dedicated PBS device provides the most useful recovery boundary because its operating system and backup disks remain available when the primary Proxmox VE node is offline. An LXC installation can teach the same interface and workflow, but it shares the node's hardware, storage, and maintenance failure domain.

## Before You Begin

Complete the earlier Proxmox VE, private DNS, Traefik, and Gotify chapters before following the complete setup path. Have a password manager ready for the PBS administrator password, API-token secrets, and any client-side encryption key.

Choose one PBS deployment and reserve its planned network values before installation:

| Deployment | System identity | Management address | Intended use |
| --- | --- | --- | --- |
| Dedicated hardware | `proxmox-backup-server.local` | `192.168.0.15/24` | Recommended backup and recovery system |
| LXC container | CT `200`, hostname `proxmox-backup-server` | `192.168.0.200/24` | Learning, testing, or constrained hardware |

Both examples use `192.168.0.1` as the gateway and initial DNS resolver. Replace any value that conflicts with your documented network, and confirm that the selected address and CT ID are unused. The private browser name remains `pbs.<MY-DOMAIN>.com`; it is a Traefik route, not the dedicated server's installation hostname.

For dedicated hardware, review the current [PBS system requirements](https://pbs.proxmox.com/docs/installation.html#system-requirements) and plan separate operating-system and backup-datastore storage. For the LXC path, confirm that the PVE node has enough capacity for the container and test backups without consuming space required by running workloads.

## Install Proxmox Backup Server

This chapter supports two deployment paths. Installing PBS on a separate physical device is recommended whenever hardware and budget allow because a failure, reinstall, or storage problem on the primary PVE node does not take its recovery system down with it. The same-node LXC path is convenient for learning and testing, but it is not equivalent protection and should not be treated as the only copy of important data.

### Install PBS on Dedicated Hardware (Recommended)

The dedicated path follows the same familiar phases as the earlier PVE installation: verify the official image, create a bootable USB drive, complete the installer screen by screen, and establish direct management access before adding private HTTPS routing.

#### Prepare the Installation USB

Verify the official installer image before writing it to removable media so a damaged or substituted download never reaches the PBS device.

1. Download the newest supported ISO from the official [PBS ISO download page](https://www.proxmox.com/en/downloads/proxmox-backup-server/iso). At the August 2026 validation of this guide, the current image is **Proxmox Backup Server 4.2 ISO Installer**, version `4.2-1`; use a newer supported image and its matching checksum if the official page has changed.
2. On a Windows personal device, open PowerShell in the download directory and calculate the ISO's SHA-256 hash. Replace `<VERSION>` with the downloaded filename's version:

   ```powershell
   Get-FileHash -Algorithm SHA256 -LiteralPath '.\proxmox-backup-server_<VERSION>.iso'
   ```

3. Compare every character in the **Hash** result with the **SHA256SUM** published beside that exact ISO. Delete and download the image again if they differ; do not write an unverified image to installation media.
4. Prepare a USB flash drive with at least `2 GB` of capacity and download [Rufus](https://rufus.ie/) from its official site.
5. Open Rufus and select:
   - **Device:** The intended USB flash drive.
   - **Boot selection:** The verified PBS ISO.
6. Click **START**. If Rufus offers to download another GRUB version, choose **No** as directed by the PBS documentation. Select **Write in DD Image mode** when prompted.
7. An ISOHybrid or enforced-DD message is expected for this image and does not mean the ISO is damaged. Reconfirm the destination drive, accept the erase warning, and wait for Rufus to report **READY** before ejecting the USB drive.

![Rufus bootable USB creation screenshot](../.assets/img/rufus-usb-creation-screenshot.jpg)

The official [installation-media documentation](https://pbs.proxmox.com/docs/installation.html#installation-medium) also provides current Linux, macOS, and Etcher procedures. Do not use UNetbootin for the PBS image.

#### Install PBS from the USB Drive

The PBS installer configures the operating system. The backup datastore is created later, so positively distinguish the smaller OS disk from the separate disk intended to hold backups.

1. Connect a monitor and keyboard to the PBS device. When practical, disconnect any unrelated or data-bearing disks; leave only the intended PBS OS disk attached until the installation is complete.
2. Insert the USB drive, open the firmware boot menu, and boot from it.
   - Current PBS installation media support Secure Boot. Leave it enabled; disable it only after a verified boot or signature failure, or when deliberately using media older than PBS `3.1`.
   - Do not enable CPU virtualization merely for PBS. It is a backup server, not the PVE hypervisor.
3. Select **Install Proxmox Backup Server (Graphical)**. If the graphical installer has a display or driver problem, use **Install Proxmox Backup Server (Console)** as the compatibility fallback. The serial-console and debug entries are for hardware or recovery cases that specifically require them.
4. Complete the installer screens in order:
   - **EULA:** Read and accept the license agreement.
   - **Target Harddisk:** Select only the PBS operating-system disk.

     > **Warning:** Installation erases all data on every selected target disk. Recheck the disk model, capacity, and purpose before continuing.

   - **Options:** Use the default `ext4` filesystem for the OS disk described here. `xfs` is also supported. Select ZFS only after planning suitable disks, memory, and redundancy; ZFS on top of hardware RAID is unsupported.
   - **Location and Time Zone:** Select the correct country, time zone, and keyboard layout.
   - **Administration Password and Email Address:** Set a strong, unique `root` password and an email address that can receive administrative notifications.
   - **Management Network Configuration:**
     - **Management Interface:** Select the connected wired interface.
     - **Hostname:** `proxmox-backup-server.local`
     - **IP Address:** `192.168.0.15/24`
     - **Gateway:** `192.168.0.1`
     - **DNS Server:** `192.168.0.1`
   - **Summary:** Recheck the target disk, hostname, address, CIDR prefix, gateway, DNS resolver, locale, and time zone. Return to an earlier screen if anything is incorrect, and then click **Install**.
5. When installation finishes, remove the USB drive and reboot. Wait for the local PBS console to show the expected management address; the monitor and keyboard can then be disconnected if reliable remote and recovery access are available.
6. From a personal device on the trusted LAN, open `https://<PBS-IP-ADDRESS>:8007`; the reference URL is `https://192.168.0.15:8007`.
   - A browser warning is expected because a new PBS installation uses a self-signed certificate. Verify that the address is the one just configured, then use the browser's advanced option to continue.
   - Keep direct port `8007` access private to the trusted LAN or approved VPN. It is the installation and recovery path, not a reason to publish PBS to the Internet.
7. Sign in with:
   - **User name:** `root@pam`
   - **Realm:** `Linux PAM standard authentication` when the interface shows a separate realm selector.
   - **Password:** The installation password.

For more detail or changed installer behavior, use the current official [PBS installer documentation](https://pbs.proxmox.com/docs/using-the-installer.html).

> **Optional — UPS-protected dedicated PBS:** If this separate device is powered by a compatible UPS, it can participate in coordinated shutdown. The documented NUT design uses the USB-connected PVE host as the restricted primary and the dedicated PBS system as a secondary; PowerMaster+ Local/Remote remains an alternative only on vendor-supported platforms. Follow [Setup UPS Software](<8. Setup UPS Software.md>) for the complete topology, timing, and test requirements rather than duplicating them here.

### Install PBS in an LXC Container

This community-supported path runs PBS inside an unprivileged LXC on the existing PVE node. It is useful for evaluation, but losing or reinstalling that node can remove both the workloads and their only PBS instance. Keep an independent copy elsewhere before relying on it for important recovery.

#### Setup LXC

Create the PBS LXC by running the current [Community Scripts PBS helper](https://community-scripts.org/scripts/proxmox-backup-server) command on the Proxmox node (**Node → Shell**). This third-party root-level script creates the Debian-based LXC and installs PBS, so review its current [`proxmox-backup-server.sh` source](https://github.com/community-scripts/ProxmoxVE/blob/main/ct/proxmox-backup-server.sh) and the sourced framework before every run.

```sh
mode=generated var_unprivileged=1 var_nesting=1 var_keyctl=0 var_tun=no var_fuse=no var_mknod=0 var_ctid=200 var_hostname=proxmox-backup-server var_cpu=2 var_ram=2048 var_disk=50 var_brg=vmbr0 var_net=192.168.0.200/24 var_gateway=192.168.0.1 var_tags=essential var_protection=yes bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/proxmox-backup-server.sh)"
```

Use these settings as the acceptance baseline:

| Setting | Reference value |
| --- | --- |
| Container type | Unprivileged |
| Container ID | `200` |
| Hostname | `proxmox-backup-server` |
| Disk size | 50 GiB |
| CPU cores | 2 |
| RAM | 2048 MiB |
| Network bridge | `vmbr0` |
| IPv4 configuration | Static: `192.168.0.200/24`; gateway: `192.168.0.1` |
| Container tag | `essential` |
| Nesting | Enabled |
| Keyctl | Disabled |
| TUN/TAP | Disabled |
| FUSE | Disabled |
| Device-node creation | Disabled |
| Container protection | Enabled |

Nesting remains enabled for the helper's modern Debian/systemd compatibility; device passthrough is not required for PBS. The `2` CPU cores and `2048` MiB RAM match the official evaluation minimum, not production sizing. The `50` GiB virtual disk is only a small learning or test datastore; increase it deliberately for the data and retention policy you intend to keep. PVE deletion protection reduces accidental removal, but it is not a backup and does not create a separate failure domain.

The helper script must finish successfully. Then verify the LXC's settings from the UI or the Proxmox node (**Node → Shell**):

```sh
pct status 200
pct config 200
```

Confirm that the LXC is running, is unprivileged and protected, uses the intended resources, static address, and bridge, and has nesting as its only enabled feature. Verify its start-at-boot behavior and investigate any mismatch before storing backups.

Open the PBS LXC (**LXC → Console**) and set the PBS `root` password through the hidden prompts:

```sh
passwd root
```

In the same console, verify the hostname, address, time synchronization, and installed services:

```sh
hostnamectl
ip -brief address show dev eth0
timedatectl status
systemctl is-active proxmox-backup proxmox-backup-proxy
```

The intended hostname and static address must be present, the clock must be synchronized, and both service results must report `active`.

Open `https://192.168.0.200:8007` from a trusted client, accept only the expected self-signed-certificate warning for that address, and sign in as `root@pam` with the password just set.

The LXC's root disk will hold `/backup/pve-backups` later unless you intentionally add a separate storage-backed mount point. That default still consumes PVE storage and must not be mistaken for an independent backup disk.

### Configure HTTPS Access with Traefik

Both installation paths now converge on the same private browser route. Direct `https://<PBS-IP-ADDRESS>:8007` access remains available from the trusted LAN for installation and recovery; normal browser access uses Traefik at `https://pbs.<MY-DOMAIN>.com` and still requires the PBS login.

The reverse-proxy chapter already installs the repository's [`proxmox-backup-server.yaml`](../TODO.md) route. In Code-Server, open `/TRAEFIK/config/dynamic/proxmox-backup-server.yaml`, record its current backend, and confirm exactly one matching value:

| PBS deployment | Expected backend URL |
| --- | --- |
| Dedicated hardware | `https://192.168.0.15:8007` |
| LXC container | `https://192.168.0.200:8007` |

Change only the backend line when using the LXC or a different documented address. Traefik watches the file, so an unrelated stack restart is unnecessary. The route's `serversTransport: skipverify@file` allows Traefik to reach PBS's self-signed backend on the private LAN; the client-facing wildcard certificate still protects the browser connection. Replace this trust exception with a verified backend certificate if your design later provides one.

After saving, open `https://pbs.<MY-DOMAIN>.com` from a normal trusted-LAN client and sign in to PBS. Confirm that private DNS resolves the hostname to the Traefik LXC, the browser trusts the client-facing certificate, and the PBS dashboard loads. Public DNS and router port forwarding must not expose the route. If it fails, first prove the direct port `8007` URL still works, review the Traefik provider logs for the `pbs` router, and restore the recorded backend line before making another change. Use [Add a Service to Traefik](../TODO.md) when adding or rebuilding a route rather than auditing this preinstalled one.

## Setup Proxmox Backup Server

Both installation paths use the same configuration workflow from here: finish the PBS host setup, prepare its datastore, define retention and integrity checks, create limited PVE credentials, connect the systems, and prove backup and recovery. The final step preserves the information needed to rebuild PBS itself.

### Complete the Initial Configuration

First configure the correct package repositories and install current PBS updates. This workflow uses the Community Scripts **PBS Post Install** helper for a homelab without a paid subscription.

The helper is a trusted but third-party convenience script with unrestricted `root` access. Review the [Community Scripts project](https://community-scripts.org/) and the exact current [`post-pbs-install.sh` source](https://github.com/community-scripts/ProxmoxVE/blob/main/tools/pve/post-pbs-install.sh) before running it. Its current source handles PBS `3` on Debian Bookworm and PBS `4` on Debian Trixie, can correct Debian sources, manages Enterprise and no-subscription entries, keeps the test repository disabled, optionally suppresses the subscription notice, upgrades packages, and offers a reboot. Those behaviors can change with the project's `main` branch.

> **Important:** Run the command in the PBS system itself, never in **Node → Shell** on the PVE host. For dedicated hardware, use **Administration → Shell** in PBS, a local console, or a trusted SSH session. For PBS in LXC, select CT `200` in PVE and use **LXC → Console**.

Keep console access available. Confirm that no backup, verification, prune, garbage-collection, or storage task is running, and expect the selected upgrade or final prompt to reboot PBS. Then run:

```sh
bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/tools/pve/post-pbs-install.sh)"
```

Read every prompt and use these recommended decisions only when they fit your environment:

- **Correct Debian sources:** Choose **Yes** for an unmodified installation that follows this guide. Preserve intentionally customized mirrors or proxy configuration until you have reviewed the proposed change.
- **Enterprise repository:** Without a paid PBS subscription, disable the Enterprise entry. With a valid subscription, stop following the no-subscription answers, keep Enterprise enabled, and use the official [PBS repository documentation](https://pbs.proxmox.com/docs/installation.html#debian-package-repositories).
- **No-subscription repository:** Keep it enabled for this no-subscription homelab. The current helper ensures that it exists, so do not add a duplicate manually. Proxmox describes it as a public, less-tested channel for non-production use.
- **Test repository:** Keep `pbs-test` disabled unless this server is deliberately testing prerelease packages with its own rollback plan.
- **Subscription notice:** Suppression is optional and cosmetic. Choose **No** to leave installed web-interface files unchanged; hiding the notice does not improve security, support status, or backup behavior.
- **Upgrade:** Review the package summary, then update only when the datastore is idle and recovery access is ready.
- **Reboot:** Reboot when the helper or updated packages require it, after confirming that no storage operation is active.

After PBS returns:

1. Reconnect through the direct management URL and open **Administration → Server Status**. Confirm the expected hostname, running version, time, CPU, memory, and root-filesystem state.
2. Open **Administration → Repositories**. Confirm that the repository matching the subscription status is enabled, inaccessible Enterprise entries are disabled, and `pbs-test` remains disabled.
3. Open **Administration → Updates**, click **Refresh**, and confirm that the task completes without repository errors. Review and install any remaining intended updates.
4. Open **Administration → Services** and confirm that `proxmox-backup` and `proxmox-backup-proxy` are running. Leave other service states unchanged unless the official documentation gives a specific reason.
5. Open **Administration → Tasks** and confirm that the update tasks finished with **OK**. A successful script exit alone is not the verification.

Now tour the interface in sidebar order and confirm only the baseline settings needed before datastore creation:

- **Dashboard:** Review the server version, datastore status area, task summary, and subscription state. No datastore appears until the next subsection creates one.
- **Notes:** Optionally record a non-secret purpose or recovery contact. Do not place passwords, tokens, or encryption keys here.
- **Configuration → Network/Time:** Check **Time**, **DNS**, and **Network Interfaces** for the expected time zone, synchronized clock, resolver, hostname, static address, gateway, and link state. Under **Other**, configure an HTTP proxy only if the network requires one; Gotify targets also honor this setting.
- **Configuration → Access Control:** This manages users, API tokens, permissions, realms, and two-factor authentication. Keep `root@pam` for administration; a later subsection creates a limited machine identity for PVE.
- **Configuration → Remotes:** A Remote represents another PBS used by synchronization. Leave the **Remotes** tab empty for the local baseline. In PBS 4.2, the adjacent **S3 Endpoints** tab defines object-storage endpoints for deliberately planned S3-backed datastores; it is not used by the local datastore created here.
- **Configuration → Traffic Control:** Bandwidth rules are optional. Leave them empty unless measured backup traffic needs a defined limit.
- **Configuration → Certificates:** The generated certificate is sufficient for the private direct backend. Traefik supplies the normal browser certificate; do not delete the PBS certificate.
- **Configuration → Encryption Keys:** Where this release exposes the shared key-management view, it supports planned sync and tape workflows. Tape deployments also expose **Tape Backup → Encryption Keys**. Both are separate from the optional PVE client key configured later.
- **Configuration → Notifications:** PBS notification targets and matchers are configured after maintenance jobs exist. Do not assume the installation email alone proves Gotify delivery.
- **Configuration → Subscription:** Upload and verify a key only if you have a paid subscription. A no-subscription homelab needs no key after its repository is configured.
- **Administration → Server Status and Shell:** Server Status is the host overview; **Shell** is a privileged console. Use the shell only for commands explicitly assigned to the PBS system.
- **Administration → Services, Updates, Repositories, Syslog, and Tasks:** The first three were checked above. **Syslog** and **Tasks** are the first places to inspect when an operation fails; open the task log rather than relying on a colored status alone.
- **Administration → Storage / Disks:** **Disks**, **Directory**, and **ZFS** manage physical storage. During this tour, inspect only disk identity, capacity, and health. Initialization, formatting, directory removal, and pool creation are destructive and belong in the next procedure.
- **Tape Backup:** Tape libraries, media pools, jobs, and tape encryption are hardware-specific advanced features. Leave this area unconfigured unless tape is part of a separately designed recovery plan.
- **Datastore:** This will contain the `pve-backups` datastore, its snapshots, maintenance jobs, permissions, and task history after the next step.

Fix an incorrect hostname, address, DNS resolver, time zone, repository error, failed essential service, or recurring critical log entry before modifying backup disks.

### Create a Datastore

A datastore is the managed directory where PBS stores backup indexes and deduplicated chunks. The dedicated and LXC paths use different backing storage, so follow only the matching procedure.

**Dedicated hardware**

1. Open **Administration → Storage / Disks → Disks** and identify the intended unused backup disk by model, serial number, capacity, device path, and health information. Cross-check the physical label or hardware inventory. It must not be the PBS OS disk or a disk containing data you need.
2. For this simple single-disk path, open **Administration → Storage / Disks → Directory** and click **Create: Directory**. Enter:
   - **Disk:** The positively identified unused backup disk.
   - **Filesystem:** `ext4`; `xfs` is also supported.
   - **Name:** `pve-backups`
   - **Add as Datastore:** `No`, so the datastore addition remains an explicit, reviewable step below.

   > **Warning:** Clicking **Create** initializes and formats the selected disk, permanently erasing its contents. Recheck its model, serial number, capacity, and device path immediately before proceeding.

3. Click **Create**, wait for the task to finish with **OK**, and confirm that **Directory** shows `/mnt/datastore/pve-backups` on the intended device.
4. Select **Datastore → Add Datastore** and enter:
   - **Name:** `pve-backups`
   - **Backing Path:** `/mnt/datastore/pve-backups`
   - **GC Schedule:** `none` for now.
   - **Prune Schedule:** `none` for now.
   - **Comment:** `Primary PVE backup datastore`

ZFS is a deliberate alternative for suitable multi-disk hardware, not an automatic upgrade for a single disk. Plan its memory, topology, replacement process, and redundancy first; do not place ZFS on hardware RAID. See the official [PBS storage documentation](https://pbs.proxmox.com/docs/storage.html) for ZFS, namespaces, multiple datastores, and resilient layouts.

**PBS in LXC**

This path places the datastore inside CT `200`'s virtual disk. It shares PVE capacity and the primary node's failure domain; protection on the LXC and filesystem or RAID redundancy below it do not make this an independent copy.

1. In CT `200` (**LXC → Console**), create only the required directory with ownership for the PBS service account:

   ```sh
   install -d -o backup -g backup -m 0750 /backup/pve-backups
   stat -c '%U:%G %a %n' /backup/pve-backups
   ```

   Expect `backup:backup 750 /backup/pve-backups`. Do not recursively change ownership above this dedicated empty path.
2. In PBS, select **Datastore → Add Datastore** and enter:
   - **Name:** `pve-backups`
   - **Backing Path:** `/backup/pve-backups`
   - **GC Schedule:** `none` for now.
   - **Prune Schedule:** `none` for now.
   - **Comment:** `Learning datastore on PBS LXC virtual disk`

If you intentionally created a separate storage-backed LXC mount point, use its documented path instead and verify its ownership, capacity, backup flag, and recovery behavior. Never let two running PBS instances manage the same datastore concurrently, and never nest one datastore inside another. Reusing an existing datastore on a replacement PBS is a recovery workflow: stop the old instance and follow the current official import or reuse procedure.

**Verify either path**

Open **Datastore → pve-backups → Summary**. Confirm that the datastore is available, its total capacity matches the intended backing storage, and no error or maintenance state is shown. Review the creation task log for **OK**. Storage redundancy can improve availability, but it does not replace an independent second or off-site copy.

### Configure Retention and Verification

Retention decides which snapshots remain available. Pruning removes snapshots selected for deletion; garbage collection (GC) later reclaims chunks no retained snapshot uses. Verification reads stored data and checks it against the backup manifest, so it detects corruption but does not prove that an application can be restored correctly.

1. Open **Datastore → pve-backups → Prune & GC Jobs**, find **Prune Jobs**, and click **Add**. Use this example only as a starting point:
   - **Datastore:** `pve-backups`
   - **Prune Schedule:** `04:00`
   - **Keep Last:** `3`
   - **Keep Daily:** `7`
   - **Keep Weekly:** `4`
   - **Keep Monthly:** `6`
   - **Keep Yearly:** `1`
   - **Enabled:** `Yes`

   Each bucket selects snapshots for a different time interval, and one snapshot can satisfy more than one bucket; the values are not a simple total. Model your actual backup times with the official [PBS Prune Simulator](https://pbs.proxmox.com/docs/prune-simulator/) before relying on the policy. Size it from backup frequency, usable capacity, and the recovery history you need.
2. In **Garbage Collect Jobs**, configure:
   - **GC Schedule:** `sun 05:00`

   Weekly GC is a reasonable starting point. PBS intentionally protects chunks newer than its safety cutoff, so newly unreferenced chunks can remain listed as pending removals until a later GC run. Do not delete chunk files manually.
3. Open **Datastore → pve-backups → Verify Jobs** and click **Add**. Configure:
   - **Local Datastore:** `pve-backups`
   - **Schedule:** `06:00`
   - **Skip Verified:** `Yes`
   - **Re-Verify After:** `30` days
   - **Comment:** `Verify new backups and recheck older data monthly`

   This checks new or outdated snapshots frequently and forces older data back into the verification cycle at least monthly. A large or slow datastore may need a less frequent non-overlapping schedule, but it should still meet the monthly re-verification goal.
4. Leave PVE-side retention at **Keep all backups** later in this chapter. PBS is the single retention authority, which matches the limited client role and prevents two systems from pruning with different rules. Protected PBS snapshots remain retained until their protection is removed deliberately.
5. Do not run a destructive prune against an empty or newly populated recovery history merely to test the button. Confirm the job rows, schedules, and **Next Run** values now. After the first backup, the next subsection on verification tells you how to run a safe manual check; after multiple known-good backups exist, preview the prune selection, run the job in a maintenance window, and inspect **Show Log** for **OK**.

Keep the `02:00` backup, `04:00` prune, Sunday `05:00` GC, and `06:00` verification windows non-overlapping, adjusting them to measured task duration. See the official [PBS maintenance documentation](https://pbs.proxmox.com/docs/maintenance.html) for pruning, the GC grace period, protected snapshots, and verification policy.

### Connect PBS to Gotify

PBS emits its own datastore-maintenance and system events. PVE remains responsible for PVE-side backup-job notifications, so this target complements rather than replaces the PVE Gotify connection from the notification chapter.

1. Open `https://gotify.<MY-DOMAIN>.com`, sign in, and create a Gotify application named `Proxmox Backup Server`. Gotify `3` shows an application token only when it is created or rotated, so copy it directly to a password manager.
2. In PBS, open **Configuration → Notifications → Notification Targets**, click **Add → Gotify**, and enter:
   - **Endpoint Name:** `gotify-pbs`
   - **Enable:** `Yes`
   - **Server URL:** `https://gotify.<MY-DOMAIN>.com`
   - **API Token:** The dedicated PBS application token.
   - **Comment:** `Actionable PBS maintenance and system alerts`

   Keep the token out of screenshots, notes, shell history, and repository files. PBS stores target secrets separately with root-only permissions.
3. Select `gotify-pbs`, click **Test**, confirm the PBS success dialog, and verify that the message appears under the correct Gotify application and reaches the intended client.
4. Under **Notification Matchers**, click **Add** and configure:
   - **Matcher Name:** `pbs-actionable`
   - **Enable:** `Yes`
   - **Match Rules → Match Severity:** `warning`, `error`, and `unknown`
   - **Targets to notify:** `gotify-pbs`

   Excluding routine `info` and `notice` events reduces success noise while retaining failed prune, garbage-collection, verification, sync, certificate, and relevant system-mail events. A target alone does not receive operational events: a matcher must route matching events to it. The target **Test** verifies transport and credentials, not every matcher condition.
5. After scheduled maintenance begins, verify that real actionable events arrive without a flood of successful-task messages. If the test or later delivery fails, check private DNS and HTTPS reachability from PBS, certificate trust, the complete server URL, token validity, target enablement, matcher severities, **Targets to notify**, the PBS task or Syslog entry, and Gotify logs.

See the official [PBS notifications documentation](https://pbs.proxmox.com/docs/notifications.html) and [Gotify push-message documentation](https://gotify.net/docs/pushmsg) for current event and token behavior.

### Create Proxmox VE Credentials

PVE needs a non-interactive PBS identity, but routine backups must not use unrestricted `root@pam`. The `DatastoreBackup` role lets the machine account back up and restore its owned groups without granting pruning or arbitrary deletion.

1. Open **Configuration → Access Control → User Management**, click **Add**, and enter:
   - **User name:** `pve-backup`
   - **Realm:** `Proxmox Backup authentication server`
   - **Enabled:** `Yes`
   - **Expire:** Leave unset for this unattended account.
   - **Comment:** `Machine account for Proxmox VE backups`

   The complete user ID is `pve-backup@pbs`. Leaving expiry unset avoids an unexpected scheduled-backup outage; set a reviewed expiry only when monitoring and a pre-expiry rotation process are in place.
2. Open **API Token**, click **Add**, and enter:
   - **User:** `pve-backup@pbs`
   - **Token Name:** `pve`
   - **Enabled:** `Yes`
   - **Expire:** Leave unset under the same monitored rotation policy.
   - **Comment:** `PVE storage integration`

   > **Warning:** The token secret is displayed only once. Copy the complete token ID `pve-backup@pbs!pve` and secret directly into a password manager. Never commit the secret to this repository or ordinary notes.

3. Open **Permissions**, click **Add → User Permission**, and enter:
   - **Path:** `/datastore/pve-backups`
   - **User:** `pve-backup@pbs`
   - **Role:** `DatastoreBackup`
   - **Propagate:** `Yes`
4. Click **Add → API Token Permission** and enter:
   - **Path:** `/datastore/pve-backups`
   - **API Token:** `pve-backup@pbs!pve`
   - **Role:** `DatastoreBackup`
   - **Propagate:** `Yes`
5. Select both the user and token in their respective tabs and use **Show Permissions**. Confirm the same datastore scope and role. A token's effective privileges are the intersection of its ACLs and its parent user's ACLs, so granting only one side is insufficient.

Review this machine credential at least annually and immediately after suspected exposure. To rotate it without a blind outage, create a differently named replacement token, grant the same ACL, update and test the PVE storage with the new full token ID and secret, then revoke the old token. See the official [PBS user-management documentation](https://pbs.proxmox.com/docs/user-management.html) for roles, ACLs, and token semantics.

### Add PBS to Proxmox VE

Register the datastore as PVE storage through its direct private address. PVE verifies the self-signed PBS endpoint with its SHA-256 certificate fingerprint; the browser-facing Traefik route is not used for backup traffic.

1. Obtain the fingerprint through a trusted local PBS path:
   - **Dedicated PBS:** Open **Administration → Shell** in PBS, or use its local console or trusted SSH session.
   - **PBS in LXC:** Open CT `200` from PVE and use **LXC → Console**.

   Run:

   ```sh
   proxmox-backup-manager cert info
   ```

   The fingerprint is also shown on the PBS dashboard. Compare the complete SHA-256 value between the trusted direct session and the value you enter; do not accept a fingerprint obtained only through an unverified connection.
2. In PVE, open **Datacenter → Storage**, click **Add → Proxmox Backup Server**, and complete **General**:
   - **ID:** `pbs`
   - **Server:** `192.168.0.15` for dedicated PBS, or `192.168.0.200` for the LXC described here.
   - **Username:** `pve-backup@pbs!pve`
   - **Password:** The one-time API token secret. The generic field label says **Password**, but this value is the token secret, not the PBS user's password.
   - **Datastore:** `pve-backups`
   - **Namespace:** Leave empty to use the root namespace.
   - **Fingerprint:** The verified SHA-256 fingerprint.
   - **Content:** `Backup`
   - **Nodes:** `All (No restrictions)` for this single-node setup.
   - **Enable:** `Yes`
3. Open **Backup Retention** in the same dialog and enable **Keep all backups**. Do not duplicate the PBS retention policy in PVE.
4. Save the storage. Confirm that `pbs` is enabled under **Datacenter → Storage**, then open the node's `pbs` storage view and confirm that its backup content can be listed without authentication, fingerprint, datastore, or network errors.

If the storage is unavailable, recheck direct PBS reachability, the selected deployment address, full token ID, token secret, fingerprint, datastore name, both ACL entries, firewall policy, and PBS task log before changing trust settings.

### Configure Client-Side Encryption (Optional)

PVE can encrypt chunks with AES-256-GCM before sending them to PBS. This protects backup content from a server that must not see plaintext, but it adds a separate key-recovery dependency. Choose it from your threat model rather than enabling it automatically for a trusted local PBS.

- **No client-side encryption:** Edit **Datacenter → Storage → pbs**, open **Encryption**, and keep **Do not encrypt backups**. TLS still protects data in transit, and PBS still checks stored data integrity. This is a valid local design when PBS and its administrators are trusted.
- **Enable client-side encryption:** In the same **Encryption** tab, choose **Auto-generate a client encryption key**, or upload an existing key only when its origin and recovery copies are already understood.

If encryption is enabled:

1. When PVE opens **Important: Save your Encryption Key**, immediately use **Copy Key** or **Download** and store a recoverable copy in a password manager plus an encrypted offline location outside both PVE and PBS. Printing a paper key for a physically secured recovery file is another supported option.
2. PVE keeps the operational key for storage ID `pbs` at `/etc/pve/priv/storage/pbs.enc`, restricted to `root`. That local file is not an independent recovery copy.
3. Reopen the **Encryption** tab and record the displayed key fingerprint with the recovery material. Confirm that the independently stored key can be opened and is labeled for this PBS storage before creating backups.

> **Warning:** If every copy of the client key is lost, backups encrypted with it cannot be restored. Deleting or replacing the PVE storage key also breaks restores of backups created with the old key.

Encrypted chunks still deduplicate when the same content uses the same key. Content encrypted with different keys produces different chunk identifiers and does not deduplicate across those keys. An optional master-public-key design can attach a recoverable encrypted copy of the client key to each backup; treat that as an advanced recovery project and follow the official [PBS encryption and master-key documentation](https://pbs.proxmox.com/docs/backup-client.html#encryption).

### Create a Backup Job

PVE schedules guest backups; PBS owns retention, garbage collection, and verification. Keep those windows separate so the primary node and datastore are not competing for storage and network I/O.

1. In PVE, open **Datacenter → Backup** and click **Add**. Configure **General**:
   - **Node:** The PVE node used in this guide, or **All** only when every selected node can reach this PBS storage.
   - **Storage:** `pbs`
   - **Schedule:** `02:00`, adjusted to a quiet non-overlapping window.
   - **Selection mode:** **Include selected VMs** and select the intended guests, or use a deliberate pool/all selection after reviewing exclusions.
   - **Compression:** `ZSTD`. Current PVE selects and locks this value for PBS storage; it is not an extra compression choice copied from a traditional file-based `vzdump` target.
   - **Mode:** `Snapshot`
   - **Enable:** `Yes`
   - **Job Comment:** `Daily guests to PBS`
2. Open **Retention** and enable **Keep all backups** so the PBS prune job remains the only retention authority.
3. Review **Notifications** against the PVE Gotify matcher configured earlier. PVE-side backup failures must reach that existing route; the PBS matcher covers PBS-side maintenance and system events.

> **Warning — PBS in LXC:** If PBS is CT `200` and `/backup/pve-backups` is inside that same container, exclude CT `200` from this job. Backing the PBS LXC into its own datastore creates recursive capacity growth and still shares the node failure domain. Protect the PBS configuration separately as described later.

Before saving, audit what each guest backup actually contains:

- Storage-backed LXC mount points are included only when their **Backup** property is enabled. LXC bind mounts and device mount points are never backed up; only their configuration is restored. Protect their underlying data separately. See the official [`pct` mount-point documentation](https://pve.proxmox.com/pve-docs/pct.1.html).
- Confirm that important Docker data lives on an included root disk or storage-backed mount point rather than an excluded host bind path.
- Snapshot mode minimizes interruption, but a running database may still need a database-native dump or vendor-supported preparation for application-consistent recovery. Keep those dumps on included storage and review the conceptual [backups, snapshots, and replication guide](../TODO.md).

Save the job and confirm that it is **Enabled**, points to `pbs`, shows the intended selection and retention, and has a **Next Run** that does not overlap PBS maintenance. See the official [PVE backup documentation](https://pve.proxmox.com/pve-docs/chapter-vzdump.html) for current modes and guest-consistency behavior.

### Run and Verify the First Backup

Prove capacity, throughput, credentials, notifications, and stored integrity with one small non-critical guest before running an unchecked all-guest job.

1. Choose a small guest that can be recovered or recreated. Confirm the datastore has sufficient free capacity, no prune/GC/verification task is active, and the test will not overlap maintenance.
2. Select that guest in PVE, open **Backup**, click **Backup now**, choose storage `pbs` and **Snapshot** mode, and start the task. This pilot is separate from running the entire scheduled job.
3. Follow the PVE task log until it ends with **OK**. Investigate a warning or failure rather than treating a partially written snapshot as success, and confirm that a failure reaches the PVE notification path.
4. In PBS, open **Datastore → pve-backups → Content** and inspect the new entry:
   - The guest type and ID match the pilot guest.
   - The snapshot timestamp matches the completed task.
   - The owner is `pve-backup@pbs!pve` or its expected owning identity.
   - Size and encryption state match the job and storage choice.
5. Select the new snapshot, click **Verify**, and wait for its PBS task to finish with **OK**. If immediate manual verification is impractical for a large snapshot, record the next scheduled verification time and confirm its completed log before considering this integrity check finished.
6. Return to **Datacenter → Backup** in PVE. Confirm the full job remains **Enabled** with the intended **Next Run**. After the pilot and capacity review succeed, run the scheduled job manually during its approved window or allow that next run, then check every selected guest and notification result.

The first backup normally transfers more data. Later PBS backups usually send changed data incrementally and reuse chunks through deduplication, but the saving depends on the workload; each snapshot remains logically complete. A visible and verified snapshot proves that data was stored consistently with its manifest, not that the full recovery workflow works.

### Test a Restore

An isolated restore smoke test proves more than a backup log. Use a recent small snapshot and keep the restored identity away from production until its contents have been inspected.

> **Warning:** Starting a restored clone on the production network can duplicate IP addresses, hostnames, scheduled jobs, cluster identities, and application credentials. Isolate it before first boot.

1. In PVE, select the pilot backup on storage `pbs` and click **Restore**.
2. In the restore dialog:
   - **CT** or **VM:** Enter an unused `<TEST-GUEST-ID>` after checking the entire PVE resource tree.
   - **Storage:** Select suitable temporary target storage.
   - **Start after restore:** Leave disabled.
   - Keep the original privilege level and other settings from the backup unless the test has a documented reason to override them.
3. Start the restore and follow its task log to **OK**. Do not continue if volume or configuration restore reports an error.
4. Before first boot, remove or disable the temporary guest's virtual network interface, or attach it only to a deliberately isolated test bridge/VLAN with no route to production.
5. Start the restored guest from the PVE console. Confirm that it boots, then inspect representative configuration, persistent files, permissions, application state, and database data where applicable. Do not enable external jobs, senders, or integrations merely to make the test look complete.
6. Shut down the test guest. Confirm that the original production guest and source PBS snapshot still exist.
7. Reconfirm the temporary guest's name and `<TEST-GUEST-ID>`, then remove only that restored copy. Never select the production guest or source backup for cleanup.

An LXC restore may recreate bind or device mount-path entries whose contents were never in the backup. Validate those external dependencies separately. For recurring drills and deeper scenarios, use the [isolated-restore guide](../TODO.md) and [Managing backups](../TODO.md).

### Protect PBS Configuration and Recovery Information

Guest backups do not automatically protect the PBS host. The `/etc/proxmox-backup/` directory contains PBS configuration and sensitive material, including users, ACLs, datastores, remotes, jobs, certificates, and notification secrets. Use a root-capable method that preserves ownership and modes to keep an encrypted, access-restricted copy outside both PBS and the primary PVE node; verify the copy and document how to restore it before depending on it.

Keep a separate non-secret recovery record containing:

- PBS hostname, direct address, and private Traefik URL.
- Datastore name and backing path; for dedicated hardware, also record the disk model, serial number, filesystem or pool, and physical location.
- PBS certificate fingerprint, PVE storage ID `pbs`, user ID `pve-backup@pbs`, and token ID `pve-backup@pbs!pve`.
- Backup, prune, GC, and verification schedules; Gotify target and matcher names; and any off-site or UPS dependency.
- Client-encryption key fingerprint and the location of its separately protected recovery copies, if encryption is enabled.

Do not put administrator passwords, token secrets, Gotify tokens, private encryption keys, or plaintext configuration archives in ordinary Markdown notes. Test access to the protected configuration copy during recovery reviews, and update it after material PBS configuration changes. The official [PBS configuration-files documentation](https://pbs.proxmox.com/docs/configuration-files.html) inventories the files under `/etc/proxmox-backup/`.

For routine PBS updates, first review the current release and migration notes, refresh the protected configuration copy, wait for datastore tasks to finish, and update through **Administration → Updates**. Reboot only when required, then recheck essential services, datastore availability, PVE content listing, scheduled jobs, and notification delivery.

Before decommissioning or replacing PBS, disable the PVE backup job, confirm that every required snapshot and recovery secret exists in an independently verified location, and preserve the configuration record. Revoke the integration token and remove the PVE storage, Traefik route, and private DNS record only after the replacement path works; never erase or reuse the datastore merely to make a failed migration disappear.

## Extend Your Backup Strategy

One local PBS is the baseline, not a complete disaster-recovery design. The **3-2-1 principle** means keeping at least **three** copies of important data, on at least **two** kinds of storage or independent systems, with at least **one** copy off-site. The live PVE workload, a dedicated PBS copy, and an independent off-site or offline copy can satisfy that intent only when they do not share the same device, location, credentials, or failure domain. A PBS LXC and its PVE host do not provide that separation by themselves.

A second off-site PBS can define the primary server as a **Remote** and pull snapshots into its own datastore over Tailscale, another VPN, or a comparably private link. Destination-initiated synchronization limits the source system's ability to delete the off-site copy; give the destination separate credentials, retention, verification, capacity monitoring, and alerts, and do not enable removal of vanished source snapshots without a deliberate policy. Keep the detailed procedure in the [encrypted off-site PBS guide](../TODO.md), and use the official [PBS remote documentation](https://pbs.proxmox.com/docs/managing-remotes.html) for current sync behavior.

Application- and data-level backups complement PBS rather than replace it. Database-native dumps can provide application-consistent recovery points; tools such as [Restic](https://restic.readthedocs.io/en/stable/), [BorgBackup](https://borgbackup.readthedocs.io/en/stable/), and [Kopia](https://kopia.io/docs/) provide retained, encrypted, versioned repositories for selected files when their threat model and destination support fit. [`rclone`](https://rclone.org/docs/) is primarily a transfer and synchronization tool: `rclone sync` can propagate source deletions to the destination, while `copy` alone still does not create retention or version history. A restorable backup therefore needs independent versions, credentials, integrity checks, and tested restores—not merely a second synchronized path.

Choose only the layers justified by the recovery objective, secure every destination, monitor failures and capacity, and periodically restore representative data from each layer. The [Understand backups, snapshots, and replication](../TODO.md) guide provides the conceptual overview.
