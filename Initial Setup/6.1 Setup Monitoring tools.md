# Monitoring Tools

This chapter adds four monitoring tools to the homelab: Beszel records system and Docker metrics, Uptime Kuma checks whether services are available, MySpeed builds a history of Internet performance, and Homepage gathers useful links into one dashboard. By the end, the services created in earlier chapters have a practical monitoring and notification baseline rather than a single generic status page.

All four applications run as separate Docker containers inside one shared monitoring LXC. This keeps the setup manageable while preserving separate application processes and persistent directories, but it is not equivalent to four independent LXCs: the applications share one LXC, kernel context, Docker Engine, network environment, maintenance window, and failure domain. Losing this LXC normally does not interrupt DNS, private HTTPS routing, remote access, or the monitored applications, but it does remove metrics, availability alerts, speed history, and dashboard access until monitoring is restored.

## About Monitoring Tools

The monitoring LXC combines four free, open-source applications that answer different questions. Beszel shows how systems are using resources, Uptime Kuma checks whether an endpoint is working, MySpeed tracks the Internet connection over time, and Homepage provides a convenient starting point for the services you use. Their roles overlap enough to be useful together without treating a link dashboard as a monitoring engine or a speed test as an availability check.

### Beszel

[Beszel](https://beszel.dev/) is a lightweight server-monitoring platform with a central Hub and an agent on every monitored system. This guide uses it for CPU, memory, disk, network, and Docker-container history, plus a small set of resource and offline alerts. Its simple Hub-and-agent model is a good fit for this homelab, although the Hub cannot independently report the loss of the LXC in which it runs.

### Uptime Kuma

[Uptime Kuma](https://github.com/louislam/uptime-kuma) is an availability monitor for HTTP(S), TCP, ping, DNS, and other checks. This guide uses it to test deliberate service paths, send down and recovery notifications through Gotify, and suppress misleading alerts during planned maintenance. A green HTTP check proves only the path it targets; it does not automatically prove every dependency or application function.

### MySpeed

[MySpeed](https://docs.myspeed.dev/) schedules Internet speed tests and records download, upload, ping, and other supported measurements. It helps reveal trends and recurring connection problems, but results depend on the chosen provider and server, concurrent traffic, the monitoring LXC's resources, and any VPN path on the same system. Treat the history as operational evidence, not formal proof for an ISP dispute.

### Homepage

[Homepage](https://gethomepage.dev/) is a configurable application dashboard built from YAML files. The baseline in this chapter provides organized links and a safe starter layout; optional widgets can later add selected status or metric information. Homepage is not an availability monitor and does not include its own authentication layer, so this passwordless design remains private and deliberately avoids sensitive widgets or credentials.

## Before You Begin

- Complete the Komodo, DNS, custom-domain, reverse-proxy, VPN, and notification-server chapters. Confirm that Komodo, Traefik, Tailscale, and Gotify are healthy before monitoring them.
- This guide uses LXC ID `105`, hostname `monitoring`, address `192.168.0.105`, gateway `192.168.0.1`, and bridge `vmbr0`. Confirm that the ID and address are unused and adapt every later occurrence consistently if your plan differs.
- Replace `<MY-DOMAIN>` and `<TIMEZONE>` wherever they appear. Use an IANA timezone such as `Europe/Budapest`.
- Keep a password manager ready for administrator credentials, Gotify application tokens, and Beszel enrollment material. Do not place those values in ordinary notes, screenshots, or repository files.
- Keep `beszel`, `uptime`, `myspeed`, and `homepage` hostnames private. This chapter does not require public DNS records or router port forwarding.

## Setup LXC

Create the monitoring LXC by running one of the following [Docker helper script](https://community-scripts.org/scripts/docker) commands on the Proxmox node (**Node → Shell**).

```sh
# Recommended: use the guide's predefined settings
mode=generated var_os=debian var_version=13 var_unprivileged=1 var_cpu=2 var_ram=4096 var_disk=16 var_ctid=105 var_hostname=monitoring var_brg=vmbr0 var_net=192.168.0.105/24 var_gateway=192.168.0.1 var_nesting=1 var_keyctl=1 var_tags=essential var_protection=yes bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/docker.sh)"

# Alternative: launch the interactive installer
bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/docker.sh)"
```

Use these settings as the acceptance baseline:

| Setting | Reference value |
| --- | --- |
| Container type | Unprivileged |
| Operating system | Debian 13 |
| Container ID | `105` |
| Hostname | `monitoring` |
| Disk size | 16 GiB |
| CPU cores | 2 |
| RAM | 4096 MiB |
| Network bridge | `vmbr0` |
| IPv4 configuration | Static: `192.168.0.105/24`; gateway: `192.168.0.1` |
| Container tag | `essential` |
| Nesting | Enabled |
| Keyctl | Enabled |
| Container protection | Enabled |
| Start at boot | Enabled by the helper |

The `2` vCPU, `4096` MiB RAM, and `16` GiB disk values are a conservative shared-LXC starting point rather than permanent requirements. Watch real usage and expand the LXC when comfortable headroom disappears. During Docker installation, decline Portainer, the Portainer Agent, and Docker TCP socket exposure. Komodo will manage this Docker host and does not require an additional management UI or an insecure TCP listener. FUSE, TUN/TAP, and device passthrough are not required.

If the helper prompts for storage, select the template and LXC storage from your storage plan. Treat failed network, DNS, package, template, or Docker checks as blockers rather than continuing from a partial installation.

The helper script must finish successfully. Then verify the LXC's settings from the UI or the Proxmox node (**Node → Shell**):

```sh
pct status 105
pct config 105
```

Confirm that the LXC is running, starts at boot, is unprivileged and protected, uses the intended resources, static address, and bridge, and has nesting and keyctl enabled. Resolve any mismatch before continuing.

Open the monitoring LXC (**LXC → Console**) and verify its address, time synchronization, Docker installation, and DNS resolution:

```sh
ip -brief address
timedatectl status
docker version
getent hosts raw.githubusercontent.com
```

The intended static address must be present, the clock must be synchronized, `docker version` must show both client and server information, and the hostname lookup must return an address.

## Setup Beszel

Beszel is deployed first because the monitoring LXC will enroll itself and the systems from earlier chapters before alert rules are created.

### Create Docker Stack

The repository-owned Beszel stack deploys only the central Hub. It does not include `beszel-agent` or `beszel-socket-proxy`; agents belong on the individual systems they monitor and are enrolled separately after the Hub is available.

1. Go to **Komodo → Stacks → New Stack** and enter:
   - **Stack Name:** `beszel`
   - **Server:** `105-monitoring`
   - **Choose Mode:** UI Defined
   - **Compose File:** paste [`beszel-compose.yaml`](../Application%20Library/Monitoring%20Tools/Beszel/beszel-compose.yaml)
   - **Environment:** paste [`beszel.env`](../Application%20Library/Monitoring%20Tools/Beszel/beszel.env), then replace `<MY-DOMAIN>` and `<TIMEZONE>`
   - **Poll for Updates:** enabled
   - **Auto Update:** disabled
   - **Full Stack Auto Update:** disabled
   - **Links:** `https://beszel.<MY-DOMAIN>.com`
2. Create and deploy the stack. Confirm that `beszel` becomes healthy. Do not add agent enrollment values to this stack environment; the Hub can run before any monitored system is enrolled. Keep automatic deployment disabled because the stack deliberately follows the current upstream image channel and each update requires release-note review and a recoverable data backup.

Verify the Hub backend inside the monitoring LXC (**LXC → Console**):

```sh
curl -fsS http://127.0.0.1:8090/api/health
```

Continue only when the health command succeeds. Port `8090` remains the trusted-LAN bootstrap and Traefik backend path. No Beszel agent or Docker socket proxy should appear in this central stack.

### Configure HTTPS Access with Traefik

The wildcard DNS rewrite already directs `beszel.<MY-DOMAIN>.com` to Traefik. Install the repository's Beszel router so normal browser access and generated agent links use private HTTPS while Traefik forwards to `http://192.168.0.105:8090`.

In the Traefik configuration editor, create `/TRAEFIK/config/dynamic/beszel.yaml` from [`beszel.yaml`](../Application%20Library/Reverse%20Proxies/Traefik/Config%20files/Traefik/dynamic/beszel.yaml) with these contents:

```yaml
# Later-service template: install only when Beszel is deployed.
http:
  routers:
    beszel:
      entryPoints:
        - websecure
      rule: Host(`beszel.<MY-DOMAIN>.com`)
      middlewares:
        - secured@file
      service: beszel

  services:
    beszel:
      loadBalancer:
        passHostHeader: true
        servers:
          - url: http://192.168.0.105:8090
```

Replace `<MY-DOMAIN>` before saving. The shared `websecure` entry point supplies TLS and the wildcard certificate, so no per-router certificate resolver is required. `secured@file` preserves the private-client, CrowdSec, header, and request-limit controls without adding Authelia in front of Beszel's own login or agent WebSocket path. Traefik handles WebSocket upgrades automatically.

Traefik hot-reloads the dynamic directory. Check the route inside the Traefik LXC (**LXC → Console**):

```sh
docker logs --since 5m traefik 2>&1 | grep -Ei 'beszel|dynamic|file|error|middleware|router'
curl -fsS "https://beszel.<MY-DOMAIN>.com/api/health"
```

Review the logs rather than treating empty output as proof. Continue only when there is no Beszel parse, middleware, router, or provider error and the HTTPS health request succeeds. If it fails, correct or remove only `beszel.yaml`; the file provider will return to the previous valid watched state without restarting unrelated stacks.

### Application Configuration

Open `https://beszel.<MY-DOMAIN>.com` and create the initial administrator account with a strong unique password. The stack already sets `APP_URL` to this private HTTPS hostname for Hub-generated links. No SMTP, OIDC, PocketBase, display, or optional account setting is required before the first system is enrolled.

### Add a System to Beszel

Every monitored system has one Beszel record and one separately installed agent. **Docker** and **Binary** in the Add System workflow are deployment methods for that per-system agent, not different system types, extra monitoring records, or services to add to the central Hub Compose.

- Prefer the **Docker** agent on an LXC that already runs Docker. It reports LXC-level metrics and can report Docker-container information when its generated deployment is deliberately granted the required Docker access.
- Prefer the **Binary** installer on an LXC such as the Tailscale subnet router that does not run Docker and needs system metrics only. The generated Linux installer creates a `beszel` user, a systemd service, and optional automatic agent updates.
- The binary agent can also use a Docker API when deliberately configured, but this repository does not establish a canonical agent or socket-proxy stack.

To enroll one system:

1. In Beszel, select **Add System** and enter:
   - **Name:** `<LXC-ID>-<SERVICE-NAME>`, for example `100-komodo`
   - **Host / IP:** `<LXC-IP>:45876` for the normal TCP agent method, or another value explicitly generated for the selected agent mode
2. Select the appropriate **Docker** or **Binary** instructions. Copy the public key, token, Hub URL, and generated command or Compose definition exactly as shown by the installed release. Treat the key and token as sensitive enrollment material.
3. Review the generated agent definition before running it. Docker access is a privileged trust boundary: understand every socket or API permission it requests, do not publish an unauthenticated Docker API on the LAN, and do not assume that the Hub-only repository Compose supplies a proxy for the target system.
4. Run the generated installation inside the system being enrolled (**LXC → Console**). Do not run it in the Beszel Hub container or on the Proxmox node. The normal TCP method has the Hub connect to the agent's TCP port, which defaults to `45876`; when the generated configuration explicitly uses a supported outbound mode, the agent instead connects to the Hub. Follow one verified mode and its generated values rather than mixing them.
5. Confirm that the separately managed agent or agent stack persists across reboot before selecting **Add System** in the Hub.
6. Finish the dialog and wait for the system to become green/online. Confirm that host metrics appear and, where Docker collection was deliberately configured on that target, that the expected containers are listed.

If an agent remains offline, verify the name and address, the selected connection mode and port, firewall reachability, the exact enrollment values, and the agent logs on that monitored system. If host metrics appear but Docker containers do not, inspect the Docker access configured for that agent. Do not solve the problem by exposing an unrestricted Docker API or by adding the agent to the central Hub stack. See Beszel's current [Getting Started](https://beszel.dev/guide/getting-started) and [Agent Installation](https://beszel.dev/guide/agent-installation) documentation for release-specific generated definitions.

### Connect Beszel to Gotify

Beszel defines notification services under **Settings → Notifications** and enables alerts per system. Give Beszel its own Gotify application so its token can be identified and revoked independently.

1. In Gotify, go to **Apps → Create Application**, create an application named `Beszel`, and copy its application token into your password manager.
2. In Beszel, go to **Settings → Notifications**, add a Gotify notification URL, and use:

   ```text
   gotify://gotify.<MY-DOMAIN>.com:443/<GOTIFY-APPLICATION-TOKEN>/?priority=1
   ```

3. Save the URL and run Beszel's notification test.
4. Confirm that the test appears under the `Beszel` application in Gotify and reaches the configured client.

Beszel's supported Gotify schema necessarily contains the token in the notification URL. Keep the URL in Beszel and your password manager, not in screenshots, logs, or ordinary notes, and rotate the application token if it is exposed. See the official [Beszel Gotify schema](https://beszel.dev/guide/notifications/gotify) for current options.

### Configure Beszel Alerts

The agent is now reporting metrics and Gotify is ready to deliver messages. Add a small set of alerts that indicates sustained or actionable conditions rather than every short-lived spike.

1. In the systems table, find a monitored system and open its bell-icon alert controls.
2. Enable only categories that the system actually reports. Current Beszel categories include status/offline, CPU, memory, disk, load average, bandwidth, and temperature.
3. Start conservatively. Suitable first decisions include an offline delay long enough to ignore a brief restart, CPU or memory pressure sustained for several minutes, and disk usage that leaves time to respond. Do not enable temperature alerts on systems without a reliable sensor.
4. Select the verified Gotify notification channel where the current dialog requests it, save the rules, and confirm that the bell state shows alerts are configured.
5. Use the notification provider's built-in test first. If the current release requires a rule-level test, apply a temporary harmless threshold to a non-foundational system, confirm the alert and recovery messages, and immediately restore the intended value. Do not stop DNS, Traefik, Tailscale, Gotify, or another foundational service merely to trigger an alert.

Review thresholds after Beszel has collected representative baseline data. Expected maintenance, short CPU bursts, workload variation, and absent sensors otherwise create alert fatigue. Beszel's [notification documentation](https://beszel.dev/guide/notifications/) lists the current provider and alert model.

5. Save the provider only after the test succeeds.

### Add a Monitor to Uptime Kuma

Choose the monitor type that proves the behavior you care about. **HTTP(s)** can exercise DNS, Traefik, TLS, and an application response; **TCP Port** proves that a listener accepts connections; **Ping** proves only basic host reachability; and **DNS** can test resolver behavior. A direct backend or health endpoint isolates application availability, while a private HTTPS hostname tests more of the user-facing dependency path.

Create a reusable HTTP monitor from **Add New Monitor** with values such as:

- **Monitor Type:** HTTP(s)
- **Friendly Name:** `<SERVICE-NAME>`
- **URL:** `https://<SERVICE>.<MY-DOMAIN>.com`
- **Heartbeat Interval:** `60` seconds
- **Retries:** `2`
- **Heartbeat Retry Interval:** `20` seconds, when shown by the installed release
- **Request Timeout:** `10` seconds
- **HTTP Method:** GET
- **Accepted Status Codes:** `200-299`
- **Ignore TLS/SSL Error:** disabled
- **Notifications:** `gotify`

The interval determines normal check frequency, retries prevent one transient failure from immediately becoming **Down**, and the timeout limits how long a request can hang. Keep certificate checks enabled for Traefik hostnames. Disable them only for an explicitly documented direct backend with a self-signed certificate, such as the Proxmox VE interface used in this guide.

Save the monitor and wait for its first result. **Pending** means no decisive result has been recorded, **Up** means the configured success condition passed, and **Down** means the retry policy was exhausted. Pausing intentionally stops normal monitoring; maintenance is the better choice for planned work because it keeps the monitor configuration and identifies an expected window.

To test down and recovery notifications without stopping a real service, temporarily create a disposable HTTP monitor for the reserved, non-routable address `http://192.0.2.1`, assign `gotify`, and wait for **Down**. Change that disposable monitor to a known-good private HTTPS target, confirm **Up** and the recovery notification, then delete only the disposable monitor.

For later services, use [`Add a Monitor to Uptime Kuma`](../Quick%20action%20guides/Add%20a%20monitor%20to%20Uptime%20Kuma.md).

### Application Configuration

1. Open `https://myspeed.<MY-DOMAIN>.com`, open **Settings**, and set a strong access password.
2. Select the speed-test provider for this deployment. MySpeed currently supports Ookla, LibreSpeed, and Cloudflare methods; the provider is the measurement system, while a server is the individual endpoint used by that provider.
3. Begin with automatic server selection. Choose a specific nearby server only after repeated tests show that it is stable and representative.
4. Run a manual test and confirm that download, upload, ping, and any supported latency or jitter values are recorded in history.
5. Set a proportionate automatic frequency or Cron schedule. A daily quiet-period test such as `0 3 * * *` is a conservative starting point; increase frequency only when the added data is worth the bandwidth and interference. Use MySpeed's pause function during temporary high-bandwidth work.
6. Configure the connection-quality thresholds for good, medium, and bad indicators from your expected service rather than copying another connection's values.
7. Open **Manage storage → Speedtests → Data retention** and select a deliberate retention period. The current default is `365` days; shorter retention is reasonable when long history is not useful.

Results can be distorted by concurrent traffic, LXC CPU or network limits, VPN routing on the same system, and server choice. Finish only after an automatic test runs on schedule and its result appears in history. See the current [MySpeed settings](https://docs.myspeed.dev/instructions/settings) documentation for provider, frequency, pause, quality, and retention behavior.

### Configure HTTPS Access with Traefik

Homepage's normal address is `https://homepage.<MY-DOMAIN>.com`; Traefik forwards it to `http://192.168.0.105:3000`.

In the Traefik configuration editor, update the `homepage` router in `/TRAEFIK/config/dynamic/homepage.yaml` from the repository's [`homepage.yaml`](../Application%20Library/Reverse%20Proxies/Traefik/Config%20files/Traefik/dynamic/homepage.yaml) template. The dashboard portion must contain:

```yaml
http:
  routers:
    homepage:
      entryPoints:
        - websecure
      rule: Host(`homepage.<MY-DOMAIN>.com`)
      middlewares:
        - secured@file
      service: homepage

  services:
    homepage:
      loadBalancer:
        passHostHeader: true
        servers:
          - url: http://192.168.0.105:3000
```

Preserve any separately reviewed optional editor router already present in the file. Replace `<MY-DOMAIN>` and save. The dashboard uses `secured@file`, not `secured-auth@file`: Homepage should open without an additional Authelia login while remaining restricted to the trusted LAN and approved Tailscale path. Do not create a public DNS record or router port forward.

Check the dashboard route inside the Traefik LXC (**LXC → Console**):

```sh
docker logs --since 5m traefik 2>&1 | grep -Ei 'homepage|dynamic|file|error|middleware|router'
curl -fsS "https://homepage.<MY-DOMAIN>.com/" >/dev/null && echo 'Homepage HTTPS route reachable.'
```

Continue only when there is no focused route error and Homepage loads through private HTTPS. If it fails, check both the Traefik host rule and `HOMEPAGE_ALLOWED_HOSTS`; correct only the affected route or stack value.

Homepage has no built-in authentication. The passwordless baseline is appropriate only because the route is private and the starter configuration contains low-sensitivity links rather than credentials or personal data. Reassess authentication and exposure before adding sensitive widgets, API keys, or access from less-trusted clients.

### Application Configuration

Homepage reads four bind-mounted YAML files:

- `services.yaml` defines groups, service cards, links, and optional service widgets.
- `settings.yaml` controls the title, theme, layout, link behavior, and application-level options.
- `widgets.yaml` defines header and information widgets.
- `bookmarks.yaml` defines grouped bookmarks.

Download one exact repository revision into a staging directory rather than following the moving `master` branch. Find the full commit SHA for the guide version you are using, replace `<COMMIT-SHA>`, and run these commands inside the monitoring LXC (**LXC → Console**):

```sh
REPOSITORY_REF="<COMMIT-SHA>"
TEMPLATE_BASE="https://raw.githubusercontent.com/TMD44/homelab-launchbook/${REPOSITORY_REF}/Application%20Library/Dashboards/Homepage/Config%20files"
STAGING_DIRECTORY="/root/homepage-template-staging"

install -d -m 0700 "$STAGING_DIRECTORY"
for CONFIG_FILE in services.yaml settings.yaml widgets.yaml bookmarks.yaml; do
  curl --fail --location --show-error --silent --retry 3 \
    "$TEMPLATE_BASE/$CONFIG_FILE" \
    --output "$STAGING_DIRECTORY/$CONFIG_FILE"
done

grep -RnoE '<[A-Z0-9-]+>' "$STAGING_DIRECTORY"
```

The commands follow redirects, fail on HTTP errors, and leave the files outside the live bind mount. Inspect all four files with a trusted editor on the monitoring LXC, replace the documented placeholders, and remove or rename examples that do not suit your environment. Entries under **Optional apps** and the UPS examples intentionally demonstrate future customization; they are not claims that those services have already been deployed.

Do not place API keys, passwords, or personal data directly into these public starter files. Use Homepage's supported environment or file-variable mechanisms if a later widget needs a secret, and revisit the passwordless security decision first.

Compare the staging set with any existing configuration and preserve a known-good copy before installation. Run inside the monitoring LXC (**LXC → Console**):

```sh
BACKUP_DIRECTORY="/HOMEPAGE/backups/config-$(date +%Y%m%d-%H%M%S)"
install -d -m 0700 "$BACKUP_DIRECTORY"

for CONFIG_FILE in services.yaml settings.yaml widgets.yaml bookmarks.yaml; do
  if [ -f "/HOMEPAGE/config/$CONFIG_FILE" ]; then
    cp -a "/HOMEPAGE/config/$CONFIG_FILE" "$BACKUP_DIRECTORY/"
    diff -u "/HOMEPAGE/config/$CONFIG_FILE" "/root/homepage-template-staging/$CONFIG_FILE" || true
  fi
done
```

After reviewing the differences and placeholders, install only the verified files and restart only Homepage (**LXC → Console**):

```sh
install -d -m 0755 -o root -g root /HOMEPAGE/config
install -m 0644 -o root -g root /root/homepage-template-staging/*.yaml /HOMEPAGE/config/
docker restart homepage
docker logs --since 5m homepage 2>&1
```

Check the logs for YAML parsing and allowed-host errors. Open `https://homepage.<MY-DOMAIN>.com`, use the refresh control if Homepage needs to regenerate its static page, and verify links only for services that are actually installed. Restore the four files from `BACKUP_DIRECTORY` and restart Homepage if the new set fails; do not delete the working configuration as a troubleshooting shortcut.

Finally, add `https://homepage.<MY-DOMAIN>.com` to Uptime Kuma using the earlier generic HTTP(s) monitor procedure.

### Make Homepage Your Own

The downloaded files are a static starter example, not a prescribed final dashboard. Reorganize them around your services and routines, remove examples you do not need, and let the dashboard evolve with the homelab.

#### Add Live Information with Widgets

Service widgets live with their service entries in `services.yaml` and can display selected application status or metrics. Information widgets live in `widgets.yaml` and appear in the header. Add one integration at a time, verify its least-privileged API access, and remember that keys or personal information make the dashboard more sensitive. Use Homepage's supported secret-variable mechanism and reconsider the passwordless baseline before adding them.

#### Personalize the Layout and Appearance

Experiment with groups and nested groups, row or column layouts, tabs, icons, themes, backgrounds, bookmarks, and—only when necessary—custom CSS or JavaScript. Keep a backup of the working YAML files, change one layer at a time, and refresh or restart only when the relevant Homepage option requires it.

#### Explore Discovery and Integrations

Homepage supports a broad integration catalog and optional Docker-label-based discovery. Discovery is not part of this baseline because it requires controlled access to Docker metadata. Never expose an unauthenticated Docker API or mount the unrestricted Docker socket directly; a future implementation must use a restricted socket proxy and receive a fresh security review.

Consult the official [Homepage configuration](https://gethomepage.dev/configs/), [services and widgets](https://gethomepage.dev/configs/services/), [settings and layout](https://gethomepage.dev/configs/settings/), and [Docker integration](https://gethomepage.dev/configs/docker/) documentation for current options. Experiment incrementally and keep the last known-good YAML set recoverable.

## Maintain and Recover the Monitoring Stack

The four applications share an LXC but retain separate state. Their minimum lifecycle is:

- **Routine update:** read the relevant release and migration notes, take a known-good backup, update one central stack at a time, and repeat its direct-backend, HTTPS, login, data, monitor, and notification checks. Beszel Hub, MySpeed, and Homepage follow upstream floating channels; Uptime Kuma follows supported major `2`. Review and update every separately deployed Beszel agent through its own documented lifecycle. Keep unattended auto deployment disabled.
- **Backup:** protect `/BESZEL/data`, `/UPTIMEKUMA/data`, `/MYSPEED/data`, and `/HOMEPAGE/config`, plus any separate LXC-level backup and any state required by separately deployed agents. Stop or quiesce the relevant stack when necessary for an application-consistent SQLite copy. The Beszel Unix-socket directory is runtime state and does not need backup.
- **Rollback:** restore the data backup created before the update and redeploy the previous known-good image or stack definition. Do not roll an application database backward without its matching backup.
- **Recovery:** keep the direct trusted-LAN ports available to distinguish an application failure from DNS, Traefik, or TLS, but do not treat them as normal remote-access paths. Restore one service at a time and repeat the combined HTTPS and notification checks.
- **Decommissioning:** remove the service's Traefik dynamic file, revoke Gotify and enrollment tokens, remove its Uptime Kuma monitor and Homepage card, and stop its stack. Delete persistent data or backups only after confirming they are no longer required; disable LXC protection deliberately before removing the complete monitoring LXC.

Use [`Update a Service`](../Quick%20action%20guides/Update%20a%20service.md) for later application updates and [`Managing Backups`](../Quick%20action%20guides/Managing%20backups.md) for routine backup operations. Continue to review the application release notes and follow the safe sequence above.

## Expand the Monitoring Stack to Suit Your Needs

Beszel, Uptime Kuma, MySpeed, and Homepage are a practical starting point, not a closed observability stack. Add another monitoring or diagnostic service to the shared LXC when it provides useful new evidence, but check the application's CPU, memory, storage, port, and network requirements against current LXC usage first. Watch the result after deployment and increase the LXC's assigned resources in Proxmox VE when comfortable headroom disappears.

Also account for persistent-data growth and port conflicts before adding a container. Complementary additions extend this stack; the projects below are mainly substitutes for one of the selected tools and are not applications beginners are expected to install alongside every service used here.
