## About Komodo

[Komodo](https://komo.do/) is a free, open-source, self-hosted Docker management platform. Its web interface provides one place to deploy, inspect, update, and manage Docker containers and Compose stacks across the homelab.

Komodo has two main components. **Komodo Core** hosts the browser interface and coordinates management actions, while **Komodo Periphery** runs on each connected Docker host and reports system information, container status, and logs back to Core. The Komodo LXC created here runs Core and a local Periphery container for its own Docker engine. Later chapters install Periphery on the other Docker-host LXCs, allowing those isolated environments to be managed from the same interface.

## Before You Begin

- Complete and verify the preceding [Proxmox VE](<1. Setup Proxmox VE.md>) chapter, and keep **Node → Shell** access available.
- Treat LXC ID `100`, hostname `komodo`, address `192.168.0.100`, gateway `192.168.0.1`, and bridge `vmbr0` as reference values. Confirm that the ID and address are unused, reserve the address or keep it outside the DHCP pool, and adapt every later reference consistently if your environment differs.
- Use a client on the trusted home network for the initial sign-in. Do not expose Komodo or forward port `9120` from the router.
- Have a password manager ready for the administrator credentials.

## Setup LXC

Create the Komodo LXC by running one of the following [Docker helper script](https://community-scripts.org/scripts/docker) commands on the Proxmox node (**Node → Shell**).

```sh
# Recommended: use the guide's predefined settings
mode=generated var_os='debian' var_unprivileged=1 var_nesting=1 var_keyctl=1 var_ctid=100 var_hostname=komodo var_cpu=2 var_ram=2048 var_disk=16 var_brg=vmbr0 var_net=192.168.0.100/24 var_gateway=192.168.0.1 var_tags=essential var_protection=yes bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/docker.sh)"

# Alternative: launch the interactive installer
bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/docker.sh)"
```

Use these settings as the acceptance baseline:

| Setting | Reference value |
| --- | --- |
| Container type | Unprivileged |
| Operating system | Debian 13 |
| Container ID | `100` |
| Hostname | `komodo` |
| Disk size | 16 GiB |
| CPU cores | 2 |
| RAM | 2048 MiB |
| Network bridge | `vmbr0` |
| IPv4 configuration | Static: `192.168.0.100/24`; gateway: `192.168.0.1` |
| Container tag | `essential` |
| Nesting | Enabled |
| Keyctl | Enabled |
| Container protection | Enabled |
| Start at boot | Enabled by the helper |

During Docker installation, decline Portainer, the Portainer Agent, and Docker TCP socket exposure. Komodo uses the local Docker socket through its Periphery container and does not require an additional management UI or an insecure TCP listener.

The helper script must finish successfully. Then verify the LXC's settings from the UI or the Proxmox node (**Node → Shell**):

```sh
pct status 100
pct config 100
```

Open the Komodo LXC (**LXC → Console**) and verify its address, time synchronization, and Docker installation:

```sh
ip -brief address
timedatectl status
docker version
```

The intended static address must be present, the clock must be synchronized, and `docker version` must show both client and server information. Treat a failed check as a blocker for the Komodo installation.

## Setup Komodo

The Community Scripts addon installs Komodo through Docker Compose and lets you choose MongoDB, the upstream recommendation, or FerretDB as its database. The selected database stores Komodo’s resource configuration, user accounts, audit logs, and other system state.

Install Komodo by running the [Komodo helper script](https://community-scripts.org/scripts/komodo) inside the Komodo LXC (**LXC → Console**):

```sh
bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/tools/addon/komodo.sh)"
```

Confirm the installation and choose the database. The helper must create `/opt/komodo`, download either `mongo.compose.yaml` or `ferretdb.compose.yaml`, generate `/opt/komodo/compose.env`, start Komodo Core and Periphery, and report that the interface is reachable at `http://192.168.0.100:9120`.

View the temporary administrator credentials from the Komodo LXC (**LXC → Console**):

```sh
cat ~/komodo.creds
```

> [!IMPORTANT]
> The direct `http://192.168.0.100:9120` address is an unencrypted bootstrap and backend path for the trusted home network only. Do not use it across an untrusted network or expose port `9120` to the Internet. The [Reverse Proxy](../TODO.md) chapter later makes Komodo available through private HTTPS for normal browser access; the direct LAN path intentionally remains available to Traefik and other internal components.

- Open `http://192.168.0.100:9120` and sign in with the temporary credentials.
- Change the temporary administrator username and password to unique values, save them in a password manager, then sign out and back in to verify the replacement credentials.
- Open **Servers**, select `Local`, rename it to `100-komodo`, and save the change.
  Also set `KOMODO_FIRST_SERVER_NAME=100-komodo` and replace `TZ=Etc/UTC` with the appropriate IANA time-zone name in `/opt/komodo/compose.env` so Periphery uses the new server name and schedules use local time.
- **Optional orientation:** From the Komodo LXC (**LXC → Console**), list the installation directory and open its environment configuration:

  ```sh
  ls -la /opt/komodo
  nano /opt/komodo/compose.env
  ```

  The directory contains `compose.env` and the selected database-specific Compose file. `compose.env` contains database credentials and application secrets. Do not share, copy into ordinary notes, or change its contents without understanding the effect. Exit Nano without saving when you are only inspecting it.
- After the replacement login works, you can remove the temporary credential file from the Komodo LXC (**LXC → Console**):

  ```sh
  rm -f ~/komodo.creds
  ```

- Verify Komodo works as expected:
  - Open **Containers** and **Servers** verify that everything works, reports a green **OK** / **RUNNING** status.

### Explore the Komodo interface

This section provides an overview of the interface. The next chapters primarily use **Servers**, **Containers**, and **Stacks**.

- **Dashboard:** Provides a quick overview of active resources and their states. Use the recent-items view for fast access to resources you opened recently, or switch to tables for a broader inventory.
- **Containers:** Lists Docker containers across every connected server, including their server, state, image, networks, ports, and volumes. Use the filters to narrow the list, then open a container to review its logs, inspect data, and available actions.
- **Terminals:** Opens and resumes browser-based shell sessions on connected servers or running containers. Terminal access is powerful and may expose application secrets, so use it only for documented administration or troubleshooting tasks.
- **Servers:** Manages Docker hosts connected through Komodo Periphery. Open a server to verify its connection and resource usage and to view its containers, images, networks, volumes, logs, and configuration.
- **Swarms:** Manages Docker Swarm clusters, including their nodes, services, stacks, configs, and secrets. The reference setup uses independent Docker hosts and Compose stacks, so no Swarm resource is required.
- **Stacks:** Manages applications defined with Docker Compose. A stack can store its Compose files in Komodo, use files already on its server, or retrieve them from a Git repository; its page exposes configuration, services, logs, and lifecycle actions such as deploy, restart, stop, and destroy.
- **Deployments:** Manages an individual Docker container, or a Docker Swarm service, as a Komodo resource. The reference setup favors Compose-based **Stacks**, so create a Deployment only when an application is intentionally managed as a single container instead.
- **Builds:** Defines jobs that build Docker images from a Dockerfile and optionally push them to one or more registries. This is not required when a stack uses prebuilt images.
- **Repos:** Clones and updates Git repositories on an attached server or builder and can run configured commands from them. This is intended for source-based build and automation workflows, not merely for storing a stack's Compose files.
- **Procedures:** Combines Komodo operations into reusable stages. Operations in one stage can run in parallel, while stages run in order; procedures can also be started by a schedule or webhook.
- **Actions:** Runs custom TypeScript automation against the Komodo API. Treat actions as code with administrative reach, review them before execution, and leave this area unused unless a workflow cannot be expressed safely with built-in operations.
- **Syncs:** Manages resources declaratively from TOML files stored in Komodo, on the Core host, or in a Git repository. A sync previews differences before it creates, changes, deletes, or deploys resources; it is an advanced configuration-as-code workflow and is not required for the initial setup.
- **Alerts:** Shows monitoring events raised for resources, including active and resolved conditions. Use it to identify the affected resource and condition; alerts reach an external service only after an **Alerter** has been configured.
- **Updates:** Shows the audit trail for configuration changes and executions, including their status and detailed output. Review failed entries here when a deployment or management action does not complete as expected; this page is activity history, not the Komodo software updater.
- **Schedules:** Provides a combined view of scheduled **Procedures** and **Actions**, including their next run. Confirm the configured time zone and test the underlying automation manually before enabling a new schedule.
- **Settings:** Shows Komodo Core information and the shared configuration used by resources and users.
  - **Variables:** Stores reusable values and secrets that can be interpolated into resource configuration. Use secret variables for credentials, and never place their values in ordinary notes or screenshots.
  - **Tags:** Creates and manages labels used to organize, filter, and target related resources.
  - **Builders:** Configures where **Builds** run, either on a connected server or on a temporary supported cloud instance. No separate builder is needed until you create image-build jobs.
  - **Alerters:** Configures notification destinations and filtering rules for Komodo alerts. Complete this after the notification server is available later in the guide.
  - **Providers:** Stores accounts and access tokens for Git providers and Docker registries. Add only the providers required by a resource and grant each token the minimum necessary scope.
  - **Users:** Enables or disables accounts and manages users, groups, and access. This tab is visible only to administrators; keep the initial administrator account protected and grant later users only the permissions they need.
  - **Onboarding:** Creates onboarding keys used to connect additional Periphery servers to Core. Treat each key as a credential, set an expiration, and disable or remove it after the intended servers have connected.

## Maintain Komodo

Komodo is a stateful management service, so protect its database before changing the deployment:

- **Backup and restore:** Follow Komodo’s official [backup and restore procedure](https://komo.do/docs/setup/backup) and verify that a current backup exists before an update or removal.
- **Update:** Review the [Komodo release notes](https://github.com/moghtech/komodo/releases) and the current [Community Scripts addon instructions](https://community-scripts.org/scripts/komodo). Take a database backup, rerun the addon inside the Komodo LXC, select **Update**, and repeat the readiness check above.
- **Troubleshoot:** Start with the server and container status in Komodo, then inspect focused Compose logs from `/opt/komodo`. Use the [Komodo documentation](https://komo.do/docs/intro) and [upstream discussions](https://github.com/moghtech/komodo/discussions) for current behavior instead of relying on generic browser-extension workarounds.
- **Remove:** Rerunning the addon also offers an uninstall path that removes `/opt/komodo` and the deployment’s Compose volumes. Use it only after creating and verifying a recoverable database backup.

## Alternatives

The following projects are substitutes to evaluate instead of Komodo, not additional management layers that the reference setup requires:

| Tool | License | Focus |
| --- | --- | --- |
| [Portainer Community Edition](https://www.portainer.io/) | Zlib | A broad container-management interface for Docker, Swarm, and Kubernetes, with commercial editions offering additional features. |
| [Arcane](https://getarcane.app/) | BSD-3-Clause | A modern Docker and Compose manager for local and remote hosts, with agents for centralized multi-host management. |
| [Dockge](https://dockge.com/) | MIT | A Compose-focused stack manager that keeps standard `compose.yaml` files and supports multiple Docker hosts through agents, but has a narrower automation scope than Komodo. |
