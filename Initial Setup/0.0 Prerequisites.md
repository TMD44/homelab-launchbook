## What We Will Build

In this **Initial Setup** guide, we will build a solid, self-hosted homelab foundation from the ground up on a physical server. Here is an overview of each core component:

- 🖥️ **Proxmox VE** is the hypervisor OS and the foundation for everything else. It lets you run multiple virtual machines and LXC containers side by side on the same hardware, with a web interface for managing them.
- 🚀 **Komodo** handles Docker deployments because we will use Docker for most applications. Think of it as your control panel for deploying, updating, and monitoring your self-hosted services. You will not need to connect over SSH just to restart a Docker container.
- 🌐 **A local DNS server** so you can reach your services by name (like `https://immich.<MY-DOMAIN>.com`) instead of memorizing IP addresses and port numbers. On top of that, we'll use it as a network-wide ad blocker, so every device on your network benefits without any extra setup.
- 🌍 **A custom domain** for consistent private service names and DNS-based HTTPS certificate validation without making the services publicly reachable.
- 🔒 **A reverse proxy with authentication** sits in front of all your services on your local network. It routes traffic to the right backend service, handles HTTPS certificates automatically, and lets you add a login screen in front of sensitive services. This avoids browser security warnings and `:port` numbers in your URLs.
- 📝 **Code-server** for editing configuration files in a comfortable browser-based interface instead of relying on terminal editors for every change.
- 🛡️ **A VPN for secure remote access** so you can connect back to your home network when you're away, as if you never left.
- 🔔 **A notification server** to send push notifications when something needs your attention: a service goes down, a backup fails, or an update is available.
- 📊 **A monitoring LXC with complementary tools** for host and Docker resource metrics, service and endpoint availability, and Internet performance history.
- 🏠 **A homepage** as your personal front door to the homelab: a clean dashboard with links to all your services.
- 💾 **Proxmox Backup Server** to schedule and store reliable backups of your virtual machines and LXC containers, helping you recover after a misconfigured update or failed disk.
- ⚡ **UPS software** to gracefully shut down your server during a power outage, protecting your data and hardware if you have a UPS.

The guide generally favors tools that are **free to use, open source, lightweight, and actively maintained**, while some optional or provider-specific components may differ. The goal is to create a setup that runs reliably in the background so you can focus on using it.

## How to Read This Guide

The numbered **Initial Setup** chapters should normally be completed in order. Finish each chapter's verification steps before continuing. Work one step at a time, inspect the result, and resolve errors before moving forward. Do not paste an entire command sequence blindly or continue after a failed command, because later services and configuration depend on earlier work functioning correctly.

This guide follows a primary path designed to work as a complete reference setup. Sections marked **Optional** are not required, and entries under **Alternatives** replace the primary tool rather than adding another service that beginners must install. If you deviate from the reference path, expect to adapt later instructions to match your design.

- **Code blocks**: A block may contain a terminal command or file content such as YAML, XML, or environment values. Follow the sentence introducing each block instead of trying to execute every block. For commands, pay close attention to the stated execution context: the guide consistently labels commands that belong in the Proxmox host as **Node → Shell** and commands for a particular LXC container as **LXC → Console**. Run commands exactly as shown unless the guide tells you to change something, and always replace placeholders first.

  For example, this harmless test belongs in a Linux shell:

  ```sh
  echo "Hello from your homelab"
  ```

- **Placeholders**: Throughout the guide, you'll see values wrapped in angle brackets like `<MY-DOMAIN>`, `<NODE>`, or `<IP-ADDRESS>`. These are placeholders. Replace them with your own values before running or saving anything.

- **Interface and execution labels**: Arrow-separated interface labels such as **Komodo → Stacks → New Stack** describe a path to follow in a web interface. Context labels such as **Node → Shell** and **LXC → Console** identify where a command must run.

- **Helper scripts**: The [Proxmox VE Helper-Scripts community project](https://community-scripts.org/) provides community-maintained automation for creating and configuring LXC containers, virtual machines, and applications. This guide uses its scripts at several points. Although the project is widely used and generally trusted, use only links reached through its official site, as this guide does, verify that the linked source is the one you intend to run, and review every script before executing it as `root`.

If you plan to differ from the example IP ranges, IDs, or any other values in the guide, keep a simple setup record containing your Proxmox node name, IP addresses, gateways, LXC IDs, hostnames, domain names, and other reusable values. Keep those choices consistent whenever their placeholders reappear. Store passwords, API tokens, encryption keys, and recovery codes separately in a password manager, not in ordinary notes.

The guide was tested multiple times, but hardware, router firmware, and software versions vary. If a command fails or a service doesn't behave as expected, read the error message carefully before searching for help. The message often identifies the cause. If the issue remains unresolved, ask the community on our [Discord server](https://discord.gg/TODO). If you confirm that the guide contains an incorrect or missing instruction, report it through the repository's [GitHub Issues page](https://github.com/TMD44/homelab-launchbook/issues).

Protect sensitive information when troubleshooting or asking for help. Never paste passwords, API tokens, onboarding keys, secret files, recovery codes, or unredacted credentials into GitHub issues, screenshots, logs, or public messages.

## Knowledge Requirements

This guide is written for **absolute beginners**, but it assumes you're comfortable with a few basics. You don't need to be a system administrator or networking expert. However, some background knowledge will make the setup easier to follow.

Here's what will genuinely help you follow along:

- **Basic Linux command line usage.** You'll be running commands in a terminal regularly. You don't need to be fluent, but you should know how to navigate directories, edit a file, run a command with `sudo`, and read an error message without panicking. If `cd`, `ls`, `nano`, and `cat` look familiar, you're in good shape.
- **Basic networking concepts.** Understanding what an IP address is, the difference between local and public networks, and what DNS and DHCP do will prevent confusion later. You don't need to know how to configure a router from scratch, just enough to understand why the network is configured this way.
- **A rough idea of what Docker is.** We use Docker containers for almost every service in this guide. You don't need to know how to write a `Dockerfile`, but you should understand that containers are lightweight, isolated environments and that `docker compose` defines and runs them. **[Komodo](https://komo.do/)** will handle most Docker operations for you.
- **A basic understanding of virtualization.** You should know the difference between a virtual machine and an LXC container and have a general idea of what a hypervisor does. Proxmox VE is a platform for creating and managing VMs and LXC containers.

If you're missing one or two of these skills, don't let that stop you. The goal isn't to filter anyone out, it is to be clear about the knowledge that will make the process smoother.

## Hardware Requirements

You don't need expensive, enterprise-grade hardware to follow this guide. Most of it can run on a used laptop or mini PC. The hardware you choose sets the limit on what you can run, so consider your requirements before you start.

You can also follow this guide by using **virtual machines** on your existing PC. VirtualBox is a practical option for learning and testing; follow [Setup Proxmox VE on VirtualBox](../TODO.md) for the repository's walkthrough. The host and desktop hypervisor must support nested virtualization. A virtualized lab is useful for exploring the setup before committing to physical hardware, but it is not the recommended long-term production setup.

### The Server

The server is the most important piece. It needs to support hardware virtualization (Intel VT-x or AMD-V), which Proxmox VE requires. Most modern x86-64 systems support this feature, but verify that it is available and enabled in the BIOS or UEFI settings.

A mini PC with an Intel N100 processor and 16 GB of RAM can be a cost-effective starter homelab. These systems are often fanless or quiet, use little power, and can run the services covered in this guide.

Power consumption is part of the long-term cost. Used enterprise systems can offer much more capacity for an attractive purchase price, but hardware that runs continuously may cost significantly more in electricity, so consider energy efficiency alongside performance.

For the number of services this guide sets up, use the following as a starting point:

| | Minimal | Recommended |
| ------------ | -------------------------------- | ------------------------------------------------------- |
| CPU | 4 cores, x86-64 with Intel VT-x or AMD-V | Modern 4–8 core CPU; IOMMU support if passthrough is planned |
| Memory | 16 GB RAM | 32 GB RAM or more |
| Boot storage | 250 GB SSD | 1 TB SSD/NVMe |
| Data storage | Optional | Separate SSD/NVMe pool, mirrored disks if possible |
| Network | 1 GbE wired Ethernet | 1 GbE wired Ethernet or faster |
| BIOS/UEFI | Virtualization enabled | Virtualization and IOMMU enabled |

Check the [Official System Requirements for Proxmox VE](https://www.proxmox.com/en/products/proxmox-virtual-environment/requirements).

### Storage

Plan your storage around the following required and optional devices:

- **OS drive (required):** A solid-state drive (SSD) where Proxmox VE and your LXC containers will live. 250 GB is the bare minimum, but 1 TB or more is highly recommended. Speed matters here more than capacity.
- **Data drive (optional):** A larger drive for storing persistent service data (databases, media, backups). This can be an HDD if you're on a budget.
- **USB flash drive (required only for installation):** Any drive with 8 GB or more capacity. It will be completely wiped during the Proxmox installation process.

### Networking

- **Ethernet cable:** A wired connection is strongly recommended. Wi-Fi works in a pinch, but it adds unnecessary complexity and instability to a server that is supposed to run 24/7.
- **Router with configurable DNS support:** Most home routers support this. You'll need to be able to set a custom DNS server address in your router settings.
- **Network switch (optional):** If your router doesn't have enough ports, a basic unmanaged switch is a cheap solution.

### Power

- **UPS (optional but recommended):** An uninterruptible power supply protects your server from unexpected power outages. Without one, a sudden outage can corrupt your data or leave a VM in a broken state. This guide includes a section on setting up UPS software if you have one.

### The Backup Server

A dedicated machine for **Proxmox Backup Server** is also recommended. Store backups on a separate physical device to prevent data loss if your main server fails. Backups are your final safety net against hardware failure, accidental deletion, and other disasters.

It can be another mini PC or an old laptop. It doesn't need to be nearly as powerful as the main server. It must meet the system requirements and have enough storage to store the backups. Proxmox Backup Server reuses identical chunks through deduplication, which can reduce the physical capacity required, but the saving depends on the data, change rate, and retention policy. Check the [Official System Requirements for Proxmox Backup Server](https://proxmox.com/en/products/proxmox-backup-server/requirements).

If you don't have another device to use as a backup server, you can create a virtual machine on your main server, but a backup stored on the same physical server cannot protect you from the loss of that server. For important data, follow the [3-2-1 backup rule](https://pbs.proxmox.com/docs/storage.html#the-3-2-1-rule-with-proxmox-backup-server).

## Network Planning

A few minutes of planning here will save you hours of headaches later. You don't need to design a full enterprise network, but making a couple of small decisions before you start will prevent you from having to redo things down the line.

This guide uses example addresses in the `192.168.0.X` range. If your router uses a different subnet or an example address is already in use, replace every affected IP address and gateway consistently before running the commands.

The reference setup intentionally uses IPv4 for its static LAN addresses. A **local subnet** is the range of addresses on the home network; the `/24` suffix in `192.168.0.100/24` is CIDR notation for the subnet mask `255.255.255.0`. The **default gateway** is the device that carries traffic beyond that subnet, normally the router's IP address `192.168.0.1` in later helper-script commands.

Your home router likely uses `192.168.0.X` or `192.168.1.X` by default. With the guide's assumed `/24` subnet (`255.255.255.0`), the subnet contains 256 total addresses: `.0` identifies the network, `.255` is the broadcast address, and `.1` through `.254` are usable host addresses. If the router occupies `.1`, the theoretical remainder is `.2` through `.254`.

The following table shows the example network values used in this guide:

| Network value | Guide example |
| --- | --- |
| Default gateway (Router) | `192.168.0.1` |
| Local subnet and CIDR | `192.168.0.0/24` |
| Subnet mask | `255.255.255.0` |
| Router DHCP pool | `192.168.0.2` - `192.168.0.253` |
| Proxmox VE management IP | `192.168.0.11` |
| DNS server IP | `192.168.0.101` |
| Reverse proxy IP | `192.168.0.102` |
| Chosen domain | `<MY-DOMAIN>.com` |

### LXC ID and IP Address Convention

This guide pairs the LXC ID with an IP address for convenience. This is not a requirement, but it can be a helpful and well-organized way to keep track of your containers.

For example, Komodo's LXC ID will be `100` and its static IP address will be `192.168.0.100`. The DNS server's LXC ID will be `101` and its static IP address will be `192.168.0.101`, and so on. This pairing is only a human-friendly convention: Proxmox does not derive or assign an IP address from an LXC ID, so both values must be configured correctly.

| LXC ID | IP Address | Service |
| --- | --- | --- |
| `100` | `192.168.0.100` | Komodo |
| `101` | `192.168.0.101` | DNS server |
| `102` | `192.168.0.102` | Reverse-proxy |
| `103` | `192.168.0.103` | VPN |

This guide uses IPv4-based addresses. If your network provides IPv6, plan IPv6 addressing, DNS, firewall policy, and exposure deliberately, and do not add IPv6 forwarding or advertised routes merely to mirror the reference commands.

### Assign static IP addresses

Your homelab server and its LXC containers need stable IP addresses. If an address changes after a reboot or reconnection, DNS entries, bookmarks, and service configurations can break. You can use either or both of the following methods:

- **Set a static IP directly in Proxmox** during LXC setup.
- **Reserve the IP in your router** by binding the server's MAC address to a specific IP (also called DHCP reservation).

Router interfaces vary, so study your router's documentation when creating DHCP reservations.

Proxmox creates `vmbr0` as its default Linux bridge and assigns the management address to that bridge. It acts like a virtual switch that connects the Proxmox host and attached LXC containers to the physical home LAN through the server's network interface.

### Point your router's DNS to your local DNS server

At first, the router acts as or advertises the DNS resolver for client devices. Once the local DNS server is set up (covered in its own chapter), you'll configure the router's DHCP settings to distribute the AdGuard Home address instead, while the router remains the default gateway. Local DNS resolves service hostnames such as `immich.<MY-DOMAIN>.com` to the reverse proxy, which then routes each request to the correct service. Most routers support this in their DHCP settings. Look for a field called **DNS Server** or **Primary DNS**.

The [Architecture chapter's request-flow explanation](../TODO.md) traces the complete **DNS → Traefik → optional authentication → service → response** path.

### Pick a domain name

This guide suggests a real, registered domain name for local service addresses (like `https://immich.<MY-DOMAIN>.com`). This lets the reverse proxy obtain valid HTTPS certificates through a DNS challenge without exposing the services or opening inbound ports to the Internet.

If you choose this approach and don't already own a domain, you'll need to obtain one. The dedicated custom-domain chapter explains the guide's Cloudflare-based registration and DNS setup.

### VLANs (advanced and optional)

VLANs let you split your network into isolated segments, for example keeping your homelab servers separate from your phones and laptops, or isolating IoT devices from everything else. This is a solid security practice and worth doing if your router and switch support it.

This guide does not use VLANs in the Initial Setup, but they can be configured later using the [Advanced guides](../TODO.md). If you're just getting started, you don't need to configure VLANs.

## Security Baseline

This guide runs real services on a real machine, so basic security practices matter even on a home network. You don't need to harden the server like a public cloud instance, but the following practices will help prevent common mistakes.

- **Use a password manager**: Every service you set up will have credentials: admin passwords, API keys, tokens. Generate unique, random passwords for every service.
- **Enable multi-factor authentication where possible**: Enable MFA on supported services, especially administrative interfaces. Store backup codes offline in case you lose access to your MFA device.
- **Use SSH keys, not passwords**: When connecting to your server over SSH, use key-based authentication. Password-based SSH is convenient but far weaker.
- **Keep management interfaces private**: Even if you plan to expose services to the public internet, keep management interfaces like the Proxmox web UI, Komodo, your DNS admin panel, and similar interfaces private. Use a VPN for remote access.
- **Keep everything updated**: Outdated software is a common cause of preventable security issues. This applies to Proxmox itself, the containers running inside it, Docker images, and any underlying Linux packages.
- **Principle of least privilege**: Where a service lets you create a non-root or limited user, do so. Don't run services as root unless there is no alternative. For example, the Proxmox VE setup guide creates a separate mobile app account with only the necessary permissions, instead of using the unrestricted `root@pam` administrator account.

The Homelab Launchbook is designed to be private by default. Management and service routes remain on the home network without public port forwarding, Tailscale VPN supplies secure remote access, Proxmox VE adds its management firewall and MFA, Traefik supplies private HTTPS and route-specific controls, CrowdSec evaluates only traffic connected to it, and Authelia adds centralized authentication and MFA only to compatible browser services. Unprivileged LXCs, separate Docker networks, limited tokens, protected secret files, monitoring, notifications, and backups provide layered defense, visibility, and recovery.
