# Notification Server

Gotify gives this homelab one private place to receive notifications and alerts from Proxmox VE, Komodo, and other services.

## About Gotify

[Gotify](https://gotify.net/) is a free, open-source, lightweight, and actively maintained self-hosted notification server. Services send messages to Gotify as **applications**, while the WebUI and official Android app act as **clients** that receive and manage those messages.

In this homelab, Gotify remains private to the trusted LAN and Tailscale network. Traefik provides its normal HTTPS endpoint; the direct HTTP listener exists only as a Traefik backend and for unauthenticated health diagnostics.

## Before You Begin

- Complete [Setup Reverse Proxy](4.1%20Setup%20Reverse%20Proxy.md) so the wildcard DNS record resolves private service hostnames to Traefik and the shared `websecure` entry point is ready.
- Confirm that Komodo Core is available at `192.168.0.100` and that the reverse proxy LXC uses `192.168.0.102`.
- This guide uses `104`, `gotify`, and `192.168.0.104/24`; replace any value that conflicts with your Proxmox VE inventory or network plan.
- Have a password manager ready for the Gotify account password and application tokens. An Android device is optional but required to complete the mobile-client tests.
- Keep `gotify.<MY-DOMAIN>.com` private. This guide does not require public DNS records or router port forwarding.

## Setup LXC

Create the Gotify LXC by running one of the following [Docker helper script](https://community-scripts.org/scripts/docker) commands on the Proxmox node (**Node → Shell**).

```sh
# Recommended: use the guide's predefined settings
mode=generated var_os=debian var_version=13 var_unprivileged=1 var_cpu=2 var_ram=2048 var_disk=4 var_ctid=104 var_hostname=gotify var_brg=vmbr0 var_net=192.168.0.104/24 var_gateway=192.168.0.1 var_nesting=1 var_keyctl=1 var_tags=essential var_protection=yes bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/docker.sh)"

# Alternative: launch the interactive installer
bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/docker.sh)"
```

Use these settings as the acceptance baseline:

| Setting | Reference value |
| --- | --- |
| Container type | Unprivileged |
| Operating system | Debian 13 |
| Container ID | `104` |
| Hostname | `gotify` |
| Disk size | 4 GiB |
| CPU cores | 2 |
| RAM | 2048 MiB |
| Network bridge | `vmbr0` |
| IPv4 configuration | Static: `192.168.0.104/24`; gateway: `192.168.0.1` |
| Container tag | `essential` |
| Nesting | Enabled |
| Keyctl | Enabled |
| Container protection | Enabled |
| Start at boot | Enabled by the helper |

The Docker helper currently requires its `2` CPU and `2048` MiB application baseline even though Gotify itself is lightweight. During Docker installation, decline Portainer, the Portainer Agent, and Docker TCP socket exposure. Komodo will manage this Docker host and does not require an additional management UI or an insecure TCP listener. FUSE, TUN/TAP, and device passthrough are not required.

If the helper prompts for storage, select the template and LXC storage defined by your storage plan. Treat failed network, DNS, package, template, or Docker checks as blockers instead of continuing from a partial installation.

The helper script must finish successfully. Then verify the LXC's settings from the UI or the Proxmox node (**Node → Shell**):

```sh
pct status 104
pct config 104
```

Confirm that the LXC is running, starts at boot, is unprivileged and protected, uses the intended resources, static address, and bridge, and has nesting and keyctl enabled. Resolve any mismatch before continuing.

Open the Gotify LXC (**LXC → Console**) and verify its address, time synchronization, Docker installation, and DNS resolution:

```sh
ip -brief address
timedatectl status
docker version
getent hosts raw.githubusercontent.com
```

The intended static address must be present, the clock must be synchronized, `docker version` must show both client and server information, and the hostname lookup must return an address.

## Setup Komodo Periphery

Connect the Docker LXC to Komodo so that the Gotify stack can be deployed and monitored from Komodo Core.

### Create Onboarding Key

Go to **Komodo → Settings → Onboarding → Create New Onboarding Key**.

- **Name:** `104-gotify`
- **Expiry:** `1 day`
- Leave **Privileged** disabled, make sure **Enabled** is selected, create the key, and copy it. Privileged onboarding is unnecessary for a new server and would allow the key to update public keys on existing servers.

### Install Komodo Periphery

On the Gotify LXC (**LXC → Console**), run the setup script below:

```sh
curl -sSL https://raw.githubusercontent.com/moghtech/komodo/main/scripts/setup-periphery.py \
  | python3 - \
  --core-address="http://192.168.0.100:9120" \
  --connect-as="104-gotify" \
  --onboarding-key="<ONBOARDING_KEY>"
```

Enable Periphery at boot and verify its state:

```sh
systemctl enable periphery
systemctl is-enabled periphery
systemctl is-active periphery

systemctl status periphery
```

The last two commands must report `enabled` and `active`. Return to **Komodo → Servers** and verify that the Gotify LXC is listed with an **OK** connection status. After the connection succeeds, disable or delete the onboarding key because it is no longer needed. See the [Komodo server connection documentation](https://komo.do/docs/setup/connect-servers) for the current script behavior and troubleshooting steps.

## Setup Gotify

Deploy Gotify through Komodo using the repository-owned stack templates, verify that the service and its database are healthy, and then configure private HTTPS access through Traefik.

### Create Docker Stack

Create the stack in Komodo using the repository-owned Compose and environment templates:

1. Go to **Komodo → Stacks → New Stack** and enter:
   - **Stack Name:** `gotify`
   - **Server:** `104-gotify`
   - **Choose Mode:** UI Defined
   - **Compose File:** paste [`gotify-compose.yaml`](../Application%20Library/Notifications%20%26%20Alerting/Gotify/gotify-compose.yaml)
   - **Environment:** paste [`gotify.env`](../Application%20Library/Notifications%20%26%20Alerting/Gotify/gotify.env)
   - **Poll for Updates:** enabled
   - **Auto Update:** disabled
   - **Full Stack Auto Update:** disabled
   - **Links:** `https://gotify.<MY-DOMAIN>.com`
2. Create and deploy the stack. Keep automatic deployment disabled because the repository pins an exact Gotify release and upgrades require a backup and release-note review.
3. Confirm in Komodo that the `gotify` Docker container is running and healthy.

Verify the unauthenticated backend health endpoint inside the Gotify LXC (**LXC → Console**):

```sh
curl -fsS http://127.0.0.1:8080/health
```

Continue only when the response reports both application and database health as green. Port `8080` is the private Traefik upstream; do not use the direct HTTP address for account sign-in, clients, tokens, or sender integrations, and do not expose it through public DNS or router port forwarding.

### Configure HTTPS Access with Traefik

The wildcard DNS record created earlier already directs `gotify.<MY-DOMAIN>.com` to the reverse proxy LXC. This step installs the repository's Gotify router so Traefik can forward private HTTPS traffic to `http://192.168.0.104:8080`.

In the Traefik configuration editor, create `/TRAEFIK/config/dynamic/gotify.yaml` from the repository's [`gotify.yaml`](../Application%20Library/Reverse%20Proxies/Traefik/Config%20files/Traefik/dynamic/gotify.yaml) template with these file contents:

```yaml
# Later-service template: install only when Gotify is deployed.
http:
  routers:
    gotify:
      entryPoints:
        - websecure
      rule: Host(`gotify.<MY-DOMAIN>.com`)
      middlewares:
        - secured@file
      service: gotify

  services:
    gotify:
      loadBalancer:
        passHostHeader: true
        servers:
          - url: http://192.168.0.104:8080
```

Replace `<MY-DOMAIN>` before saving. The shared `websecure` entry point supplies TLS and the wildcard certificate, so this router does not need its own certificate resolver. `secured@file` retains the private-client, CrowdSec, headers, and rate-limit protections without adding Authelia in front of Gotify's WebUI, Android client, REST API, or WebSocket traffic. Traefik handles WebSocket upgrades automatically; do not add obsolete upgrade-header middleware.

Gotify trusts forwarded headers only from the reverse proxy LXC address `192.168.0.102/32`, as configured in the Compose file. If either LXC address changes, update the router backend and trusted-proxy value together.

Traefik watches the dynamic directory and should load the new file without a container or stack restart. Check the focused provider output inside the Traefik LXC (**LXC → Console**):

```sh
docker logs --since 5m traefik 2>&1 | grep -Ei 'gotify|dynamic|file|error|middleware|router'
curl -fsS https://gotify.<MY-DOMAIN>.com/health
```

Review the logs rather than assuming that no output proves success. Continue only when Traefik reports no parse, middleware, router, or provider error for Gotify and the HTTPS health response is green. If validation fails, remove or correct only `gotify.yaml`; Traefik will return to the previous watched configuration without an unrelated stack restart.

### Application Configuration

1. Open `https://gotify.<MY-DOMAIN>.com` and sign in with the default user name and password.
2. Open the `Users` menu, change the account username and password to something you will remember and store it in your password manager.
3. Create a dedicated mobile user without admin privileges.

### Connect a Notification Client

Gotify's official mobile client is available for Android through [Google Play](https://play.google.com/store/apps/details?id=com.github.gotify), [F-Droid](https://f-droid.org/packages/com.github.gotify/), and signed APKs on the [official GitHub releases page](https://github.com/gotify/android/releases). Install from one of those official sources.

1. Open the Android app and add `https://gotify.<MY-DOMAIN>.com` as the server.
2. Sign in with the previously created **mobile user**.
3. Allow Gotify to post notifications when prompted.
4. Follow the official client's battery guidance and exempt Gotify from battery optimization if delayed or missing background notifications occur. Keep its foreground service notification enabled when reliable persistent delivery is required.
5. While the device is on the trusted LAN, confirm that the app reports a connected state.
6. After creating the first application token in the next section, send a controlled test message and confirm that it arrives on the Android device while still on the LAN.
7. Disconnect from Wi-Fi, connect Tailscale on the device with the tailnet's private DNS and required subnet routes accepted, and repeat the test over cellular. Do not continue if the private hostname resolves publicly or works without the intended LAN/Tailscale path.

Receiving the message in real time through both the WebUI and Android client also verifies the proxied WebSocket path. Gotify does not provide an official iOS client; do not present third-party iOS applications as official or equivalent to this tested path.

### Connect a Service to Gotify

In Gotify, an **application** represents a service that sends messages, while a **client** receives and manages them. Create a separate application and token for each sender so its messages remain identifiable and its access can be revoked independently.

1. In Gotify UI, go to **Apps → Create Application** and enter:
   - **Name:** `<SERVICE>`
   - **Description:** `<SERVICE> notifications`
2. Create the application. Gotify shows tokens only when they are created or rotated, so copy the **application token** immediately into your password manager or the sender's supported secret store.
3. Open the service's notification or integration settings and select its native Gotify integration when available.
4. Enter `https://gotify.<MY-DOMAIN>.com`, the dedicated application token, and only the event, title, or priority options supported by that service. Exact field names vary; follow the sender's current Gotify documentation.
5. Save the integration and send a test notification.
6. Confirm that the message appears under the correct application in the Gotify WebUI and reaches the intended client.

If the sender has no native Gotify integration, a compatible webhook or the [Gotify push-message API](https://gotify.net/docs/pushmsg) is an advanced fallback. A generic webhook is suitable only if it can send Gotify's required request. Prefer a dedicated token or header field, never place the token in a URL or log when a safer field exists, and rotate or delete a token that is exposed or no longer needed.

### Connect Existing Homelab Services

Apply the generic sender procedure to the two management systems already present in this homelab. Give each system its own Gotify application token and test it independently.

#### Connect Proxmox VE to Gotify

Proxmox VE currently includes a native Gotify notification target and notification matchers. Configure it through the cluster-wide notification system rather than a custom webhook:

1. In Gotify, create an application named `Proxmox VE` and store its application token.
2. In Proxmox VE, go to **Datacenter → Notifications → Notification Targets → Add → Gotify** and enter:
   - **Name:** `gotify`
   - **Server:** `https://gotify.<MY-DOMAIN>.com`
   - **Token:** the dedicated `Proxmox VE` application token
3. Keep certificate verification enabled. The private hostname uses the trusted wildcard certificate supplied by Traefik.
4. Save the target and use its **Test** action. Confirm receipt under the `Proxmox VE` application in the WebUI and Android client.
5. Under **Datacenter → Notifications → Notification Matchers**, create or edit a matcher that targets `gotify` and selects severities `warning` and `error`.

The warning/error baseline covers important failures such as failed backup or replication jobs and other high-severity system events without forwarding routine `info` and `notice` traffic. Add lower-severity or event-specific rules only when they are useful and do not create alert fatigue. On `/mapping/notifications`, creating or changing a target requires `Mapping.Modify`, viewing its configuration requires `Mapping.Audit`, and sending a test requires at least one of `Mapping.Use`, `Mapping.Audit`, or `Mapping.Modify`. Use an administrative account for initial setup, then grant delegated operators only the permissions their role needs. See the current [Proxmox VE notification documentation](https://pve.proxmox.com/pve-docs/pve-admin-guide.pdf) for version-specific event and matcher options.

#### Connect Komodo to Gotify

Current Komodo releases do not list a native Gotify endpoint. The repository therefore uses FoxxMD's community `komodo-gotify-alerter`, an HTTP receiver that Komodo calls as a **Custom** Alerter; the receiver then pushes the alert to Gotify. It does not require or use Komodo API credentials.

1. In Gotify, create an application named `Komodo` and store its application token.
2. In **Komodo → Settings → Variables**, create `GOTIFY_APP_TOKEN`, paste the token, and mark the variable as secret.
3. Confirm that Komodo Core owns the `komodo_default` Docker network on server `100-komodo`. Check inside the Komodo LXC (**LXC → Console**):

   ```sh
   docker network inspect komodo_default
   ```

4. In **Komodo → Stacks → New Stack**, create `komodo-gotify-alerter` on server `100-komodo` in UI Defined mode:
   - **Compose File:** paste [`komodo-gotify-alerter-compose.yaml`](../Application%20Library/Notifications%20%26%20Alerting/Gotify/Integrations%20%26%20Extensions/komodo-gotify-alerter/komodo-gotify-alerter-compose.yaml)
   - **Environment:** paste [`komodo-gotify-alerter.env`](../Application%20Library/Notifications%20%26%20Alerting/Gotify/Integrations%20%26%20Extensions/komodo-gotify-alerter/komodo-gotify-alerter.env), then replace `<MY-DOMAIN>`
   - **Auto Update:** disabled
   - **Full Stack Auto Update:** disabled
5. Deploy the stack and confirm that `komodo-gotify-alerter` joins `komodo_default`. The Compose file deliberately does not publish port `7000`; Komodo Core reaches it through the shared private Docker network.
6. Go to **Komodo → Alerters → New Alerter**, choose **Custom**, and enter:
   - **Name:** `gotify`
   - **Endpoint:** `http://komodo-gotify-alerter:7000`
   - **Enabled:** enabled
7. Select only useful alert types initially, such as server or stack failures and important recovery events. Save the alerter and use **Test Alerter**.
8. Confirm receipt under the `Komodo` application in the WebUI and Android client. If the internal endpoint fails, verify that both Komodo Core and the receiver are attached to the exact `komodo_default` network before considering any host-port publication.

The alerter image is pinned to a repository-reviewed revision rather than `latest`. Review the [upstream deployment example](https://github.com/FoxxMD/deploy-gotify-alerter) and retest the callback before changing that revision or its optional severity mapping.

### Maintain and Recover Gotify

- **Routine update:** read the [Gotify release notes](https://github.com/gotify/server/releases), confirm migration requirements, take a known-good backup of `/GOTIFY/data` and the protected bootstrap secret, update the exact `VERSION`, redeploy, and repeat backend health, HTTPS, sign-in, sender, and client tests. Gotify 3 tokens are shown only on creation or rotation, so verify that stored integration tokens remain available before a migration.
- **Rollback:** stop the failed version, restore the matching `/GOTIFY/data` backup, restore the previous exact image version, and redeploy. Do not attempt a database rollback without a backup created before the upgrade.
- **Credential recovery:** changing the bootstrap secret does not change an existing database account. Use the password-manager credential or restore a known-good data backup; do not delete the database merely to regain access.
- **Decommissioning:** revoke sender tokens, disconnect clients, remove `/TRAEFIK/config/dynamic/gotify.yaml`, and stop the stack. Delete `/GOTIFY/data` or its backups only after confirming that their notification history, users, and tokens are no longer required and that LXC protection has been deliberately disabled for the final removal.
