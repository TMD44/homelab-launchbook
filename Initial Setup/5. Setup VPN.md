# VPN

Tailscale adds secure remote access to the homelab. When this chapter is complete, approved phones and computers can resolve your homelab domain and reach Traefik from outside the home without router port forwarding.

The earlier application-focused chapters create LXC containers with Docker and deploy services as Docker containers. This design instead installs Tailscale directly as a systemd-managed service in a small, dedicated Debian LXC container. Its sole role is to route traffic to the DNS server and reverse proxy; it does not expose the rest of the home subnet or route ordinary internet traffic.

## About Tailscale

[Tailscale](https://tailscale.com/) is a WireGuard-based mesh VPN that connects authenticated devices in a private network called a tailnet. Its [clients are open source and actively maintained](https://github.com/tailscale/tailscale), while Tailscale operates the proprietary coordination service. A [free Personal plan](https://tailscale.com/pricing) is available; review the current plan limits before relying on a feature outside this guide.

This guide selects Tailscale because it combines encrypted device connections, identity-based access controls, and straightforward subnet routing. It is the repository's preferred privacy-by-design remote-access path: homelab services retain no public application record or inbound router port forward, which reduces their public attack surface. That trade-off fits this reference architecture but is not a universal answer for every environment.

## How Tailscale Provides Remote Access

Tailscale can connect devices directly, or it can use a subnet router when the destination cannot run a Tailscale client. Understanding that distinction makes the routing, DNS, and access-control steps below easier to verify.

### Tailnets, Clients, and Identity

A **tailnet** is the private network associated with a Tailscale account or organization. Each phone, computer, or server runs a Tailscale client and receives a cryptographic node identity. The identity provider protects user sign-in, device approval determines which hardware may join, and the tailnet policy determines what an approved identity may reach.

Installing a Tailscale client directly on every destination provides the clearest end-to-end identity and encryption boundary. AdGuard Home and Traefik do not run Tailscale in this reference design, so a native Tailscale system service in the Debian LXC acts as a [subnet router](https://tailscale.com/docs/features/subnet-routers). It receives encrypted traffic from a remote client, decrypts it, and forwards ordinary IP traffic to the selected LAN destination.

Running `tailscaled` directly under systemd avoids adding a Docker networking layer to this gateway. Keeping it in a dedicated LXC instead of on the Proxmox VE node also limits host-level changes and gives remote access a separate update, backup, recovery, and failure boundary. The trade-off is that the LXC must remain available whenever remote access is needed.

The router uses the non-human identity `tag:subnet`. A tag owner is allowed to assign that identity, but tag ownership does not itself grant network access. The separate Grant created later names the users, destinations, protocols, and ports that are allowed.

### The Reference Request Path

The two advertised `/32` routes represent individual hosts rather than the complete `192.168.0.0/24` home subnet:

```text
Remote Tailscale client
  → encrypted Tailscale connection
  → subnet router at 192.168.0.103
  ├─ DNS on 192.168.0.101:53
  └─ HTTP/HTTPS on 192.168.0.102:80/443
       → Traefik middleware and routing
       → selected private service
```

When a client requests `service.<MY-DOMAIN>.com`, Tailscale split DNS sends only that domain's queries to AdGuard Home. AdGuard Home returns `192.168.0.102`, and the client's HTTPS request follows the second `/32` route to Traefik. Traefik then applies the private-client, CrowdSec, TLS, and optional Authelia policies established in the reverse-proxy chapter.

A `/32` selects one IPv4 address. Routers, NAS devices, printers, IoT networks, and other LAN destinations remain outside this path unless an administrator deliberately advertises and authorizes them. The single `.102` route can still reach multiple applications because Traefik selects a backend from the requested hostname and then applies its middleware and application controls.

Cloudflare remains the public authoritative DNS provider and supports ACME DNS-01 certificate validation in this repository, but it is not in this private application request path. Tailscale protects access to the private network path, while HTTPS protects and authenticates the browser-facing request through Traefik.

### Routes, Grants, and DNS

The controls operate at different layers and are intentionally cumulative:

| Control | Reference scope | Purpose |
| --- | --- | --- |
| Advertised routes | `192.168.0.101/32`, `192.168.0.102/32` | Make only the DNS server and reverse proxy reachable through this router. |
| Grant | TCP/UDP `53` to `.101`; TCP `80`/`443` to `.102` | Restrict approved users to the required services and ports. |
| Device approval | Manually reviewed clients and router | Prevent an authenticated but unapproved device from exchanging tailnet traffic. |
| Split DNS | `<MY-DOMAIN>.com` only | Send private homelab names to AdGuard Home without replacing unrelated DNS resolution. |

A subnet route is not an access grant. Approving a route makes a path available, while the tailnet policy decides whether a source may use that path. Likewise, `tag:subnet` identifies the router; it does not give the router or its owner unrestricted access.

Linux IP forwarding lets the LXC pass packets between interfaces. The Tailscale client then advertises the two routes, and an administrator separately approves them in the control plane. A new tailnet begins with allow-all access, so the route and tag become least privilege only after the port-scoped Grant replaces that default.

[MagicDNS](https://tailscale.com/docs/features/magicdns) is a separate convenience that assigns names to Tailscale devices and is enabled by default on modern tailnets. It may be enabled or disabled and is not required for the restricted nameserver used here. An exit node is also different: it offers a default route for a client's internet traffic. This chapter advertises only two host routes and does not configure an exit node, so the client's normal internet connection remains unchanged.

Tailscale applies source NAT to subnet-routed traffic by default. This guide retains that default because it avoids adding a `100.64.0.0/10` return route to the LAN and matches the reverse-proxy configuration. AdGuard Home, Traefik, and CrowdSec will normally see `192.168.0.103` as the source instead of the individual remote client's Tailscale address. This simplifies routing but reduces downstream per-client attribution; use the Tailscale configuration audit records and, where available, network flow logs alongside the service logs.

### Encryption, Trust, and Availability

Tailscale clients generate their private node keys locally. The coordination service distributes public connection information, and DERP relays carry encrypted traffic when a direct peer-to-peer path is unavailable. Tailscale still processes account, device, public-IP, connection, and policy metadata needed to coordinate the service, so using the hosted control plane is a deliberate SaaS trust decision. Review Tailscale's [security model](https://tailscale.com/security) and [privacy policy](https://tailscale.com/privacy-policy) for the current details.

The WireGuard-protected path ends at the subnet router. Traffic from `192.168.0.103` to AdGuard Home is ordinary LAN DNS traffic, while browser traffic receives another protected layer from the HTTPS connection terminated by Traefik. Protect the router as a security boundary, keep its software updated, and do not add unrelated workloads to it.

This setup has one subnet router, one DNS server, and one reverse proxy. If any of them is offline, the corresponding remote path is unavailable. Tailscale deliberately fails closed when an expired connector key makes an advertised route unreachable. Tagged-device key expiry is disabled by default; the one-day auth-key lifetime does not disconnect the enrolled router. The reference path retains that availability choice and compensates with manual approval, a one-off enrollment key, least-privilege policy, updates, and periodic device review. Redundant subnet routers are a possible future availability improvement, not part of this initial setup.

> [!NOTE]
> [Tailnet Lock](https://tailscale.com/docs/features/tailnet-lock) can reduce trust in control-plane key distribution, but it requires signing-node and disablement-secret operations. Tailscale does not permit Tailnet Lock and device approval at the same time. This guide uses device approval; adopting Tailnet Lock requires a separate enrollment and recovery design.

## Before You Begin

Complete and verify the DNS server, custom-domain, reverse-proxy, and code-server chapters first. AdGuard Home must answer private wildcard queries with `192.168.0.102`, Traefik must be the only host publishing ports `80` and `443`, and the home router must have no inbound port forwards for these services.

Prepare the following before changing the tailnet:

- A Tailscale owner or administrator account protected by multifactor authentication at its identity provider.
- Direct **Node → Shell** and **LXC → Console** access in case routing, DNS, or policy changes interrupt remote access.
- A trusted phone or computer that can be tested on a mobile or other network outside the home LAN.
- A copy of the current tailnet policy. Saving a new policy affects the entire tailnet, including existing devices.
- An unused and reserved LXC ID and IPv4 address. Keep static homelab addresses outside the DHCP pool or create reservations.

The guide uses these coherent reference values. Adapt them before running commands, then replace every later occurrence consistently:

| Purpose | Reference value |
| --- | --- |
| LXC ID | `103` |
| LXC and Tailscale machine name | `tailscale-subnet` |
| Bridge / IPv4 / gateway | `vmbr0` / `192.168.0.103/24` / `192.168.0.1` |
| DNS server route | `192.168.0.101/32` |
| Reverse proxy route | `192.168.0.102/32` |
| Private DNS suffix | `<MY-DOMAIN>.com` |
| Subnet-router identity | `tag:subnet` |
| Allowed-user group | `group:homelab-users` |
| Tailscale login selector | `<TAILSCALE-USER>` |

Replace `<TAILSCALE-USER>` with the full login email shown on the Tailscale **Users** page. It is a policy selector, not a display name. Never put an auth key, password, recovery code, or other secret in ordinary setup notes.

## Setup LXC

Create the Tailscale LXC by running one of the following [Debian helper script](https://community-scripts.org/scripts/debian) commands on the Proxmox node (**Node → Shell**).

```bash
# Recommended: use the guide's predefined settings
mode=generated var_unprivileged=1 var_nesting=0 var_keyctl=0 var_tun=yes var_cpu=1 var_ram=256 var_disk=4 var_ctid=103 var_hostname=tailscale-subnet var_brg=vmbr0 var_net=192.168.0.103/24 var_gateway=192.168.0.1 var_tags=essential var_protection=yes bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/debian.sh)"

# Alternative: launch the interactive installer
bash -c "$(curl -fsSL https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/ct/debian.sh)"
```

Use these settings as the acceptance baseline:

| Setting | Reference value |
| --- | --- |
| Container type | Unprivileged |
| Container ID | `103` |
| Hostname | `tailscale-subnet` |
| Disk size | 4 GiB |
| CPU cores | 1 |
| RAM | 256 MiB |
| Network bridge | `vmbr0` |
| IPv4 configuration | Static: `192.168.0.103/24`; gateway: `192.168.0.1` |
| Container tag | `essential` |
| Nesting | Disabled |
| Keyctl | Disabled |
| TUN/TAP | Enabled |
| Container protection | Enabled |

These resources provide modest update headroom rather than universal minimum requirements. Tailscale needs the TUN device, but it does not need Docker, nesting, keyctl, FUSE, a privileged container, or broad device access. Proxmox documents the security impact of optional LXC features in the [`pct.conf` reference](https://pve.proxmox.com/pve-docs/pct.conf.5.html).

Use only one creation command. If you launch the interactive installer, select an unprivileged Debian LXC, enable TUN/TAP, leave nesting and keyctl disabled, and reproduce the planned network and protection settings. The downloaded script runs as root on the Proxmox node, so use only the official project link and inspect it before execution.

The helper script must finish successfully. Then verify the LXC's settings from the UI or the Proxmox node (**Node → Shell**):

```bash
pct status 103
pct config 103
```

Confirm that the LXC is running, is unprivileged and protected, uses the intended resources, static address, and bridge, has TUN/TAP enabled, and has nesting and keyctl disabled. Resolve any mismatch before continuing.

Open the Tailscale LXC (**LXC → Console**) and verify its address, time synchronization, default route, TUN device, and DNS resolution:

```sh
ip -brief address
timedatectl status
ip -4 route
test -c /dev/net/tun && echo "TUN device available."
getent ahostsv4 tailscale.com
```

The intended static address must be present, the clock must be synchronized, the default route must use `192.168.0.1`, `/dev/net/tun` must be a character device, and the hostname lookup must return an address. A DNS, route, template, package, or TUN failure blocks the setup. Correct failures through direct Proxmox access, and do not enable unrelated container features as a workaround.

## Setup Tailscale

Prepare the router's identity and least-privilege policy before enrollment, then configure Linux forwarding, install Tailscale, approve the exact routes, and test the complete path from outside the home LAN. Keep the direct Proxmox console available until every positive and negative check succeeds.

### Create the Subnet-Router Tag and Auth Key

Sign in to the [Tailscale admin console](https://login.tailscale.com/admin) with the MFA-protected identity provider selected for the tailnet, such as GitHub or Google.

1. **Enable device approval:** Open **Settings → Device management** and select **Enable device approval**. If Tailnet Lock is already enabled, stop and choose which enrollment model to use; Tailscale does not allow both features simultaneously.
2. **Create the subnet-router tag:** Go to **Access controls → Tags → Create tag** and enter:

   - **Tag name:** `tag:subnet`
   - **Tag owner:** `autogroup:admin`
   - **Note:** `Homelab subnet routers`

3. **Generate the enrollment key:** Go to **Settings → Keys → Generate auth key** and enter:

   - **Description:** `One-off enrollment for tailscale-subnet`
   - **Reusable:** disabled
   - **Ephemeral:** disabled; this is a persistent infrastructure node
   - **Pre-approved:** disabled; the router will be reviewed manually
   - **Expiration:** `1 day`
   - **Tags:** `tag:subnet`

The key is displayed once. Place it temporarily in a password manager and remove it after successful enrollment. Do not paste it into a command, ordinary note, issue, screenshot, or log. Tailscale automatically revokes a one-off key after it is used; revoking an auth key later would not deauthorize a node already enrolled with it.

The key assigns `tag:subnet` as the machine identity, replacing user identity on the router. End-user phones and computers must remain signed in as users and must not receive this tag. For more detail, see Tailscale's documentation for [tags](https://tailscale.com/docs/features/tags), [auth keys](https://tailscale.com/docs/features/access-control/auth-keys), and [device approval](https://tailscale.com/docs/features/access-control/device-management/device-approval).

### Configure Tailnet Access Controls

Tailscale uses a default allow-all policy until the tailnet policy file contains explicit access controls. The following [Grant](https://tailscale.com/docs/features/access-control/grants) permits members of `group:homelab-users` to use DNS through AdGuard Home and HTTP/HTTPS through Traefik, specifically through a router carrying `tag:subnet`. TCP `80` remains allowed because the canonical Traefik configuration redirects it permanently to HTTPS.

> [!WARNING]
> A tailnet policy is global. Keep the current policy in a protected change record, retain direct local access to managed systems, and inspect all existing Grants and ACLs before saving. Policies are additive: an old allow-all rule would override the intended restriction. If this tailnet already serves other systems, merge the group, tag owner, Grants, and tests into its policy instead of deleting unrelated required rules.

Go to **Access controls → JSON editor**. Replace `<TAILSCALE-USER>` with the full login email from the **Users** page, remove the default allow-all rule, and use this as the complete policy for a new reference tailnet:

```json
{
  "groups": {
    "group:homelab-users": [
      "<TAILSCALE-USER>"
    ]
  },
  "tagOwners": {
    "tag:subnet": [
      "autogroup:admin"
    ]
  },
  "grants": [
    {
      "src": [
        "group:homelab-users"
      ],
      "dst": [
        "192.168.0.101"
      ],
      "via": [
        "tag:subnet"
      ],
      "ip": [
        "tcp:53",
        "udp:53"
      ]
    },
    {
      "src": [
        "group:homelab-users"
      ],
      "dst": [
        "192.168.0.102"
      ],
      "via": [
        "tag:subnet"
      ],
      "ip": [
        "tcp:80",
        "tcp:443"
      ]
    }
  ],
  "tests": [
    {
      "src": "<TAILSCALE-USER>",
      "proto": "tcp",
      "accept": [
        "192.168.0.101:53",
        "192.168.0.102:80",
        "192.168.0.102:443"
      ],
      "deny": [
        "192.168.0.1:443",
        "192.168.0.101:22",
        "192.168.0.101:80",
        "192.168.0.101:3000",
        "192.168.0.102:22",
        "192.168.0.102:53"
      ]
    },
    {
      "src": "<TAILSCALE-USER>",
      "proto": "udp",
      "accept": [
        "192.168.0.101:53"
      ],
      "deny": [
        "192.168.0.1:53",
        "192.168.0.102:53"
      ]
    }
  ]
}
```

Use **Preview rules** to inspect the effective permissions for `<TAILSCALE-USER>`, then save. Tailscale runs the built-in policy tests on every change and rejects the policy if an assertion fails. Confirm that the saved policy contains no other rule granting broader access to these addresses.

If the change affects an existing tailnet unexpectedly, restore the recorded policy or use the previous revision in **Logs → Configuration**. Do not restore connectivity by adding a temporary allow-all rule; fix the missing intentional permission and add a test for it.

### Enable IPv4 Forwarding

Linux must forward IPv4 packets between `tailscale0` and the LXC's LAN interface. The reference routes are IPv4-only, so enabling global IPv6 forwarding would add unused attack surface.

The following command owns one dedicated sysctl file and is safe to rerun. If that file already exists, it preserves one rollback copy before replacing it. Run it inside the subnet-router LXC (**LXC → Console**):

```bash
if test -e /etc/sysctl.d/99-tailscale.conf && \
   ! test -e /etc/sysctl.d/99-tailscale.conf.before-vpn; then
  cp -a /etc/sysctl.d/99-tailscale.conf \
    /etc/sysctl.d/99-tailscale.conf.before-vpn
fi

cat >/etc/sysctl.d/99-tailscale.conf <<'EOF'
net.ipv4.ip_forward = 1
EOF

sysctl -p /etc/sysctl.d/99-tailscale.conf
test "$(sysctl -n net.ipv4.ip_forward)" = "1" && \
  echo "IPv4 forwarding enabled."
```

The final command must print `IPv4 forwarding enabled.`. If it does not, stop and inspect the sysctl output. The `/32` route advertisements, protocol-and-port Grants, device approval, and Tailscale's default netfilter mode constrain how this forwarding can be used. Do not add a broad forwarding exception to the Proxmox or LXC firewall.

To roll back before enrollment, run the following inside the subnet-router LXC (**LXC → Console**). The first path restores the preserved file; the second removes the guide-owned file and returns forwarding to the disabled state expected before this setup:

```bash
if test -e /etc/sysctl.d/99-tailscale.conf.before-vpn; then
  mv /etc/sysctl.d/99-tailscale.conf.before-vpn \
    /etc/sysctl.d/99-tailscale.conf
  sysctl -p /etc/sysctl.d/99-tailscale.conf
else
  rm -f /etc/sysctl.d/99-tailscale.conf
  sysctl -w net.ipv4.ip_forward=0
fi
```

### Install and Configure Tailscale

Tailscale publishes a stable Debian package through its official installer. Review the current [Linux installation instructions](https://tailscale.com/docs/install/linux) and installer source before piping it into a root shell.

Install the stable package inside the subnet-router LXC (**LXC → Console**):

```bash
curl -fsSL https://tailscale.com/install.sh | sh
systemctl is-enabled tailscaled
systemctl is-active tailscaled
apt-cache policy tailscale
tailscale version
```

Both systemd checks must report `enabled` and `active`. The package policy must show an installed stable Tailscale package from Tailscale's package repository. Record the installed version in the setup record, but do not describe that version as permanently preferred.

The next block reads the one-off auth key without echoing it, stores it temporarily in a root-only runtime file, and removes the file even if enrollment fails. The command line contains only the file path, not the secret. Run the complete block inside the subnet-router LXC (**LXC → Console**):

```bash
(
  set -eu
  AUTH_KEY_FILE=/run/tailscale-auth-key
  trap 'rm -f "$AUTH_KEY_FILE"' EXIT
  umask 077
  install -m 0600 /dev/null "$AUTH_KEY_FILE"
  read -r -s -p 'Paste the one-off Tailscale auth key: ' TS_AUTH_KEY
  printf '\n'
  printf '%s' "$TS_AUTH_KEY" >"$AUTH_KEY_FILE"
  unset TS_AUTH_KEY

  tailscale up \
    --auth-key="file:$AUTH_KEY_FILE" \
    --hostname=tailscale-subnet \
    --advertise-routes=192.168.0.101/32,192.168.0.102/32 \
    --netfilter-mode=on \
    --snat-subnet-routes=true

  rm -f "$AUTH_KEY_FILE"
  trap - EXIT
  tailscale set --auto-update=true
  tailscale ip -4
  tailscale status
)
```

The tagged auth key assigns `tag:subnet`, so a redundant `--advertise-tags` flag is unnecessary. The command explicitly retains Tailscale's normal netfilter management and subnet-route SNAT. It does not advertise an exit node, enable Tailscale SSH, accept other subnet routes, or expose the complete LAN.

The router may report that it needs approval, and its routes remain unusable until the next section. Confirm that the machine name is `tailscale-subnet`, that the status contains no unrelated health error, and that `/run/tailscale-auth-key` no longer exists. Remove the temporary key from the password manager. Protect `tailscale status` output because it can contain device names, identities, and addresses.

If enrollment fails or the key's secrecy is uncertain, revoke that key from **Settings → Keys** before generating a replacement. Do not make it reusable or extend its lifetime as a troubleshooting shortcut.

Use `tailscale set` for later preference changes. Re-running `tailscale up` requires restating all non-default preferences and can unintentionally remove an advertised route or change the security model.

### Optional: Optimize Linux Forwarding Performance

Most homelabs need no extra tuning. Tailscale documents UDP throughput improvements for Tailscale `1.54` or later on Linux kernel `6.2` or later, but only when the virtual network device exposes both required offload features. The same upstream optimization applies to exit nodes, but this LXC is configured only as a subnet router. This optional step appears after installation so the actual Tailscale version can be checked. Skip it unless higher routed throughput matters.

Check the versions inside the subnet-router LXC (**LXC → Console**). An LXC shares the Proxmox host kernel, so `uname -r` reports the kernel that actually performs this forwarding:

```bash
tailscale version
uname -r
```

Continue only when both version requirements are satisfied. Install `ethtool`, discover the interface used to reach the DNS server, and inspect the two features inside the subnet-router LXC (**LXC → Console**):

```bash
apt update
apt install --no-install-recommends -y ethtool

NETDEV="$(ip -o route get 192.168.0.101 | awk '{
  for (i = 1; i <= NF; i++) {
    if ($i == "dev") {
      print $(i + 1)
      exit
    }
  }
}')"
test -n "$NETDEV"
printf 'LAN interface: %s\n' "$NETDEV"
ethtool -k "$NETDEV" | grep -E 'rx-udp-gro-forwarding|rx-gro-list'
```

Both feature names must appear. If either is absent or fixed, stop and skip the optimization; do not replace the virtual interface or enable extra LXC features to force support.

The reference Debian LXC uses systemd, so the following one-shot unit reapplies the settings only after the network is online. It does not install or assume `networkd-dispatcher`. Create and start it inside the subnet-router LXC (**LXC → Console**):

```bash
cat >/usr/local/sbin/tailscale-udp-gro <<'EOF'
#!/bin/sh
set -eu
NETDEV="$(ip -o route get 192.168.0.101 | awk '{
  for (i = 1; i <= NF; i++) {
    if ($i == "dev") {
      print $(i + 1)
      exit
    }
  }
}')"
test -n "$NETDEV"
exec /usr/sbin/ethtool -K "$NETDEV" \
  rx-udp-gro-forwarding on rx-gro-list off
EOF
chmod 0755 /usr/local/sbin/tailscale-udp-gro

cat >/etc/systemd/system/tailscale-udp-gro.service <<'EOF'
[Unit]
Description=Apply Tailscale subnet-router UDP GRO settings
Wants=network-online.target
After=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/tailscale-udp-gro
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable --now tailscale-udp-gro.service
systemctl is-active tailscale-udp-gro.service

NETDEV="$(ip -o route get 192.168.0.101 | awk '{
  for (i = 1; i <= NF; i++) {
    if ($i == "dev") {
      print $(i + 1)
      exit
    }
  }
}')"
ethtool -k "$NETDEV" | grep -E 'rx-udp-gro-forwarding|rx-gro-list'
```

The service must report `active`; `rx-udp-gro-forwarding` must be `on`, and `rx-gro-list` must be `off`. The reboot check in the next section is required before treating the optimization as persistent.

If the unit fails, remove the optional persistence files inside the subnet-router LXC (**LXC → Console**):

```bash
systemctl disable --now tailscale-udp-gro.service || true
rm -f /etc/systemd/system/tailscale-udp-gro.service
rm -f /usr/local/sbin/tailscale-udp-gro
systemctl daemon-reload
```

Reboot to restore the interface defaults, then continue without the optimization. See Tailscale's [current performance guidance](https://tailscale.com/docs/reference/best-practices/performance) for upstream changes.

### Approve the Subnet Router and Routes

Device approval and route approval are separate review gates. Approve only the expected machine and exact prefixes.

1. Open the Tailscale [**Machines**](https://login.tailscale.com/admin/machines) page.
2. Find `tailscale-subnet`, confirm that it is a Linux device managed by `tag:subnet`, and review its creation time and addresses.
3. If it shows **Needs approval**, open its menu and select **Approve**.
4. Open the machine details, find **Subnets**, and approve only:

   - `192.168.0.101/32`
   - `192.168.0.102/32`

Do not approve `192.168.0.0/24`, `0.0.0.0/0`, or any unexpected route. If the advertisements are wrong, correct them inside the subnet-router LXC (**LXC → Console**) and then review the admin console again:

```bash
tailscale set \
  --advertise-routes=192.168.0.101/32,192.168.0.102/32
```

In the machine details, confirm that key expiry is disabled for this tagged infrastructure node and that automatic updates are enabled. The reference design leaves node-key expiry disabled to avoid an unattended router failing closed after expiry. Review the device regularly and delete it immediately if it is replaced or compromised. A stricter design may enable expiry, but it must schedule and test reauthentication before the deadline.

Reboot the LXC from the Proxmox node to prove that its service, forwarding, and route advertisements survive a restart (**Node → Shell**):

```bash
pct reboot 103
pct status 103
pct exec 103 -- systemctl is-active tailscaled
pct exec 103 -- sysctl -n net.ipv4.ip_forward
pct exec 103 -- tailscale status
```

Expect `running`, `active`, and `1`, followed by a connected Tailscale status. If the optional optimization was installed, also run `pct exec 103 -- systemctl is-active tailscale-udp-gro.service` and recheck both `ethtool` values inside the LXC. Finally, confirm in **Machines** that the same two routes remain approved. Any failed reboot check blocks remote-client testing.

### Enable Split DNS in Tailscale

A restricted nameserver sends only queries beneath `<MY-DOMAIN>.com` to the private AdGuard Home resolver. Other DNS queries continue through the client's normal resolver. This is split DNS and does not require MagicDNS or a global DNS override.

Go to **DNS → Nameservers → Add nameserver → Custom** and enter:

- **Nameserver:** `192.168.0.101`
- **Restrict to domain:** enabled
- **Domain:** `<MY-DOMAIN>.com`

Save the nameserver and confirm that it appears as a restricted entry for exactly `<MY-DOMAIN>.com`, entered without `*.` or `https://`. Do not enable **Override DNS servers** for this design. MagicDNS may remain in its current state; enabling it only adds names for Tailscale devices and does not replace this restricted rule.

Clients must accept Tailscale DNS settings for split DNS to operate. The standard clients accept them by default, but a previous local preference can disable that behavior. Private homelab names intentionally stop resolving when AdGuard Home or its approved route is unavailable; do not add a public fallback that cannot provide the private rewrite. The next section verifies both the direct DNS route and the operating system's normal hostname resolution. See Tailscale's [DNS documentation](https://tailscale.com/docs/reference/dns-in-tailscale) for current client behavior.

### Connect and Test a Remote Device

Run these tests from a phone or computer connected through mobile data or another network outside the home LAN. Testing from the LAN can hide missing routes or policy errors because the destination is locally reachable.

1. Install the official [Tailscale client](https://tailscale.com/download) and sign in as `<TAILSCALE-USER>`. Do not tag an end-user device.
2. Before approving this new device, confirm that it appears with **Needs approval** and cannot resolve through `192.168.0.101` or open a private homelab hostname. This proves that authentication alone is insufficient.
3. Review the device on **Machines**, approve it, and reconnect if the client does not update immediately.
4. On Linux, explicitly accept subnet routes and Tailscale DNS settings from the client terminal:

   ```bash
   sudo tailscale set --accept-routes=true --accept-dns=true
   ```

   Android, iOS, macOS, tvOS, and Windows normally accept subnet routes automatically. In graphical clients, confirm that **Use Tailscale DNS settings** and **Use Tailscale subnets** are enabled; the Linux command above applies their command-line equivalents.

Verify the direct DNS route from the remote client terminal. Replace the domain placeholder before running the command:

```bash
nslookup "traefik.<MY-DOMAIN>.com" 192.168.0.101
```

The answer must contain `192.168.0.102`, and the request must appear in AdGuard Home's **Query Log**. This command deliberately names the DNS server and therefore proves the direct DNS route, not the operating system's split-DNS selection. Tools such as `nslookup` and `host` can bypass the native split-DNS resolver on some platforms, particularly macOS.

Open `https://traefik.<MY-DOMAIN>.com` in a browser without specifying a DNS server. A valid certificate and the expected Traefik or Authelia page are the authoritative beginner-facing proof that the operating system used split DNS, the `.102/32` route, and HTTPS through Traefik. Disconnect Tailscale and confirm that this private hostname no longer opens through the VPN path, then reconnect before continuing.

Confirm that public DNS remains closed from the remote client terminal:

```bash
nslookup "traefik.<MY-DOMAIN>.com" 1.1.1.1
```

The public resolver must not return a homelab A, AAAA, or CNAME target. If it does, return to the custom-domain chapter and remove the public record before continuing.

Verify the intended HTTP redirect and HTTPS path from the remote client terminal:

```bash
curl -fsSI --max-time 10 http://192.168.0.102
curl -fsSIL --max-time 10 "https://traefik.<MY-DOMAIN>.com"
```

The first request must redirect to HTTPS. The second must complete TLS validation and reach the expected protected route; an Authelia redirect is valid. Do not use `--insecure` to work around a certificate failure.

Now verify that the policy blocks direct administration and unrelated ports. On Linux or macOS, run:

```bash
for TARGET in \
  192.168.0.101:22 \
  192.168.0.101:80 \
  192.168.0.101:3000 \
  192.168.0.102:22 \
  192.168.0.102:53; do
  HOST="${TARGET%:*}"
  PORT="${TARGET##*:}"
  if nc -z -w 5 "$HOST" "$PORT"; then
    printf 'FAIL: unexpected access to %s\n' "$TARGET"
  else
    printf 'PASS: blocked %s\n' "$TARGET"
  fi
done
```

Every line must begin with `PASS`. On Windows PowerShell, run the equivalent checks with `Test-NetConnection <IP-ADDRESS> -Port <PORT> -InformationLevel Quiet`; every result must be `False`. A successful connection is a security failure: inspect all Grants and ACLs for a broader matching rule rather than weakening another control.

Inspect the client's route table and confirm that `192.168.0.101/32` and `192.168.0.102/32` use Tailscale. The default route must continue through the client's local network, and no complete home-LAN route may be present. Be careful on networks that also use `192.168.0.0/24`; the two more-specific `/32` routes should still win for the documented hosts, but other overlapping LAN addresses are not proof of VPN access.

Complete the security and attribution checks:

- In **Logs → Configuration**, confirm that the policy change and device/route approvals identify the expected administrator.
- In AdGuard Home's **Query Log**, confirm the remote private-domain lookup. With default SNAT, the source normally appears as `192.168.0.103`.
- In the Traefik access log and CrowdSec verification described in the reverse-proxy chapter, confirm the remote HTTPS request. The downstream source normally appears as `192.168.0.103`, so use Tailscale records when individual-client attribution is required.
- Inside the subnet-router LXC, inspect `journalctl -u tailscaled --since today --no-pager` for route, authentication, or health errors. Redact identities, addresses, and keys before sharing output.
- Delete or revoke approval for a separate disposable test client, then confirm that it can no longer resolve the private domain or open the HTTPS route. Do not use the only trusted administration device for this revocation test.

If any expected access fails, check—in order—the client's approval, `--accept-routes` and DNS preference, the two route approvals, built-in policy tests, `tailscale status`, IPv4 forwarding, AdGuard Home's Query Log, and Traefik's focused logs. Use `tailscale netcheck` and `journalctl -u tailscaled` for connection diagnostics. Fix the failing layer; do not add a `/24` route, an allow-all Grant, public DNS record, disabled certificate validation, or router port forward as a workaround.

## Maintenance and Recovery

The LXC is small, but it is a high-value remote-access gateway. Maintain its operating system, Tailscale identity, tailnet policy, and SaaS-side approvals as separate layers.

### Update the Subnet Router

Tailscale stable-track automatic updates are enabled in the reference setup. Review **Machines** regularly for stale devices, disabled auto-updates, health warnings, and available security updates. Subscribe to Tailscale's [security bulletins](https://tailscale.com/security-bulletins) and review release notes before a deliberate version change.

Before a Debian, kernel, or manual Tailscale update, create a current Proxmox snapshot or verified guest backup and record the working versions. Then run inside the subnet-router LXC (**LXC → Console**):

```bash
tailscale version
tailscale update --dry-run
apt update
apt upgrade
```

Apply one layer at a time. Reboot when required and repeat the forwarding, route, split-DNS, HTTPS, denied-port, and log checks. If an update fails, use direct **LXC → Console** access and the recorded version or LXC backup; do not expose services publicly while the VPN is unavailable.

### Back Up and Recover the Configuration

A Proxmox guest backup preserves the Debian filesystem and Tailscale state directory, including the node's private identity, but it does not back up the hosted tailnet policy, device approvals, route approvals, split-DNS settings, or identity-provider account. Encrypt or otherwise restrict access to that credential-bearing backup. Keep a protected copy of the policy and a setup record containing the two routes, restricted DNS suffix, tag ownership, key-expiry decision, and recovery contacts. Do not retain a used auth key.

Never run a restored copy and the original LXC simultaneously because they contain the same node identity. For a clean rebuild or suspected compromise, the safer path is to delete the old machine from Tailscale, create a new one-off tagged key, re-enroll the replacement, approve it manually, and repeat every acceptance test.

### Revoke Access or Decommission the Router

For a lost client, remove or revoke the device on **Machines** and confirm that its access stops. Removing an auth key alone does not remove an enrolled device. For a compromised subnet router, first disable its approved routes and delete its machine identity from the admin console, then isolate the LXC through Proxmox and investigate from direct console access.

To decommission the complete VPN path deliberately:

1. Disable both approved routes and remove `tailscale-subnet` from **Machines**.
2. Revoke any unused enrollment key and remove the restricted nameserver if no other subnet router provides it.
3. Remove the Grants, tests, group, and tag owner only when no other required device or user depends on them.
4. Run `tailscale logout` in the LXC, take a final backup if required, stop the protected LXC, and remove it only after verifying the exact CT ID.
5. Confirm from an external client that the private DNS and HTTPS routes are no longer reachable and that no public exposure was introduced.

Record the change and retain only the policy and recovery evidence required by your backup and audit policy.
