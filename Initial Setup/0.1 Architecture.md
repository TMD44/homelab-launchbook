# Architecture

Before touching any configuration, it helps to understand how the homelab's parts fit together. This chapter introduces the physical host, Proxmox VE, the LXC and Docker layers, central management, networking, security, storage, monitoring, and resilience choices used by the reference setup. Knowing which component depends on which other component will make the later setup chapters easier to follow and will help you diagnose problems without treating the homelab as one opaque system. The diagram gives the high-level view; the sections that follow explain each layer and the decisions behind it.

The LXC IDs, hostnames, and IPv4 addresses shown here are reference values, not placeholders or Proxmox defaults. You may adapt them to your network. Values such as `<MY-DOMAIN>` are placeholders and must be replaced wherever they appear.

## Architecture Layers

The reference architecture is a stack of cooperating layers. A lower layer normally provides the environment or connectivity needed by the layer above it, while management, security, backup, and monitoring cross several layers. This separation makes components replaceable and limits many service failures, but it also gives the operator more individual systems to understand and maintain.

### Physical Infrastructure Layer

The baseline starts with one physical server connected to the home router or switch. The router remains the default gateway, provides DHCP during the initial setup, and connects the private LAN to the Internet. The server runs Proxmox VE and is the shared hardware failure domain for the reference LXC containers.

An uninterruptible power supply (UPS) is recommended where orderly shutdown during an outage matters. A physically separate Proxmox Backup Server (PBS), shown by the reference address `192.168.0.15`, is also recommended when the budget permits because it keeps backups outside the primary server's hardware failure domain. The guide supports an optional PBS LXC on the primary node as a lower-cost alternative, but that alternative cannot protect against loss of the node itself. None of these additions turns the single-node design into high availability.

### Proxmox VE and Virtualization Layer

Proxmox VE owns the physical server's CPU, memory, storage, network bridge, firewall, and guest lifecycle. In the reference plan, the node uses `192.168.0.11` on the LAN and creates the Linux bridge `vmbr0`. The node then presents virtual network interfaces and virtual disks to its guests.

Application workloads do not run directly on the Proxmox host. Keeping Docker and application data out of the host reduces package conflicts and keeps the hypervisor focused on virtualization, storage, networking, backup, and guest recovery. Host-level infrastructure that must interact directly with hardware, such as the reference Network UPS Tools (NUT) service for a USB-connected UPS, is a deliberate exception and should remain narrowly scoped.

The baseline uses one node because it is affordable and straightforward to operate. The tradeoff is that node maintenance or failure affects every local guest. Proxmox clustering and high availability can be added later, but they require additional nodes, quorum, suitable storage, spare capacity, and a reliable network; installing a second node alone does not remove the failure domain.

### Workload Isolation Layer: VMs and LXC Containers

Proxmox can run both virtual machines (VMs) and LXC containers. The reference setup normally uses **unprivileged LXC containers**: each has its own hostname, filesystem, resource limits, and LAN address, while sharing the Proxmox host's Linux kernel. This is efficient and makes services easier to back up or restart independently, but it is not the same security boundary as a VM with its own kernel.

The current reference placement is:

| Guest | Reference address | Runtime and responsibility |
| --- | --- | --- |
| LXC `100`, `komodo` | `192.168.0.100` | Docker; Komodo Core, local Periphery, and its database backend |
| LXC `101`, `adguard-dns1` | `192.168.0.101` | Docker for AdGuard Home; systemd-managed Periphery |
| LXC `102`, `traefik` | `192.168.0.102` | Docker for Traefik, CrowdSec, and Authelia; optional on-demand code-server; systemd-managed Periphery |
| LXC `103`, `tailscale-subnet` | `192.168.0.103` | Tailscale as a native systemd service; no Docker or Periphery |
| LXC `104`, `gotify` | `192.168.0.104` | Docker for Gotify; systemd-managed Periphery |
| LXC `105`, `monitoring` | `192.168.0.105` | Docker for the monitoring and dashboard services; systemd-managed Periphery |
| Optional LXC `200`, `proxmox-backup-server` | `192.168.0.200` | Native PBS services; no Docker or Periphery |

The matching ID and final IP octet are only a human-friendly convention. Proxmox does not derive one from the other, and both must be configured explicitly. A VM remains the better boundary for workloads that need a different operating system or kernel, stronger isolation, vendor-supported Docker deployment, complex kernel features, or safer hardware passthrough.

### Runtime Layer: Docker and Systemd Services

Most application LXCs contain their own Docker Engine. The nesting is therefore **Proxmox host → unprivileged LXC → Docker Engine → Docker container**. Each engine has an independent daemon, images, volumes, Compose projects, and Docker networks. A network name on one LXC has no connection to a network with the same name on another LXC.

Related containers can communicate over an engine-local Docker network. Traefik, CrowdSec, and Authelia share `traefik-net` inside LXC `102`; the optional code-server joins that same network and publishes no host port. Komodo's companion alerting stack uses the engine-local `komodo_default` network. Other application stacks publish only the ports needed for Traefik, trusted-LAN administration, or recovery to the LXC's LAN address. Published ports cross the Docker boundary, so they must not be mistaken for traffic protected automatically by Traefik.

Not every LXC runs Docker. Tailscale and PBS run as native systemd services, as does Periphery on Docker hosts other than the Komodo LXC. NUT can run on the Proxmox host when direct UPS access is required. Native services avoid unnecessary container layers for host- or network-facing infrastructure, but their files and lifecycle must be managed with the operating system rather than through a Compose stack.

### Management Layer: Komodo Core and Periphery

Komodo provides one management interface for several otherwise independent Docker engines. Core runs in LXC `100` and stores the desired resources and deployment metadata. A Periphery agent runs alongside the local engine and on the other Docker LXCs so Core can deploy Compose stacks, inspect containers, and perform approved management actions on each server.

This is a management plane, not a runtime dependency or cluster scheduler. If Core is unavailable, already running containers continue according to their Docker restart policies, although centralized deployment and visibility are lost. If one Periphery agent is unavailable, Core loses control of that Docker host while its existing workloads can continue. Periphery's access to Docker is a privileged management trust boundary: an account or token able to control it can materially affect that LXC's workloads and data.

Central management reduces repetitive administration without merging all workloads into one Docker engine. The cost is another control plane to secure, back up, and restore, plus a dependency on correct server enrollment and deployment ordering.

### Application and Service Layer

The upper layer contains the services people actually use and the supporting services that make those applications reachable and operable:

- **Foundation and access:** AdGuard Home provides local DNS; Traefik provides private HTTPS routing; Tailscale provides approved remote access.
- **Request security:** CrowdSec evaluates the traffic connected to Traefik, while Authelia adds centralized authentication and multi-factor authentication to selected browser-compatible routes.
- **Management:** Komodo manages the distributed Docker workloads. The optional code-server provides on-demand administrative editing for the reverse-proxy LXC.
- **Operations:** Beszel, Uptime Kuma, MySpeed, and Homepage provide metrics, availability checks, Internet-performance history, and a dashboard. Gotify receives notifications.
- **Protection:** PBS stores and verifies Proxmox backups, and NUT coordinates UPS-aware shutdown where configured.

These are roles rather than claims that every component is independently redundant. Several operations services share LXC `105`, Traefik's security components share LXC `102`, and all baseline LXCs share one Proxmox node. Grouping related components is efficient, but a failure in a shared layer can remove several functions at once.

### Networking and Access Layer

The reference design uses IPv4 on the home LAN and adds Tailscale only for the narrow remote routes needed by this guide. It separates name resolution, request routing, and backend service access so each stage can be tested independently.

#### Local Network and Proxmox Bridge

`vmbr0` acts like a virtual switch. It connects the Proxmox node and each attached LXC virtual interface to the physical LAN through the server's network adapter; it is not a second router and does not create a second IP range. The router at the reference address `192.168.0.1` remains the default gateway.

Giving foundational LXCs stable LAN addresses makes DNS targets and Traefik backend definitions predictable. It also means that a service with a published port may be reachable directly from a trusted LAN client, bypassing the reverse proxy. That direct path is useful for bootstrap and recovery, but it needs its own access controls and should not be treated as equivalent to the proxied path.

#### DNS and Reverse Proxy

After the DNS chapter's cutover, DHCP tells LAN clients to use AdGuard Home at `192.168.0.101`. AdGuard's local wildcard rewrite resolves names below `<MY-DOMAIN>.com` to Traefik at `192.168.0.102`. DNS chooses the destination IP; it does not select a backend service or proxy the request.

Traefik listens on ports `80` and `443`. Port `80` redirects permanently to HTTPS. On port `443`, a file-provider router matches the requested hostname and forwards the request to an explicitly configured backend. The setup deliberately does not mount the Docker socket into Traefik, so routes are not discovered implicitly from container labels.

Traefik terminates browser HTTPS with a wildcard certificate obtained from Let's Encrypt through Cloudflare DNS-01 validation. Cloudflare is used for the public DNS challenge and is not in the normal application-data path. The public zone does not need a public homelab `A`, `AAAA`, or `CNAME` record, and no inbound router port is opened. The certificate process still needs outbound Internet access, publishes a temporary DNS `TXT` challenge, and results in public Certificate Transparency records; “private” here describes service reachability, not invisibility of the domain or certificate.

#### Request Flow Through the Homelab

For a concrete browser example, consider `https://adguard.<MY-DOMAIN>.com` from a LAN client:

1. **The client resolves the name.** Its DNS query goes to AdGuard Home at `192.168.0.101`, which returns Traefik's address, `192.168.0.102`, for the local wildcard name.
2. **The client connects to Traefik.** The browser opens an encrypted connection to `192.168.0.102:443`. If the user began with HTTP, Traefik redirects the browser to HTTPS first.
3. **Traefik selects the route and handles TLS.** The `adguard.<MY-DOMAIN>.com` host rule selects the AdGuard router. Traefik presents the wildcard certificate to the browser and decrypts the request at the proxy boundary.
4. **The middleware chain evaluates the request.** This route uses `secured-auth`: the private-client allowlist runs first, CrowdSec and its AppSec checks run next, and Authelia then requires the configured browser authentication. Security headers, rate limiting, and the in-flight request limit are also applied.
5. **Traefik contacts the backend.** After the checks pass, Traefik forwards the request to `http://192.168.0.101`. The backend leg is private LAN traffic and is separate from the browser's HTTPS connection.
6. **The response returns through the same proxy.** AdGuard Home sends its response to Traefik; Traefik applies response middleware as applicable, encrypts the browser-facing leg, and returns the page to the client.

Authentication is route-specific. Komodo uses the `secured` chain without Authelia because it needs its own application authentication and API-compatible behavior; its backend is `http://192.168.0.100:9120`. The optional code-server uses `secured-auth`, but its backend is reached as `http://traefik_code_server:8443` over the engine-local `traefik-net` rather than through an LXC-published port. A request made directly to a published backend port does not pass through either Traefik chain.

This verified sequence is therefore **DNS → Traefik and TLS → route-specific security and optional Authelia → backend service → Traefik → client**. DNS resolution, authentication, and the backend response are separate steps; failure at any one of them produces a different symptom.

#### Remote Access with Tailscale

Remote clients use an encrypted Tailscale connection to the subnet-router LXC at `192.168.0.103`. Split DNS sends only queries for `<MY-DOMAIN>.com` to AdGuard Home, and the reference router advertises narrow routes for the DNS server and reverse proxy rather than the entire LAN. The client therefore follows the same AdGuard → Traefik → service path after entering the home network.

With Tailscale's default subnet-router source NAT, AdGuard and Traefik normally see the subnet router's LAN address rather than the remote device's individual Tailscale address. That behavior is part of the allowlist and logging model. The design is not an exit node, does not require inbound Internet port forwarding, and does not expose all LAN subnets. If the Tailscale LXC or its narrow routes fail, remote access fails while ordinary LAN access remains available.

Tailscale's coordination services are an external control-plane dependency. Application traffic uses a direct peer path when possible and the Tailscale relay infrastructure when a direct path cannot be established. Narrow `/32` LAN routes reduce exposure and avoid advertising the whole home subnet, although the network plan must still consider address overlap and the availability of AdGuard and Traefik. See Tailscale's current [subnet-router](https://tailscale.com/docs/features/subnet-routers) and [DNS](https://tailscale.com/docs/reference/dns-in-tailscale) documentation for those boundaries.

### Authentication and Security Layer

Security is layered because no single control covers every path:

- The router has no inbound application port forwards, and public DNS does not publish a homelab address for the private application names.
- The Proxmox management firewall restricts host administration to intended sources, and Proxmox accounts use least privilege and multi-factor authentication where the guide configures them. Guest and Docker-service access remains a separate responsibility.
- Unprivileged LXCs reduce host privilege compared with privileged containers, while separate guests and per-engine Docker networks limit accidental coupling. Because LXCs share the host kernel, this is containment rather than VM-equivalent isolation.
- Traefik's `secured` chain applies a private-client allowlist, CrowdSec/AppSec checks, security headers, rate limiting, and an in-flight limit. `secured-auth` adds Authelia between CrowdSec and the response-oriented controls.
- Authelia is used only for suitable browser routes. Services that need native API, WebSocket, or application-login behavior retain their own authentication behind `secured`.
- Protected files and Compose secrets carry sensitive values such as the Cloudflare API token and Authelia keys. Traefik uses the file provider and does not receive the Docker socket.

These controls protect only the paths connected to them. CrowdSec sees Traefik access logs and proxied requests, not every packet on the LAN. Authelia does not guard `secured` routes or direct ports. The default CrowdSec/AppSec configuration is intentionally fail-closed for its proxied checks, so a security dependency outage can deny those requests instead of silently bypassing inspection.

The optional code-server is an administrative surface and should remain stopped except during maintenance. Its tracked Compose file publishes no host port, uses `1000:1000`, joins `traefik-net`, and is reached through the `secured-auth` route. It intentionally mounts the full Traefik configuration directory and CrowdSec acquisition directory plus the Authelia configuration file as read-write. That directory-oriented scope—not an individual-file allowlist—is the security boundary; secrets, certificate state, application data, the Docker socket, and the rest of the LXC filesystem remain outside it.

### Storage, Backup, and Recovery Layer

Proxmox separates guest and backup storage from the application view. In the default layout, `local` holds content such as ISO images, container templates, and local backup files, while `local-lvm` normally holds VM disks and LXC root filesystems. Inside an LXC, Docker bind paths such as `/GOTIFY/data` appear to be ordinary guest directories even though their bytes ultimately live on Proxmox-managed storage.

A Proxmox guest backup protects the LXC root filesystem and storage-backed mount points that are included with the **Backup** flag. It does not automatically include LXC bind mounts or device mounts that refer to host paths. A running database may also need an application-native dump or another consistency step; having the files inside a guest backup does not by itself prove application-consistent recovery.

PBS adds deduplicated backup storage, retention, pruning, garbage collection, and verification. A dedicated PBS system at `192.168.0.15` provides a separate hardware failure domain. The optional PBS LXC at `192.168.0.200` is useful for accidental deletion and some guest failures but remains vulnerable to loss of the same Proxmox node and storage. PBS integrates directly with Proxmox over the private network and a verified fingerprint; it is not an application that needs to traverse Traefik.

Snapshots, backups, and replication solve different problems. A snapshot is a short-term point-in-time state tied to its storage. A backup is an independently retained recovery copy. Replication creates another copy for availability or migration but can reproduce deletion or corruption and may lose changes since the last synchronization. Whatever the mechanism, the architecture is only recoverable after representative restores are tested and the PBS configuration, encryption material, and credentials are protected separately. See [Understand backups, snapshots, and replication](../Other%20guides/Storage%20and%20recovery/Understand%20backups,%20snapshots,%20and%20replication.md) for the dedicated decision guide.

### Monitoring, Notifications, and Operations Layer

The operations stack intentionally uses several focused tools. Komodo shows deployment and container state; Beszel provides system metrics; Uptime Kuma checks availability; MySpeed records Internet performance; Homepage collects useful links and status; and Gotify receives notifications from supported services. This separation lets a tool be replaced without redesigning the workload layer, but it also requires the operator to decide which tool is authoritative for each signal.

LXC `105` groups Beszel Hub, Uptime Kuma, MySpeed, and Homepage. If that LXC or the Proxmox node fails, those tools cannot independently report their own complete outage; an external monitor is needed for that failure mode. Gotify is separate, so a monitoring service can still send to it, but a Gotify outage removes delivery rather than stopping the protected workloads.

The tracked Beszel Compose intentionally defines **Beszel Hub only**. Each system that should report metrics still needs a separately installed and enrolled Beszel Agent, managed on that monitored system rather than as part of the central Hub stack. Architecture and alert coverage must be assessed from those actual enrollments, not inferred from the Hub container.

Monitoring observes behavior; it does not create redundancy or guarantee recovery. Alerts also depend on the monitored service, monitoring stack, notification server, network, and power path remaining sufficiently available to deliver them.

### Power Protection and Resilience Layer

In the reference UPS design, a USB-connected UPS is monitored by NUT on the Proxmox node. The host acts as the primary system and can optionally provide status to a physically separate PBS as a secondary system. The router and switch must also remain powered if the secondary shutdown signal depends on the LAN.

When the battery reaches the configured critical condition, the goal is an orderly Proxmox shutdown. Normal guest shutdown follows Proxmox start/shutdown ordering in reverse and respects guest timeouts. Backup and snapshot jobs should not be started once the environment has entered a critical-battery state because they consume time and storage I/O needed for shutdown.

The PowerMaster route remains a compatibility-dependent alternative, not part of the documented Proxmox VE 9/Debian 13 reference path. The currently documented PowerMaster `1.2.3` package is not presented as a supported substitute on that baseline. A UPS improves tolerance of short outages and enables graceful shutdown; it is neither high availability nor a backup.

## Architecture Decisions and Key Concepts

The layers describe where components live. The following decisions explain why the repository places them there, what that design gains, and what the operator accepts in return.

### LXC Containers vs Virtual Machines

An LXC container virtualizes a Linux userspace while sharing the Proxmox host's kernel. A VM virtualizes hardware and runs a separate guest kernel. Both can isolate workloads, but their boundaries and operational costs differ.

| Consideration | Unprivileged LXC container | Virtual machine |
| --- | --- | --- |
| Isolation | Separate userspace and mapped user IDs, but a shared host kernel | Separate guest kernel and stronger workload boundary |
| Resources | Lower memory and storage overhead; fast startup | More overhead for a complete guest OS |
| Compatibility | Linux only; host-kernel and LXC restrictions can affect software | Broader OS, kernel, and vendor-support compatibility |
| Maintenance | Fewer full guest systems, but nested Docker needs LXC-specific care | More guest patching, but a conventional Docker host |
| Hardware and kernel features | Possible but often needs explicit device mappings or added features | Usually clearer for passthrough, custom kernels, and appliances |
| Failure boundary | Guest processes/files separated, host kernel still shared | Guest kernel failures and exploits are more strongly separated |

This repository normally chooses unprivileged LXCs because the applications are Linux-based and the single-node reference benefits from their efficiency. Choose a VM when stronger isolation, a non-Linux OS, a custom kernel, complex hardware access, live migration expectations, or vendor-supported Docker behavior matters more than the resource savings. Proxmox's own documentation recommends running application containers such as Docker inside a QEMU VM when that conventional boundary is preferred; this guide's LXC design is a deliberate homelab tradeoff, not a universal best practice. See the [Proxmox VE container documentation](https://pve.proxmox.com/pve-docs/pct.1.html) and [Choose between an LXC container and a virtual machine](../Other%20guides/Choose%20between%20an%20LXC%20container%20and%20a%20virtual%20machine.md) for deeper guidance.

### Why Docker Runs Inside Unprivileged LXCs

Docker provides a familiar application-packaging ecosystem, while Docker Compose gives each stack an explicit, repeatable definition. The surrounding LXC gives that Docker engine a separate LAN identity, resource limits, filesystem, backup unit, and restart boundary. This combination keeps Docker off the Proxmox host and lets Komodo manage several small engines instead of one engine containing every service.

The additional layer is not free. Docker inside LXC needs selected features such as nesting and `keyctl`, inherits the host kernel, and can expose compatibility issues that would not exist in a normal VM. Docker control is effectively root-equivalent inside the guest, so Periphery and any socket access require strong protection. Troubleshooting may cross Proxmox, LXC, Docker, and application boundaries, and a guest backup containing live database files may still need application-consistent preparation.

The choice fits a resource-conscious, Linux-only homelab whose operator accepts that complexity. A VM-based Docker host is the safer default when isolation or vendor support outweighs density, and installing Docker directly on Proxmox is intentionally avoided because it couples application packages, storage, and failures to the hypervisor itself.

### Service Placement and Failure Domains

Placement balances isolation against overhead. A separate LXC narrows many maintenance and failure effects, while a shared LXC reduces operating-system instances and keeps tightly related containers on one local Docker network. The reference design uses both patterns rather than claiming that every service needs its own guest.

#### Dedicated LXC Containers

Foundational services with distinct network identities or recovery paths receive dedicated LXCs. AdGuard Home, Tailscale, Gotify, and the Komodo management plane can be restarted or restored without rebuilding the other groups. Dedicated placement also makes resource limits and guest backups easier to reason about.

The boundary is still the LXC, not necessarily one Docker container. Komodo Core shares its guest with its database and local Periphery, and AdGuard shares its guest with the Periphery service used to manage that Docker engine. Dedicated guests consume more memory, addresses, patching time, and backup capacity than a single large Docker host.

#### Shared LXC Containers

Components that operate as one request path or one operational function may share a guest. Traefik, CrowdSec, and Authelia share LXC `102` and `traefik-net`; the monitoring and dashboard tools share LXC `105`. Local communication becomes simple and the groups can be backed up together.

The tradeoff is a larger shared failure domain. Losing LXC `102` removes private HTTPS routing and its attached security services together. Losing LXC `105` removes several kinds of visibility at once. Related placement improves convenience, not redundancy, and a resource-heavy member can affect its neighbors unless limits are planned.

#### Systemd-Native Services

Tailscale runs natively in LXC `103` because the guest's purpose is network routing, not application hosting. PBS also uses native services, and NUT runs at the host layer when it must monitor a USB device. Periphery runs under systemd on the remote Docker hosts so it can manage the local engine without becoming part of the application stacks it controls.

This reduces unnecessary Docker nesting for infrastructure services, but it creates two management methods: Komodo/Compose for applications and operating-system service management for native components. Backup and update procedures must account for both.

### Centralized Management of Distributed Docker Workloads

The Komodo Core → Periphery model centralizes intent and visibility while leaving execution distributed. Each LXC keeps its own Docker daemon, networks, persistent paths, and restart behavior. A deployment can therefore target one server without giving every application a shared Docker network or storage namespace.

Core does not proxy application traffic, provide storage replication, or automatically move workloads when a server fails. It also does not need to stay online for already created containers to keep running. Restore planning must include Core's own state and the Compose/environment/configuration files that define each remote stack; the visible dashboard alone is not a recovery copy.

This pattern is a good fit when the operator wants explicit Compose deployments and independent failure domains with one control surface. It is more involved than managing a single Docker host and requires careful enrollment, credentials, permissions, and ordering for foundational services such as DNS, Traefik, and notifications.

### Private-by-Default Network Design

The reference design keeps application traffic on the home LAN or Tailscale. Local DNS returns a private address, the router has no inbound application port forwards, and Traefik issues public certificates by proving DNS control rather than accepting an inbound validation connection. Remote users enter through Tailscale and follow the same local DNS and reverse-proxy path.

This reduces exposure to opportunistic Internet traffic and keeps routing under local control. It does not remove the need for authentication, patching, logging, backups, or firewalling: a compromised LAN or approved VPN client is already inside the private boundary, and published backend ports can bypass Traefik. DNS-01 also relies on narrowly scoped Cloudflare credentials and outbound access to public services.

Private HTTPS gives stable names and trusted browser encryption without making services public. Readers who intentionally publish a service need a separate threat model, public-DNS plan, router/firewall rules, rate limits, monitoring, and recovery plan; that is outside this baseline.

### Persistent Data and Recovery Boundaries

The recovery unit spans several layers: the application writes to a Docker bind path or volume, that path lives in an LXC filesystem or included mount point, Proxmox snapshots or backs up the guest, and PBS may retain the resulting backup. A green container health check proves none of those recovery stages by itself.

For every stateful service, record its persistent paths, credentials or encryption keys, database-consistency method, guest/storage location, backup inclusion, retention, and tested restore procedure. Treat LXC bind mounts and hardware device mappings as explicit exceptions because ordinary guest backup does not include them. Protect the Komodo control state and configuration repository as well as the application data needed to rebuild remote stacks.

A local snapshot is convenient for short rollback, PBS provides retained backups, and a replicated copy supports availability or migration. They are complementary, not interchangeable. The strongest reference placement is a dedicated PBS with independently protected configuration and tested restores; the PBS-in-LXC alternative trades fault isolation for lower cost.

### Dependency and Failure Behavior

Understanding what continues running is more useful than calling every component “critical.” The table describes the reference behavior; application-specific clients and custom changes can add dependencies.

| Unavailable component | Expected effect | What can remain available |
| --- | --- | --- |
| Proxmox node | All local guests and their services stop | A physically separate PBS and unrelated network devices |
| Komodo Core | Central deployment, control, and consolidated visibility stop | Existing Docker containers follow their own restart state |
| One Periphery agent | Komodo cannot manage that Docker engine | Existing workloads on that LXC can continue |
| AdGuard Home | Private names and split-DNS resolution fail | Trusted-LAN direct-IP recovery paths |
| Traefik | Private HTTPS hostnames and proxied security path fail | Trusted-LAN direct backend ports, where deliberately published |
| Authelia | Routes using `secured-auth` fail authentication | `secured` routes with application-native authentication |
| CrowdSec/AppSec | The configured fail-closed proxied checks can deny requests | Paths that do not use that Traefik middleware, subject to their own controls |
| Tailscale subnet router | Remote DNS and proxy routes fail | Ordinary LAN access |
| Gotify | Notifications cannot be delivered there | Workloads and monitoring collection can continue |
| Monitoring LXC | Local metrics, checks, speed history, and dashboard are lost | Core application services; external monitoring if configured |
| PBS | New PBS backups and PBS-based restores are unavailable | Running guests and any independent recovery copies |
| UPS or its network path | Automated orderly-shutdown coverage is reduced or lost | Workloads while utility power and hardware remain available |
| Internet or an external provider | Renewals, updates, registry pulls, and remote coordination may be affected | Existing local services that need no current external call |

The table is not a substitute for testing. Cached DNS, active sessions, peer connectivity, database behavior, and Docker restart policies can change the exact user-visible timing.

### Single-Node Architecture vs Proxmox Cluster

The supported baseline is one Proxmox node. It is simple to learn, economical, and adequate when planned maintenance and a shared hardware failure domain are acceptable. Backups and a UPS improve recoverability and shutdown behavior, but they do not keep workloads online when that node is down.

A Proxmox cluster provides centralized management and the foundation for migration and high availability. It does not automatically provide redundant storage, spare compute, or application-level resilience. Quorum requires a reliable majority of votes; a two-node design commonly needs an independent QDevice vote to avoid an unsafe or unavailable tie, while three voting members provide a clearer majority. High availability also needs working fencing/watchdog behavior, compatible guest storage or replication, enough capacity on surviving nodes, and the network paths those features depend on.

Shared storage must itself be resilient or it becomes another single point of failure. ZFS replication avoids a shared storage system but is periodic rather than synchronous, so changes since the last completed replication can be lost, and replication is still not a backup. Plan the complete failure and maintenance behavior before enabling HA. See the current [Proxmox VE Administration Guide](https://pve.proxmox.com/pve-docs/pve-admin-guide.pdf), [Plan a Proxmox cluster and quorum](../Other%20guides/Advanced%20guides/High%20availability/Plan%20a%20Proxmox%20cluster%20and%20quorum.md), and [Choose shared storage or ZFS replication](../Other%20guides/Advanced%20guides/High%20availability/Choose%20shared%20storage%20or%20ZFS%20replication.md).

### Why Not an All-in-One Homelab Platform?

All-in-one platforms can be excellent when fast deployment, a curated app store, and one friendly interface matter more than understanding or customizing every layer. They package many decisions that this repository asks the operator to make explicitly. The products below are not interchangeable, and their capabilities and licensing can change; the linked official pages are the source to recheck before choosing one.

| Platform | Current official positioning | Where it can fit well | Architectural consideration for this guide |
| --- | --- | --- | --- |
| [CasaOS](https://github.com/IceWhaleTech/CasaOS) | Apache-2.0 Linux-hosted personal-cloud UI and Docker app ecosystem | Adding an approachable dashboard and app store to a supported Linux host | The host and its app conventions become the main unit; this guide instead makes Proxmox guests, explicit Compose files, and per-service recovery boundaries visible |
| [ZimaOS](https://www.zimaspace.com/docs/zimaos/get-started) | Vendor-managed NAS and personal-cloud appliance experience with integrated applications and updates | Users who want storage and apps delivered as one polished appliance | The managed OS and release model reduce setup work but give the operator less reason—and sometimes less freedom—to replace layers independently; check current device and license terms on the [official product page](https://www.zimaspace.com/zimaos) |
| [umbrelOS](https://github.com/getumbrel/umbrel) | Standalone personal-server OS and Docker-based app framework, currently distributed under the PolyForm Noncommercial license | A curated, appliance-like home-server experience, especially on supported hardware | The curated framework simplifies installation; [DIY installations](https://github.com/getumbrel/umbrel/wiki/umbrelOS-on-Umbrel-Home-vs.-DIY) have a different support expectation, while this guide prioritizes portable configuration and explicit infrastructure boundaries |
| [Cosmos Cloud](https://docs.cosmos-cloud.io/) | Docker server manager and gateway combining application deployment with proxy, authentication, VPN, and security features | Users who want one integrated web interface for application and gateway functions | Integration removes wiring work but couples several control and request-path roles and requires broad host control; its [repository](https://github.com/azukaar/Cosmos-Server) currently applies the Commons Clause to its Apache-2.0 license |

Compared with a typical single-host all-in-one deployment, the Proxmox VE → unprivileged LXC → Docker/systemd → Komodo design makes several tradeoffs:

| Area | This repository's modular design | Typical all-in-one experience |
| --- | --- | --- |
| First setup and learning | Longer setup and a steeper learning curve across several layers | Faster onboarding and fewer infrastructure choices |
| Applications and portability | Repository-owned Compose/configuration can be inspected, adapted, and moved component by component | Curated packages are convenient but may depend on platform metadata or lifecycle |
| Isolation and failures | Services can use separate guests, addresses, backups, and resource limits | A single host/runtime is simpler but often creates a broader default failure domain |
| Networking and authentication | DNS, Traefik, Tailscale, CrowdSec, and Authelia are explicit and replaceable | Integrated gateway controls reduce wiring but follow the platform's model |
| Backup and recovery | Recovery boundaries can be designed per guest and tested with PBS | Platform backup features may be easier, but scope and portability must be evaluated product by product |
| Upgrades and troubleshooting | Components can be upgraded independently and traced through visible files | Coordinated releases can be easier, but failures may cross an abstraction the user did not configure |
| Hardware and growth | Proxmox can add VMs, LXCs, storage choices, and a planned cluster path | Appliance-first platforms usually optimize a narrower supported deployment model |
| Ongoing responsibility | The operator owns patching, compatibility, credentials, monitoring, and recovery design | The platform makes more defaults and may provide a more unified update/support path |

The modular approach is chosen for control, transparent configuration, component replacement, stronger separation, practical learning, and a clearer path to more nodes or different workloads. Those benefits are valuable only if the operator is willing to maintain the extra layers. A well-supported all-in-one platform is the better choice for many homes, particularly when simplicity and time-to-service outweigh customization.

### Architectural Tradeoffs and Limitations

The reference architecture is intentionally understandable and modular, not automatically highly available or maintenance-free. Its main limitations are:

- One Proxmox node remains the dominant compute and storage failure domain.
- Docker inside unprivileged LXCs is efficient but shares the host kernel, needs added LXC features, and differs from Proxmox's conventional VM recommendation for Docker workloads.
- Separate LXCs and Docker engines improve boundaries while increasing patching, backup, credential, and troubleshooting work.
- AdGuard, Traefik, Tailscale, Authelia, Komodo, PBS, monitoring, and Gotify each have distinct dependency effects; central dashboards do not make them redundant.
- Traefik's controls apply only to proxied routes. Published backend ports, native services, Proxmox management, PBS, and Periphery require their own restrictions.
- The default monitoring tools run on the infrastructure they observe, so complete node or monitoring-LXC failure needs an external vantage point.
- DNS-01 certificates, software updates, image pulls, and remote coordination retain outbound or third-party dependencies even though applications are not publicly exposed.
- Recovery depends on correct persistent-path mapping, application-consistent data, independently protected credentials, and tested restores—not merely successful scheduled backup jobs.
- code-server's writable directory mounts grant broader configuration access than an individual-file allowlist, and Beszel coverage depends on separately deployed Agents rather than the central Hub Compose; both boundaries require deliberate access review and runtime verification.

These are accepted tradeoffs for the guide's resource-conscious, learning-oriented baseline. Readers should change the design where their threat model, availability target, hardware, support requirements, or willingness to operate the system differs.
